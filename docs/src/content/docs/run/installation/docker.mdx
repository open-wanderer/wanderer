You can install <span class="-tracking-[0.075em]">wanderer</span> components either via Docker ([Quick Setup](./quick) or [Manual Setup](./docker)) or [from source](./from-source).

## Prerequisites

<span class="-tracking-[0.075em]">wanderer</span> uses several secrets for database access, to encrypt passwords, private keys, and to secure communication. The secrets are: `MEILI_MASTER_KEY`, `POCKETBASE_ENCRYPTION_KEY` and `POCKETBASE_PROXY_SECRET`. You need to generate these secrets. For example using:

```bash
# MEILI_MASTER_KEY and POCKETBASE_PROXY_SECRET (one each)
openssl rand -hex 32
# Example output: 1e85a99427bd2543aacc24c99419183756eaeccd0e3485c9ac2ac2ab110e72f1

# POCKETBASE_ENCRYPTION_KEY (must be exactly 32 characters)
openssl rand -hex 16
# Example output: ce7f0ddb97100c42e6409a8537c11e23
```

:::caution
Do not share these keys with anyone!
:::

## Start

After cloning the repository, you will find a [`docker-compose.yml`](https://github.com/open-wanderer/wanderer/blob/main/docker-compose.yml) and a [`.env.example`](https://github.com/open-wanderer/wanderer/blob/main/.env.example) file in the root directory. Copy `.env.example` to `.env` and fill in `ORIGIN` and the required secrets `MEILI_MASTER_KEY`, `POCKETBASE_ENCRYPTION_KEY` and `POCKETBASE_PROXY_SECRET` with the values you generated [above](#prerequisites):

```bash
cp .env.example .env
```

Then start everything by running:

```bash
docker compose up -d
```

If a required value is missing, `docker compose` stops and names it.

## Configuration Notes

If you're not hosting <span class="-tracking-[0.075em]">wanderer</span> at `http://localhost:3000`, update `ORIGIN` in `.env` accordingly:

```env
ORIGIN=http(s)://<your_domain>:<your_port>
```

If this is not set correctly, you may encounter CORS-related issues.

## Configuration Files

- **`.env`** holds your settings and secrets. Both the `db` and the `web` service receive all of its variables, so any option from the [environment configuration](/run/environment-configuration) can be added there.
- **`docker-compose.yml`** only connects the services (internal URLs, volumes, ports). You normally don't need to change it.

:::caution
Keep `.env` private and back it up together with your data.
:::

## Networking

All services must be part of the same Docker network. This is handled by the default `wanderer` network in `docker-compose.yml`.

Make sure to set the `ORIGIN` environment variable to the full public URL (including port) where your instance is reachable. If misconfigured, the frontend will show this error:

> Cross-site POST form submissions are forbidden

## Volumes

By default, four volumes are mounted:

- Meilisearch index data: `./data/data.ms`
- PocketBase data: `./data/pb_data`
- Installed plugins: `./data/plugins`
- Uploads: `./data/uploads`

These can be changed to bind mounts or other volume strategies if needed.

## Environment

All settings are made in `.env`. For advanced options, refer to the [environment configuration documentation](/run/environment-configuration). Apply changes with `docker compose up -d`.

## Updating

To update your instance to the latest version:

```bash
docker compose pull
docker compose up -d
```

Always consult the [changelog](/changelog) before updating, in case of breaking changes.

## Upgrade to the photo library

The first start of a version with the asset photo library migrates existing trail, waypoint and summit-log photos before the backend starts listening. Plan a maintenance window and update `db` and `web` together. Size the startup allowance for your storage and photo library. The supplied `db.healthcheck.start_period` is `24h`; it applies after every container start and stops applying after the first successful health check in that run. A later container start that hangs before **Server started** can therefore wait through this period before failed checks count toward the ordinary unhealthy threshold. Update this value in existing Compose files before upgrading: pulling new images does not update them. Pause autoheal and other tools that restart unhealthy containers during the maintenance window.

Custom file-size and MIME-type restrictions on legacy `photos` fields are not carried over; reapply them to `assets.file` in PocketBase after the upgrade.

Before committing, the migration streams every original through SHA-256. Proven local hard links need only that one payload read. For local copy fallback and S3, the migration also streams the entire migrated copy, checking actual lengths and digests against the source. S3 uses server-side copies, but verification downloads both objects to the backend. On successful synchronous cleanup, each independent original and replacement is read twice in total, or three times each when cleanup processes cached thumbnails between the two deletion checks. These reads finish before **Server started** unless cleanup is deferred. Recovery and retries can add reads. Budget for these reads, local copy writes, S3 requests and transfer. The migration processes up to four records concurrently and keeps cleanup metadata for each migrated legacy key until synchronous cleanup finishes.

1. Stop the services and any other writers to the database or media storage. Pause bucket lifecycle rules and other automated jobs that can replace or remove photo objects during migration or cleanup. Back up the entire `pb_data` directory, including `data.db` and `storage/`, together with your configuration and encryption keys. With S3 storage, also back up the photo bucket: a PocketBase backup does not include S3 objects. Keep database and media backups from the same point in time. Restoring both is the supported rollback; `migrate down` cannot restore the old photo fields.
2. Before upgrading local storage, replace legacy photo files that are symbolic links with verified regular files inside `storage/` from a matching backup. The migration does not accept a symbolic link as verified media; if verification stops the upgrade, the source is not deleted. Local storage uses hard links within `storage/` when supported. Filesystem support and Linux ownership restrictions can prevent hard links; the migration then copies readable files and their content-type sidecars and needs space for a second copy. S3 temporarily needs space for both sets of objects. Original paths are removed only after the migration commits and cleanup verifies the current replacement; S3 reads and deletes are separate operations, not an atomic check-and-delete. Keep both sets intact until the migration removes the originals. Do not remove either set manually to get cleanup to finish.
3. Start the backend first and follow its logs:

   ```bash
   docker compose pull
   docker compose up -d db
   docker compose logs -f db
   ```

   Wait for **Server started**, then run `docker compose up -d` to start the remaining services. The photo-copy completion message can precede further cleanup. Comparison, rollback and deletion phases report progress as well. If an earlier start reported an unhealthy backend, let the migration finish before starting the remaining services again. Do not stop or restart the backend before **Server started**, even when an older healthcheck reports it as unhealthy.

    A run interrupted before its database commit starts again from the beginning. When the database is still on the old version and no committed-migration marker exists, files under `storage/assetcollect001/` (or the same S3 prefix) are disposable copies: a retry removes them without requiring the legacy originals to remain unchanged. Do not remove these files by hand; the next upgrade attempt handles them automatically. This also allows users to return temporarily to v0.21.2, delete photos there, and later retry the upgrade. After the database commit, the backend checkpoints the database, syncs copied local-file contents and all migrated local-media directories (children before parents), then writes `.photo-migration-committed` under the asset prefix before deleting any originals. If it stops between the commit and marker, startup cleanup completes these steps before deleting originals.

   With the committed-migration marker, a photo migration committed against this storage and may already have removed legacy originals. Recovery validates leftover asset media against the legacy sources. If recovery stops because existing asset media has no identical legacy source, the database is older than its media; no asset files were deleted. Start the database that completed the upgrade, or restore the database and media backup taken together. Do not delete the asset files or the marker to force an upgrade: they can be the only remaining copies of photos whose originals were already removed.

   Original files already missing at the copy step, invalid photo names and missing or unresolved owners are reported and skipped. For a present original, a missing, unreadable or mismatched copy stops the migration before commit and retains the original. The recorded content hash and cleanup digest come from the original, not from the storage provider's copy response or ETag. Waypoint photos use the trail author when that owner resolves, otherwise the waypoint author. Files skipped because of their name or author may remain in storage without a database reference. Review these warnings before accepting the upgrade. After the migration commits, the old `photos` fields are gone: retrying skipped photos requires restoring the full pre-upgrade database and media backup, correcting the missing files or authors, and running the migration again.

   At each backend start, retained legacy keys and the reason for retaining each one are listed once on stderr in `docker compose logs db`, with separate cleaned and retained totals. Later cleanup passes report only the totals, and only when they attempted or cleaned rows. Individual cleanup failures are logged when they occur. The private `_photo_migration_cleanup` table in `pb_data/data.db` records `attempts`, `last_error`, `next_attempt_at` (Unix milliseconds) and `needs_review`. If post-commit verification fails, cleanup retains the original, any thumbnails it has not already removed, and the queue entry. Background cleanup starts with the backend and retries eligible failures while it keeps running. The recorded delay starts at one hour and doubles up to 24 hours; shutdown stops the waiting loop. A claimed item interrupted by a crash becomes eligible after its recorded delay. Digest mismatches and missing or no longer referenced migrated copies are suspended for review, as are copies whose asset is no longer marked available. `legacy_media_changed` and `migrated_copy_changed` mean the named object did not match the recorded digest; neither proves which copy is correct, particularly for entries from an earlier build.

   Deliberately removing or replacing an asset can leave a legacy original taking up storage and a queue entry pending review: the absence of the referenced copy does not prove the original is redundant. If both files are already absent, the queue entry can still remain visible for review. Reconcile these entries against the matching backup and the intended asset state. Do not restore an intentionally removed asset just to complete cleanup, or remove retained media to silence a warning.

   Stop the backend and any other writers, take a matching database and media backup, and keep both sets of files intact while you inspect the table with SQLite tools. If the asset should still exist, repair access problems or recover and verify the current replacement before retrying a retained key. Do not assume the recorded digest alone identifies the correct copy. To make one repaired entry eligible at the next start, update only that entry. Copy its exact key from the retained-key log line: the key has the form `<collection id>/<record id>/<file>`, using PocketBase collection and record IDs rather than a collection name. Replace the placeholder below with that exact logged key:

   ```sql
   UPDATE _photo_migration_cleanup
   SET needs_review = 0, next_attempt_at = 0
   WHERE legacy_key = '<exact retained key from the log>';
   ```

   Keep `attempts` for the history of the entry. If the original is already absent, cleanup still requires a current replacement that matches the recorded digest before it removes remaining thumbnails or clears the entry. Never remove an original by hand to bypass this check.

4. Migrated photos initially have no capture time and may have only the trail's approximate coordinates. Summit-log photos receive these trail coordinates only when the entry author also owns the trail. Legacy WebP route previews and imported route-preview names receive a generated-preview marker. A summit-log PNG named `route_<suffix>.png` also receives it when the entry has a GPX and that PNG is its first photo. Other PNG and JPEG upload names remain ordinary photos. v0.21.2 cannot rename an existing photo. Before upgrading, upload such a real photo again under another file name (not `route.png`), or make sure it is not the entry's first photo, if you need to retain ordinary-photo classification. The photo and its bytes remain in the entry. Existing generated route-placeholder SVGs are also kept as generated assets; real photos take precedence as thumbnails and previews, and a trail with only its placeholder still shows it.
5. Old photo URLs are resolved to migrated assets using their current access rules. Making a trail private or revoking a share also revokes access through these URLs. Existing external caches cannot be revoked by the migration.
6. The migration sends no federation activities. Previously cached legacy photos on remote records are retained. Coordinate upgrades of federating instances when possible.

## Verify the Installation

Regardless of the installation method, once everything is running you should be able to access <span class="-tracking-[0.075em]">wanderer</span> at:

```
http://localhost:3000
```

If you see the UI and no errors in the logs, you're all set!
