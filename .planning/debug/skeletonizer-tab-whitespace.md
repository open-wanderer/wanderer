- timestamp: T5
  checked: Flutter SDK `/opt/flutter/packages/flutter/lib/src/rendering/stack.dart` (`RenderStack._computeSize`, lines 625-663) and `/opt/flutter/packages/flutter/lib/src/widgets/animated_switcher.dart` (`defaultLayoutBuilder`, lines 231-236); also `/opt/flutter/packages/flutter/lib/src/rendering/viewport.dart` `RenderViewport.computeDryLayout` (sliver-based Viewport sizes to `constraints.biggest` — does NOT shrink-wrap) vs. `SingleChildScrollView`'s internal `_RenderSingleChildViewport` (sizes to `constraints.constrain(childSize)` — DOES shrink-wrap under loose constraints). Also confirmed `enum StackFit` docs (`stack.dart:301-330`): `passthrough` = "constraints passed to the stack from its parent are passed unmodified to the non-positioned children" (vs. `loose` which deflates min to 0, and `expand` which tightens to `constraints.biggest` — dangerous if that biggest is unbounded/infinite).
  found: `RenderStack._computeSize` seeds `height = constraints.minHeight` (the STACK's own un-loosened incoming constraint) then does `max(height, childHeight)` — so under a TIGHT incoming constraint (min=max=H) the Stack's own size is always H regardless of child size, while children are separately handed LOOSENED constraints. This is the missing piece: it explains why the Stack itself still fills H (matching visual "correct" outer bounds) while its child can independently shrink and get centred within it. `StackFit.passthrough` hands the Stack's own constraints straight through with no loosening/tightening — a strictly safer fix vector than `StackFit.expand` (which would break call sites receiving genuinely unbounded constraints) and narrower than disabling `enableSwitchAnimation` (which would kill the cross-fade for all 8+ call sites).
  implication: `passthrough` is mathematically a subset of `loose`'s allowed constraint range (same max, min ≥ 0 instead of min = 0) — so for any call site that currently receives already-loose or unbounded constraints (i.e. AsyncLoader sits inside a scrollable/Column-without-Expanded), switching to `passthrough` is a no-op. It only changes behavior where the Stack's own incoming constraints were tight, forcing the child back to full height there. This makes `passthrough` structurally non-regressive across all 8+ call sites, not just empirically assumed safe.

## Resolution

root_cause: "`AsyncLoader`'s `Skeletonizer` hardcodes `enableSwitchAnimation: true`, which permanently wraps its child in an `AnimatedSwitcher` whose default `layoutBuilder` is `Stack(alignment: Alignment.center, fit: StackFit.loose)` (skeletonizer-2.1.3 + Flutter SDK `AnimatedSwitcher.defaultLayoutBuilder`). This Stack sits between the tight constraints handed down from `trail_detail_screen.dart`'s `Positioned.fill > Padding` and `TrailPanel`'s `SingleChildScrollView`. `StackFit.loose` loosens those tight constraints before handing them to the non-positioned child; `SingleChildScrollView` (via its non-sliver `_RenderSingleChildViewport`) responds to loose constraints by shrink-wrapping to its actual content height instead of filling. The outer Stack, however, still reports its own size as the full available height (`RenderStack._computeSize` seeds from its OWN un-loosened incoming constraint). `Alignment.center` then centers the shrink-wrapped scroll view inside that full-height Stack, producing an empty band above and below whenever tab content is shorter than the panel's available height (Summit Book, Comments) — while the About tab, being the tallest, nearly fills the space and shows no visible gap. Confirmed via Flutter/skeletonizer source (T1, T5) and a widget-test reproduction whose measured numbers match the predicted centering formula exactly (T6)."
fix: "In `app/lib/components/async_loader.dart`, pass a custom `switchAnimationConfig: SwitchAnimationConfig(layoutBuilder: ...)` to `Skeletonizer` that rebuilds the same overlay `Stack` used by `AnimatedSwitcher.defaultLayoutBuilder` but with `fit: StackFit.passthrough` instead of the package default `StackFit.loose`. `passthrough` hands the Stack's own incoming constraints through unmodified — tight constraints stay tight (forcing full-height fill, matching pre-Skeletonizer-wrapping behavior and eliminating the shrink-wrap/centering artifact), while call sites that already receive loose/unbounded constraints (AsyncLoader instances inside scrollables) are provably unaffected, since passthrough's allowed range is always a subset of loose's. Keeps `enableSwitchAnimation: true` and the cross-fade transition intact; only the layout mechanics of the transition's Stack change."
verification: "Widget-test reproduction against the fixed `AsyncLoader` (`switchAnimationConfig` with `StackFit.passthrough` layoutBuilder): short (50px) content under `Positioned.fill > Padding(bottom:72)` in a 600-tall Scaffold body now measures size=(800,528) at globalTopLeft=(0,0) -- fills the full 528px available height flush at the top, vs. the pre-fix (800,50) shrink-wrapped and centred at y=239. Second widget test confirms no regression for AsyncLoader already nested inside a scrollable/unbounded-height parent (mirrors profile_screen.dart / list_screen.dart usage): no exception thrown, content sizes naturally to its own 80px height as before. `flutter analyze lib/components/async_loader.dart` -> No issues found. Full `flutter analyze` -> only 5 pre-existing unrelated warnings/infos (confirmed present before this change too). Existing permanent test suite for AsyncLoader call sites (`trail_detail_screen_retired_redirect_test.dart`, `profile_trail_map_navigation_test.dart`, `settings_offline_regions_screen_test.dart`, `trail_panel_sync_badge_test.dart`) and the full `test/components` suite (65 tests) all pass. Reproduction test file was temporary and has been deleted; not part of the permanent suite.
