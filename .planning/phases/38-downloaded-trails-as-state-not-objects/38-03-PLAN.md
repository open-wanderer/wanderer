<objective>
Build the one mechanism behind D-13 and D-14 — writing a known-good server model into the stored
library row — and the network-only fetch seam plan 38-06 needs for D-15.

Purpose: today a downloaded trail's stored row never receives anything after the download.
`applyNetworkEditToLocalRow` exists but keys on `localId & owner` (the unsynced-capture key), and a
downloaded row has `localId == null`, so the hiker's own edit never lands (bug 2, D-13). Separately,
`TrailNotifier.build()` already fetches the trail record **and** unconditionally fetches the GPX file
on every online open (D-23) — so both the metadata and the track are already paid for by the time a
downloaded trail renders, which is what makes the D-14 refresh literally free. D-19 is a hard user
constraint: a downloaded trail must never be stale while online.

D-11 must survive into the code: automatic refresh (this plan) and the explicit *Update* action
(plan 38-05) are complementary, not redundant. This plan spends **zero** bytes and deliberately
never touches photos (D-14a) — photos are the only expensive asset in the download path (D-23), and
refreshing them stays an active decision.

Output: one new store function with two call sites, plus `fetchServerTrail` extracted out of
`TrailNotifier.build`.
</objective>

  <action>
Add one new top-level function to `app/lib/store/local_trail_store.dart`, placed immediately after
`applyNetworkEditToLocalRow` so the two sit together:

`void applyServerTrailToLibraryRow(Store store, {required String accountId, required Trail trail})`

It is a SECOND function, not a loosened gate on `applyNetworkEditToLocalRow`. That function keys on
`TrailEntity_.localId.equals(localId) & TrailEntity_.owner.equals(accountId)`; a downloaded row has
`localId == null`, so it can never match. This one keys on library membership:
`TrailEntity_.id.equals(trail.id) & TrailEntity_.savedByUserIds.containsElement(accountId)` — the
exact predicate `TrailNotifier._readCached` already builds.

Behaviour:
- Return immediately when `trail.id` is empty (D-06 blanks a local-sentinel id, and an empty id must
  never match a row).
- Open a single `store.runInTransaction(TxMode.write, ...)`. Build the query, `findFirst()`, close
  the query immediately after the read, and return silently when no row matches — no row simply
  means this account has not downloaded this trail. A silent no-op, never an error, mirroring
  `applyNetworkEditToLocalRow`.
- Build the refreshed row with `TrailEntity.fromModel(trail)` (the `updateLocalTrail` precedent),
  then carry forward from the existing row, explicitly, every column `fromModel` cannot know or
  would wrongly reset: `obxId`, `id`, `owner`, `localId`, `syncState`, `syncAttempts`,
  `syncNextAttemptAt`, `savedByUserIds`, `photos`, `localPhotos`, `navCacheJson`. `savedByUserIds`,
  `photos` and `localPhotos` are the load-bearing three — dropping `savedByUserIds` would erase
  every account's claim on the trail, and `photos` on a downloaded row holds LOCAL FILE PATHS
  written by `TrailDownloadService`, not server filenames, so overwriting it would strand the
  downloaded images (D-14a: nothing automatic ever spends bytes, and nothing automatic ever
  destroys already-spent ones).
- Guard `gpxData`: when the incoming `trail.expand?.gpxData` is null or empty, keep the existing
  row's `gpxData` rather than blanking the stored track. When it is present, take it — this is
  D-14's track refresh, a single ObjectBox string write with no file I/O (D-23).
- Guard the author and category relations plus `authorRecordId`: when the incoming model carries no
  expanded author/category, `fromModel` leaves those unset, so fall back to the existing row's
  values instead of dropping them.
- Waypoints: only touch them when `trail.expand?.waypointsViaTrail` is non-null. When it is,
  carry each existing child's `localPhotos` onto the matching refreshed child (match on
  `WaypointEntity.id`) so downloaded waypoint photos survive, then remove the `WaypointEntity` rows
  whose ids are absent from the refreshed set, following `updateLocalTrail`'s orphan-pruning loop.
  When it is null, carry the existing children forward untouched.
- `trailBox.put(entity)` last, inside the same transaction.

Write a doc comment above it that states, in the same enumerating style as
`applyNetworkEditToLocalRow`'s: which trigger calls it (D-13 the hiker's own edit, D-14 any
successful fetch of a downloaded trail), that it costs zero additional network traffic because both
the record and the GPX are already in hand (D-23), that photos are deliberately excluded (D-14a),
and that `accountId` must be read fresh via `currentAccountId(store)` at every call site (never a
cached value) or account B's fetch could write onto account A's row.

Do not modify `applyNetworkEditToLocalRow`, `updateLocalTrail`, or any other existing function in
this file.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server response → ObjectBox write | An attacker-influenced or federated trail record is written into the local store |
| signed-in account → shared trail rows | One `TrailEntity` row is shared by every account that downloaded the trail |
| automatic action → the hiker's already-downloaded data | A background refresh can destroy bytes the hiker deliberately spent |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-38-03-01 | Information disclosure | `applyServerTrailToLibraryRow` query | mitigate | Query is `TrailEntity_.id.equals(trail.id) & TrailEntity_.savedByUserIds.containsElement(accountId)` with `accountId` read fresh via `currentAccountId(store)` at both call sites, so one account can never write into (or learn of) another's downloaded private trail |
| T-38-03-02 | Tampering / data loss | carry-forward columns in `applyServerTrailToLibraryRow` | mitigate | `obxId`, `id`, `owner`, `localId`, `syncState`, `syncAttempts`, `syncNextAttemptAt`, `savedByUserIds`, `photos`, `localPhotos`, `navCacheJson` are explicitly carried from the found row; a blind `fromModel` put would erase library membership and the local photo paths |
| T-38-03-03 | Denial of service | `_refreshLibraryRow` inside `build`'s try | mitigate | Its own `try`/`catch` + `debugPrint` prevents a store failure from being caught by `build`'s `catch (_)` and silently downgrading a good server response to a stale cached one |
| T-38-03-04 | Tampering | `gpxData` overwrite | mitigate | Guarded: a response with no GPX leaves the stored track untouched rather than blanking it, so a partial/failed server response cannot erase a downloaded route |
| T-38-03-05 | Tampering | waypoint child rows | mitigate | Each existing child's `localPhotos` is carried onto its refreshed counterpart by id, and orphan pruning follows `updateLocalTrail`'s established loop |
| T-38-03-SC | Tampering | package installs | accept | No package-manager install occurs in this plan; `pubspec.yaml` is untouched |
</threat_model>
