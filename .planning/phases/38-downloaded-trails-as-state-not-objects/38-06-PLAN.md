<objective>
Close bug 1 at its root (D-15, D-18) and put automated coverage under the whole new menu.

Purpose: `TrailDownloadService` overwrites `entity.photos` with LOCAL FILE PATHS
(`trail_download_service.dart:148`), and `toModel()` surfaces those as `localPhotos` while leaving
the model's `photos` at its `[]` default. The edit form therefore seeds
`initialValue: trail.localPhotos` (real files, so they render normally and look correct) and
`initialWebPhotos: trail.photos` — empty. On save those local paths survive the `existsSync()` filter
and are sent under the append-only `photos+` key (`form_data.dart:47-51`), so **the server photo set
doubles on every Library edit**, and `_removedServerPhotos` — computed from the same empty
`trail.photos` — makes removing a photo a silent no-op. This is live data damage on `feature/app`
today and nothing cleans it up.

D-15 fixes it structurally rather than by hiding the path to it: Edit stays enabled and fetches the
server copy on tap; the editor opens only on success. The editor can then never receive a cached
model, so `trail.photos` always holds real server filenames. D-16 records why the alternatives were
rejected: disable-and-grey is silent (exactly what this file's own D-17 comment calls "reads like a
broken app"), and hiding Edit on your own trail reads as a permissions problem.

Output: the edit path can no longer be handed a cached model, plus widget tests covering both menu
branches, both destructive axes, and the refusal.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| edit form → `POST /trail/form/{id}` | The form's photo fields decide what is appended to and removed from the server's photo set |
| cached model → edit form | A model read from ObjectBox carries local file paths in fields the form treats as server filenames |
| network failure → user-visible outcome | A silent refusal is indistinguishable from a broken app |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-38-06-01 | Tampering (server-side data damage) | Edit `onTap` → `trail_create_screen` photo seeding | mitigate | The editor is handed the model returned by `fetchServerTrail`, whose `photos` are real server filenames, so local paths are never resent under the append-only `photos+` key and `_removedServerPhotos` is computed from a non-empty list |
| T-38-06-02 | Information disclosure | `fetchServerTrail` on the edit path | mitigate | Network-only by construction (plan 38-03 forbids any ObjectBox read in it), so the edit path cannot silently fall back to another account's or a stale cached copy |
| T-38-06-03 | Repudiation | failed edit fetch | mitigate | Refusal is surfaced as a `ToastType.warning` with `edit_needs_connection` and logged with `debugPrint`; D-16 rejects the silent disable-and-grey alternative explicitly |
| T-38-06-04 | Elevation of privilege | destructive availability under a timed-out fetch | mitigate | Device check step 8 exercises the original defect path (fetch times out, cached copy renders) and asserts no server delete is offered for a trail the hiker did not author |
| T-38-06-SC | Tampering | package installs | accept | No package-manager install occurs in this plan; `pubspec.yaml` is untouched |
</threat_model>
