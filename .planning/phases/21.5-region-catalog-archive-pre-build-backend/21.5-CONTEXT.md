# Phase 21.5: Region Catalog & Archive Pre-Build (Backend) - Context

**Gathered:** 2026-07-21
**Status:** Ready for planning

<domain>
## Phase Boundary

The Go backend reads an admin-supplied, Docker-volume-mounted config file defining this instance's regions (id, name, bbox). A daily cronjob pre-builds one mosaicked vector PMTiles archive and one DEM archive per configured region — ahead of any user request. An API endpoint serves the resulting catalog (id, name, bbox, archive URLs + sizes, status) so a region download is always a single, already-ready file. No admin-facing CRUD UI/API — config changes are file-edit + restart. Fulfills BACK-01 through BACK-05.

</domain>

<decisions>
## Implementation Decisions

### Archive Build Mechanism
- **D-01:** Vector archives are built via direct `pmtiles extract --bbox=<region bbox> --maxzoom=14` against the Protomaps source, one archive per region — no per-cell extraction, no merge/join logic. `generator.go`'s existing per-cell cache and cell-merge path are untouched; this is a parallel, independent build path.
- **D-02:** DEM archives use the same direct-extract approach: `pmtiles extract --bbox=<region bbox> --maxzoom=12` against `mapterhornSource`, mirroring the vector build for symmetry.
- **D-03:** Pre-built region archives are written to a new directory, separate from the existing per-cell `pb_data/pmtiles_cache/` — e.g. `pb_data/region_archives/{region_id}/vector.pmtiles` and `dem.pmtiles`.

### Config File Shape & Location
- **D-04:** Config file format is JSON, matching the existing `pluginsystem/manifest.go` precedent (`plugin.json` + `json.Unmarshal`) — no new parsing dependency.
- **D-05:** File path comes from an env var (e.g. `REGION_CATALOG_CONFIG_PATH`), following the existing `os.Getenv(...)` convention (`main.go`). Read once at startup — no live hot-reload. An admin edits the mounted file then restarts/redeploys to pick up changes, matching the milestone's stated non-goal of live admin CRUD. No config file or an empty one → empty catalog, not an error (per Success Criterion 1).

### Catalog API Endpoint Shape
- **D-06:** Route is `GET /api/v1/regions`, following the existing versioned `/api/v1/...` convention.
- **D-07:** Endpoint requires authentication — any logged-in user (not admin-only, not public/unauthenticated). This diverges from the existing per-cell endpoints (`map_cells_id.go`), which are unauthenticated — flag this divergence explicitly for the planner/researcher.
- **D-08:** Each region entry exposes `status`: `ready` / `building` / `error`.
  - `ready` — archive built and servable; full URL/size fields present.
  - `building` — first-ever build in progress; URL/size fields omitted. A region that already has a `ready` archive stays `ready` during background rebuilds (never regresses to `building`) so the client always has something downloadable.
  - `error` — last build attempt failed; URL/size omitted, region still included in the response (id/name/bbox present) with an error indicator, so the app can show "unavailable" rather than the region silently vanishing from the list.

### Cron Cadence & Staleness Detection
- **D-09:** Cronjob runs daily, matching the cadence of the Protomaps vector source's own daily-dated builds (`getValidProtomapsURL`). Configurable via its own env var (e.g. `REGION_ARCHIVE_CRON_SCHEDULE`, default `"0 3 * * *"`), following the existing `POCKETBASE_CRON_SYNC_SCHEDULE` pattern in `main.go`.
- **D-10:** Staleness for vector archives: store the Protomaps `YYYYMMDD` date string used for a region's last successful build. On each cron tick, resolve today's valid Protomaps date and compare — if different, rebuild the vector archive and mark `updateAvailable`. Cheap string comparison; no hashing, no speculative re-download.
- **D-11:** DEM archives never auto-rebuild after their first successful build — Mapterhorn's DEM source has no date-stamped URL to compare against, and its data is treated as effectively static. A DEM archive is only regenerated if the region's config entry itself changes (e.g. a bbox edit is detected).

### Claude's Discretion
None — all four discussed areas reached explicit decisions; no "you decide" selections were taken.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `pmtiles extract` CLI invocation pattern from `generator.go` (bbox + maxzoom flags, `extractTimeout` handling) — reusable directly for region-scale extraction, just with the region's full bbox instead of a 0.5° grid cell.
- PocketBase's `app.Cron()` — already wired up in `main.go`; adding a second named cron job (`app.Cron().MustAdd("region-archive-build", schedule, ...)`) requires no new infrastructure.

### Established Patterns
- Env-var-driven configuration for schedules and paths (`os.Getenv`) is the dominant convention — no existing YAML/JSON-mounted-config convention for *settings* exists, only `pluginsystem`'s JSON-manifest-per-directory pattern for structured data, which this phase's config loader should mirror.
- Local-disk file serving via `e.FileFS(os.DirFS(...), ...)` is how all tile data is currently served — no object storage/CDN layer exists. The new region archives should be served the same way.

### Integration Points
- No existing staleness/version/hash tracking on any tile-cell record (`tile_cells` collection only has `status`/`size_bytes`/`download_count`) — the region catalog will need its own new PocketBase collection (or similar persistence) to track per-region `status`, last-built Protomaps date, archive paths, and sizes. This is new schema, not an extension of `tile_cells`.

</code_context>
