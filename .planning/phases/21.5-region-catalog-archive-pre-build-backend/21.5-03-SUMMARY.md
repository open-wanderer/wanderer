# Phase 21.5 Plan 03: Region Catalog Endpoint, Cron Wiring & SvelteKit Proxy Summary

**`GET /api/v1/regions` (auth-gated, reachable at the app's public origin via a SvelteKit proxy) returns the merged config-plus-build-state region catalog; archive downloads are auth-gated and id-validated; the daily `region-archive-build` cron now runs `regions.BuildAll`; docker-compose wires the admin config path in all three deployment files.**

## Accomplishments

- `db/routes/regions_get.go`: `RegionsList` builds a single-shot catalog array from the admin config (source of truth for which regions exist) joined to `region_archives` build state, baking D-08's `ready`/`building`/`error` status semantics into each entry — a region removed from config disappears even if a stale record lingers
- `RegionArchiveDownload`/`RegionArchiveDownloadDem` re-validate the untrusted `{id}` URL param against the allow-list regex before any filesystem path is built, then serve via `e.FileFS` confined to `RegionCacheDir` (T-21.5-01 mitigation)
- `db/main.go`: new `/api/v1/regions` route group with `apis.RequireAuth()` **enabled** (D-07 — diverges from the dormant `/map/cells` auth), and a new `region-archive-build` cron (default `0 3 * * *`, overridable via `REGION_ARCHIVE_CRON_SCHEDULE`) invoking `regions.BuildAll` (D-09)
- All three compose files (`docker-compose.yml`, `docker/docker-compose.prod.yml`, `docker/docker-compose.dev.yml`) now set `REGION_CATALOG_CONFIG_PATH` unconditionally on the `db` service and document a commented bind-mount example, closing RESEARCH.md's Pitfall 6
- `web/src/routes/api/v1/regions/**`: a thin SvelteKit proxy (GET catalog via `event.locals.pb.send`; both download routes via `event.fetch` + forwarded `Authorization` header) makes the same public path `/api/v1/regions` the one external clients (browser, and Phase 22's Flutter app) actually call, since the Go backend's port is not published in the real deployment compose files

## Decisions Made

- Confirmed, before implementing, that neither `docker/docker-compose.prod.yml` nor `docker/docker-compose.dev.yml` publish the `db` service's port — only the root `docker-compose.yml` does, for local convenience. This validated the plan's `<assumptions>` routing resolution (Go route stays internal-only at the literal `/api/v1/regions` path; SvelteKit proxies the same public path) before writing any code, per the important-context instruction in this plan's execution prompt.
- For the two download proxy routes, followed the existing `web/src/routes/api/v1/map/cells/[cellKey]/download(-dem)/+server.ts` precedent verbatim (`event.locals.pb.baseURL` + `Bearer ${token}` Authorization header, Content-Length/Content-Disposition passthrough) rather than the plan's suggested `$env/dynamic/public` + `PUBLIC_POCKETBASE_URL` construction — both resolve to the same internal origin, but the `pb.baseURL` approach is the codebase's own established convention for this exact class of route (CLAUDE.md: follow existing patterns).
- Used the existing `handleError(e)` helper (`$lib/util/api_util.ts`) for the catalog proxy's error path instead of hand-rolling a `ClientResponseError` branch — `handleError` already propagates `e.status`/`e.response` unchanged for `ClientResponseError`, satisfying the plan's requirement with less duplicated logic.
