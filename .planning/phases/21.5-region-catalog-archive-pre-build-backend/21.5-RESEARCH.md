## User Constraints (from CONTEXT.md)

### Locked Decisions

**Archive Build Mechanism**
- **D-01:** Vector archives are built via direct `pmtiles extract --bbox=<region bbox> --maxzoom=14` against the Protomaps source, one archive per region — no per-cell extraction, no merge/join logic. `generator.go`'s existing per-cell cache and cell-merge path are untouched; this is a parallel, independent build path.
- **D-02:** DEM archives use the same direct-extract approach: `pmtiles extract --bbox=<region bbox> --maxzoom=12` against `mapterhornSource`, mirroring the vector build for symmetry.
- **D-03:** Pre-built region archives are written to a new directory, separate from the existing per-cell `pb_data/pmtiles_cache/` — e.g. `pb_data/region_archives/{region_id}/vector.pmtiles` and `dem.pmtiles`.

**Config File Shape & Location**
- **D-04:** Config file format is JSON, matching the existing `pluginsystem/manifest.go` precedent (`plugin.json` + `json.Unmarshal`) — no new parsing dependency.
- **D-05:** File path comes from an env var (e.g. `REGION_CATALOG_CONFIG_PATH`), following the existing `os.Getenv(...)` convention (`main.go`). Read once at startup — no live hot-reload. An admin edits the mounted file then restarts/redeploys to pick up changes, matching the milestone's stated non-goal of live admin CRUD. No config file or an empty one → empty catalog, not an error (per Success Criterion 1).

**Catalog API Endpoint Shape**
- **D-06:** Route is `GET /api/v1/regions`, following the existing versioned `/api/v1/...` convention.
- **D-07:** Endpoint requires authentication — any logged-in user (not admin-only, not public/unauthenticated). This diverges from the existing per-cell endpoints (`map_cells_id.go`), which are unauthenticated — flag this divergence explicitly for the planner/researcher.
- **D-08:** Each region entry exposes `status`: `ready` / `building` / `error`.
  - `ready` — archive built and servable; full URL/size fields present.
  - `building` — first-ever build in progress; URL/size fields omitted. A region that already has a `ready` archive stays `ready` during background rebuilds (never regresses to `building`) so the client always has something downloadable.
  - `error` — last build attempt failed; URL/size omitted, region still included in the response (id/name/bbox present) with an error indicator, so the app can show "unavailable" rather than the region silently vanishing from the list.

**Cron Cadence & Staleness Detection**
- **D-09:** Cronjob runs daily, matching the cadence of the Protomaps vector source's own daily-dated builds (`getValidProtomapsURL`). Configurable via its own env var (e.g. `REGION_ARCHIVE_CRON_SCHEDULE`, default `"0 3 * * *"`), following the existing `POCKETBASE_CRON_SYNC_SCHEDULE` pattern in `main.go`.
- **D-10:** Staleness for vector archives: store the Protomaps `YYYYMMDD` date string used for a region's last successful build. On each cron tick, resolve today's valid Protomaps date and compare — if different, rebuild the vector archive and mark `updateAvailable`. Cheap string comparison; no hashing, no speculative re-download.
- **D-11:** DEM archives never auto-rebuild after their first successful build — Mapterhorn's DEM source has no date-stamped URL to compare against, and its data is treated as effectively static. A DEM archive is only regenerated if the region's config entry itself changes (e.g. a bbox edit is detected).

## Summary

This phase adds a new, parallel build path to the existing Go/PocketBase backend (`db/`) — it does not modify `db/services/tiles/generator.go`'s per-cell cache logic, it sits alongside it. Every mechanism CONTEXT.md locks in (`pmtiles extract` CLI invocation, JSON config file loading, PocketBase's built-in `app.Cron()`, `e.JSON`/`e.FileFS` response helpers) already has a working, verified precedent elsewhere in this exact codebase — this is a "assemble known parts in a new shape" phase, not a "learn a new library" phase. The `pmtiles` CLI (go-pmtiles v1.28.0) is already vendored into the `db` Docker image at `/usr/local/bin/pmtiles`, and PocketBase is pinned at `v0.38.0` (both confirmed against the actual `Dockerfile` and `go.mod`, and cross-checked against the locally cached `pocketbase@v0.38.0` module source for every API call cited below).

Three things need the planner's explicit attention because they are not simply "copy generator.go's pattern": (1) the region-archive build must **never overwrite a currently-served `ready` file in place** — D-08 requires a `ready` region to keep serving through a background rebuild, which `generator.go`'s cell-rebuild path does not need to guarantee and does not currently do (it removes/overwrites the target path directly); the new build path needs a temp-file-then-atomic-rename pattern. (2) D-06's locked route path (`GET /api/v1/regions`) cites a "convention" that actually lives in the **SvelteKit web layer** (`web/src/routes/api/v1/...`), not in the Go backend, whose custom routes (`db/main.go`'s `registerRoutes`) are all registered **unprefixed** (`/map/cells`, `/activitypub/actor`, etc.) — this is a real inconsistency in the locked decisions that the planner must resolve explicitly (see Common Pitfalls §3). (3) `getValidProtomapsURL()` doesn't expose the bare `YYYYMMDD` string D-10 needs to persist and compare — a small signature change or companion helper is required.

**Primary recommendation:** Create a new `db/services/regions` package (mirroring the existing `db/services/tiles` and `db/services/trailmerge` per-domain package convention) holding: a config loader (mirrors `pluginsystem.LoadLocalPlugin`), a build function (mirrors `generator.generateCell`/`generateDemCell` but with atomic-rename output and a longer, region-scale timeout), and a new PocketBase collection (mirrors `tile_cells`'s migration shape) for per-region build/status tracking. Wire the cron job into `main.go`'s `registerCronJobs` and the API route into `registerRoutes`, resolving the `/api/v1` prefix question first.

### Pattern 1: Config file loading (mirrors `pluginsystem.LoadLocalPlugin`)
**What:** Read a JSON file from a path resolved via `os.Getenv`, tolerate "file doesn't exist" as a valid empty state, `json.Unmarshal` into a typed slice.
**When to use:** BACK-01's config loader.
**Example (source: `db/pluginsystem/manifest.go` lines 109–119, read directly from this repo):**
```go
// Existing precedent to mirror — LoadLocalPlugin, db/pluginsystem/manifest.go:109-119
func LoadLocalPlugin(dir string) (*LocalPlugin, error) {
	manifestPath := filepath.Join(dir, "plugin.json")
	data, err := os.ReadFile(manifestPath)
	if err != nil {
		return nil, err
	}

	var manifest Manifest
	if err := json.Unmarshal(data, &manifest); err != nil {
		return nil, fmt.Errorf("parse plugin.json: %w", err)
	}
	// ...
}
```
For the region catalog, the "file doesn't exist" case must NOT propagate as an error (unlike `LoadLocalPlugin`, which does return the `os.ReadFile` error) — BACK-01/D-05 explicitly requires "no config file or an empty one → empty catalog, not an error." Recommended shape:
```go
func LoadRegionCatalog() ([]Region, error) {
	path := os.Getenv("REGION_CATALOG_CONFIG_PATH")
	if path == "" {
		return []Region{}, nil // no path configured → empty catalog, no error
	}
	data, err := os.ReadFile(path)
	if err != nil {
		if os.IsNotExist(err) {
			return []Region{}, nil // missing file → empty catalog, no error
		}
		return nil, err // file exists but unreadable (permissions, etc.) → real error
	}
	if len(data) == 0 {
		return []Region{}, nil // empty file → empty catalog, no error
	}
	var regions []Region
	if err := json.Unmarshal(data, &regions); err != nil {
		return nil, fmt.Errorf("parse region catalog config: %w", err)
	}
	return regions, nil
}
```

### Anti-Patterns to Avoid
- **Overwriting a `ready` archive's file path in place during a background rebuild:** violates D-08 ("a region that already has a ready archive stays ready during background rebuilds"). Build to a temp path, `os.Rename` on success (atomic on the same filesystem/volume). See Common Pitfalls §1.
- **Re-checking `os.Stat` + `status=="ready"` without first locking against concurrent cron ticks:** `generator.go`'s `EnsureCell` uses an `inFlightMu`/`sync.WaitGroup` map keyed by cell to dedupe concurrent builds of the *same* cell (lines 41–74). The region builder needs an equivalent per-region in-flight guard if the cron job could ever overlap with itself (e.g., a manual trigger or an unexpectedly slow prior run still executing when the next scheduled tick fires) — reuse this exact `sync.Mutex` + `map[string]*sync.WaitGroup` pattern, keyed by region id.
- **Reusing `extractTimeout` (5 min) verbatim for region-scale extracts:** tuned for 0.5°×0.5° grid cells; will likely be too short for a metro/state-sized bbox. See Common Pitfalls §2.

## Common Pitfalls

### Pitfall 1: In-place file overwrite breaks D-08's "ready stays ready during rebuild" guarantee
**What goes wrong:** `generator.go`'s `generateCell` writes directly to `outputPath` and does `os.Remove(outputPath)` on extract failure (line 184). If the region-archive builder copies this verbatim, a background rebuild of an already-`ready` region would either serve a partially-written file mid-extract, or briefly 404 if the old file is removed before the new one is confirmed written.
**Why it happens:** The per-cell code has no "must stay available during rebuild" requirement (a cell is only rebuilt if `os.Stat` shows it missing — see `EnsureCell` lines 80–87); the region-archive code has an explicit new requirement (D-08) that generator.go's design was never built to satisfy.
**How to avoid:** Extract to a temp path within the same directory/filesystem (e.g. `vector.pmtiles.building`), verify via `os.Stat` after the subprocess exits successfully, then `os.Rename(tmpPath, finalPath)` (atomic on POSIX same-filesystem renames). Only update the collection record's `status` to `ready` and the size fields after the rename succeeds. The previous `ready` file remains fully servable via `e.FileFS` for the entire build window.
**Warning signs:** intermittent 404s or truncated-file errors on `/regions`'s archive download URL during the daily cron window.

### Pitfall 2: `extractTimeout` (5 min) is tuned for 0.5° grid cells, not region-scale bboxes
**What goes wrong:** `generator.go`'s `extractTimeout = 5 * time.Minute` (line 38) bounds a single `pmtiles extract` subprocess for a ~55km×55km grid cell. A region bbox (e.g. covering an entire metro area or state) will contain a much larger tile volume; reusing the same timeout constant risks the cron job's `context.WithTimeout` (lines 171/220 pattern) killing the subprocess mid-extract on every run for larger regions.
**Why it happens:** Copy-pasting `generator.go`'s extract invocation without re-deriving the timeout for the new scale.
**How to avoid:** Introduce a distinct, longer timeout constant for region-scale builds (e.g. `regionExtractTimeout = 30 * time.Minute`, or make it configurable via its own env var) rather than reusing `extractTimeout` verbatim.
**Warning signs:** Region archives repeatedly stuck in `error` status for larger regions specifically, with a context-deadline-exceeded error message; smaller regions succeed fine.

### Pitfall 3: D-06's literal route path conflicts with this phase's own "no SvelteKit changes" boundary — planner must resolve explicitly
**What goes wrong:** D-06 locks `GET /api/v1/regions` and cites it as following "the existing versioned `/api/v1/...` convention," with `map_cells_id.go` named as the structural pattern to mirror. But `/api/v1/...` is **not** a Go-backend routing convention in this codebase — it's the SvelteKit web layer's own route namespace (`web/src/routes/api/v1/...`, confirmed by `hooks.server.ts:196`'s `csrf(['/api/v1'])` and by every `+server.ts` file under that path). `map_cells_id.go` itself — the cited structural pattern — is registered in `db/main.go` as `/map/cells/{cellKey}` (no `/api/v1` prefix at all); its public `/api/v1/map/cells/{cellKey}` shape only exists because a matching SvelteKit proxy file (`web/src/routes/api/v1/map/cells/[cellKey]/+server.ts`) calls `event.locals.pb.send('/map/cells/${cellKey}', ...)` server-side. Every other custom Go route in `main.go`'s `registerRoutes` (lines 177–222) is likewise unprefixed. This phase's own scope explicitly excludes SvelteKit changes.
**Why it happens:** CONTEXT.md's decision conflates the *public-facing URL convention* (owned by SvelteKit) with the *structural code pattern* of a specific Go file (owned by the Go backend) — they are different layers that happen to share visual similarity in the final public URL.
**How to avoid — two options for the planner to choose between, both technically valid (confirmed: PocketBase's `RouterGroup.GET(path string, ...)` treats `path` as a plain `net/http.ServeMux`-style string, so registering the literal path `/api/v1/regions` directly in the Go router works with no special handling):**
1. **Register the Go route at the literal path `/api/v1/regions`** in `main.go`'s `registerRoutes` (deviates from every other custom Go route's unprefixed convention, but satisfies D-06's exact path with zero SvelteKit involvement — consistent with this phase's stated boundary). *Recommended*, since it makes Success Criterion 4 ("GET ... returns this instance's region catalog") satisfiable entirely within this phase's own scope.
2. **Register unprefixed** (e.g. `/regions`, matching the Go-layer convention) and explicitly note that a SvelteKit proxy (mirroring `map/cells/[cellKey]/+server.ts`) is a **follow-up task for Phase 22** (which the CONTEXT.md canonical_refs already flags as needing replanning once this phase's API contract is locked) — meaning this phase's endpoint is only reachable by calling the `db` container directly (port 8090), not through the documented public API surface, until that follow-up lands.
**Recommendation:** Option 1. Flag this explicitly in the plan so the chosen path is a recorded decision, not an implicit accident — Phase 22 (per the pending replan todo) needs to know the *exact* final path either way.
**Warning signs:** none at build time (both compile and run fine) — the risk is entirely "the Flutter client in Phase 22 calls a URL that doesn't exist yet," a scope/integration gap, not a code bug.

### Pitfall 4: `getValidProtomapsURL()` doesn't expose the raw date string D-10 needs
**What goes wrong:** D-10's staleness check needs to persist and compare the bare `YYYYMMDD` Protomaps date string, but `getValidProtomapsURL()` (`generator.go` lines 126–136) only returns a fully-formed URL (`https://build.protomaps.com/20260721.pmtiles`), with the date embedded but not separately returned. Also note: the fallback to yesterday's URL (line 134–135) is unconditional — it does NOT call `urlExists` on the yesterday URL before returning it, unlike the today-URL check (line 130). So `getValidProtomapsURL()` can return a URL that 404s if both today's and yesterday's Protomaps builds are somehow unavailable.
**Why it happens:** The function was designed only to hand a downloadable URL to `pmtiles extract`; it was never meant to expose the date as a standalone comparable value.
**How to avoid:** Add a companion function (or change the return signature) that returns `(date string, url string)` so the region builder can persist `date` for D-10's comparison without re-deriving it via string parsing on the URL. Do not silently assume the returned URL is always valid — extraction failure against a stale/missing daily build should be handled the same way `generateCell` already handles any extract failure (mark `error`, log, don't crash the cron job).
**Warning signs:** N/A at implementation time — this is a design gap to close, not a bug to detect later.

### Pitfall 5: Concurrent cron overlap without an in-flight guard
**What goes wrong:** If a region's build takes longer than expected (see Pitfall 2) and overlaps with the next scheduled cron tick (or a manual re-trigger), two goroutines could race to write the same region's archive files.
**Why it happens:** `generator.go`'s per-cell `EnsureCell` already solves this exact class of problem with an `inFlightMu sync.Mutex` + `map[string]*sync.WaitGroup` keyed by cell (lines 41–74) — but that guard is scoped to per-cell keys, not region ids, so it does not automatically protect the new region-archive path.
**How to avoid:** Add an equivalent in-flight map keyed by region id in the new `db/services/regions` package (or reuse a generalized version if refactoring `tiles` isn't in scope — a small, independent copy is safer given D-01/D-02's "parallel, independent build path" framing).
**Warning signs:** Corrupted/truncated `.pmtiles` files, or two competing `os.Rename` calls resulting in a torn write.

### Pitfall 6: Config-file Docker volume mount is a real infra task, easy to forget
**What goes wrong:** D-05 requires the config file be "mounted via Docker volume," but `docker-compose.yml`'s `db` service currently only mounts `./data/pb_data:/pb_data` and `./data/plugins:/data/plugins` (confirmed, lines 42–44) — there is no existing mount point for an admin-supplied region catalog file, and no `REGION_CATALOG_CONFIG_PATH` env var is set anywhere.
**Why it happens:** The Go code change (env var read + file parse) is easy to plan for; the accompanying `docker-compose.yml`/`docker-compose.prod.yml` volume+env additions are infrastructure changes that are easy to omit from a "backend code" phase's task list.
**How to avoid:** Include an explicit task to add both the volume mount and the env var to `docker-compose.yml` (and `docker/docker-compose.prod.yml`), e.g. `- ./region-catalog.json:/data/region_catalog.json:ro` + `REGION_CATALOG_CONFIG_PATH: /data/region_catalog.json`. Note this is within the phase's "Go/PocketBase backend" scope (infra config, not SvelteKit/Flutter code).
**Warning signs:** Success Criterion 1 ("no config file... serves an empty catalog") will trivially pass in dev (nothing mounted = nothing to read = empty catalog by design) even if the volume mount was never actually wired up for the *populated* case — this pitfall can hide behind a passing "empty catalog" test.

### Pitfall 7: Region `id` from admin config is attacker-adjacent input for filesystem paths
**What goes wrong:** D-03 builds archive paths as `pb_data/region_archives/{region_id}/vector.pmtiles`. If `region_id` is used unsanitized, a config entry with e.g. `id: "../../etc"` could path-traverse outside the intended archive directory.
**Why it happens:** The admin config file is a trusted-ish input (only the instance operator edits it), but defense-in-depth is cheap here and this codebase already has two directly relevant precedents for exactly this class of risk: `pluginsystem`'s `pluginIDPattern = regexp.MustCompile('^[a-z0-9][a-z0-9_-]*$')` (validates untrusted-ish plugin directory names before they're used in `filepath.Join` calls), and the Flutter app's `map_cache_path.dart` (per project memory: "operator-controlled fontstack/range tokens are whitelisted... and rejected with `ArgumentError` before a path is built").
**How to avoid:** Validate each config entry's `id` against a strict allow-list regex (mirroring `pluginIDPattern`) before it is ever used in `filepath.Join`; reject the whole entry (log + skip, don't crash startup) if it fails, consistent with BACK-01's "config errors shouldn't break startup" spirit.
**Warning signs:** N/A — this is a preventive control, not something that surfaces as an observable bug until actively exploited.

## Open Questions

1. **Which resolution of Pitfall 3 does the user actually want?**
   - What we know: D-06 locks the *path string* `GET /api/v1/regions`; the phase boundary locks "no SvelteKit changes."
   - What's unclear: whether the user was aware these two locked constraints point at different layers when D-06 was decided during `/gsd-discuss-phase`.
   - Recommendation: the planner should surface this explicitly (e.g. as a `checkpoint:human-verify` note or an explicit assumption call-out in the plan) rather than silently picking Option 1, since it affects what Phase 22's Flutter client will call.

2. **Should the in-flight concurrency guard (Pitfall 5) be a full copy of `generator.go`'s `sync.Mutex`+`WaitGroup` map, or is a simpler "cron job only ever runs region builds sequentially within one goroutine, so no two builds for the *same* region can ever overlap by construction" argument sufficient?**
   - What we know: `app.Cron()` runs each *job* in its own goroutine (`go j.Run()`), but a single job's `run func()` can internally loop over regions sequentially — meaning within one cron tick, no two regions build concurrently, and no single region builds twice concurrently *within that tick*.
   - What's unclear: whether a prior day's cron tick could still be running (a very large region, or a stuck subprocess before Pitfall 2 is fixed) when the next tick fires — in which case two `region-archive-build` job invocations WOULD overlap.
   - Recommendation: build the guard anyway (cheap insurance, ~20 lines, direct precedent to copy) rather than relying on "should never happen if the timeout fix works."
