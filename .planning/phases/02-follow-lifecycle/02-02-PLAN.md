<objective>
Deliver the receiving half of the instance Follow lifecycle as a complete vertical slice: a remote Wanderer instance can POST an HTTP-signed Follow activity to this instance's inbox, the signature is verified, and the Follow is stored as `pending` (awaiting admin approval) instead of being auto-accepted.

Covers INST-03 (signed instance inbox endpoint) and FLCL-02 (incoming Application-type Follow → pending, not auto-accepted).

Purpose: Phase 1 created the instance actor and advertised its inbox IRI (`{ORIGIN}/api/v1/activitypub/instance/inbox`) but no endpoint serves it. This plan implements the endpoint and the actor-type branch that distinguishes instance follows (require admin approval, D-05) from user follows (auto-accept, unchanged).
Output: A Go inbox handler in `instance.go`, a thin SvelteKit proxy route that sets `X-Forwarded-Path` (required for signature verification in this codebase), the route registration in `main.go`, the actor-type branch in `ProcessFollowActivity`, and a Go test for the branch.

CRITICAL ARCHITECTURE NOTE (deviation from RESEARCH.md assumption): RESEARCH.md/PATTERNS.md assume an external reverse proxy sets `X-Forwarded-Path`. That is NOT how this codebase works. The existing user inbox is fronted by a SvelteKit route (`web/src/routes/api/v1/activitypub/user/[handle]/inbox/+server.ts`) that sets `X-Forwarded-Path = event.url.pathname` and forwards to the Go route `/activitypub/activity/process` via `event.locals.pb.send(...)`. The Phase 1 instance GET endpoint was likewise refactored to SvelteKit (commit 483f3aea). Therefore the instance inbox REQUIRES a matching SvelteKit proxy route. This is a thin 1:1 mechanical mirror of the existing user inbox proxy — it is not a federation-logic change and does not violate D-03 (the federation LOGIC stays in Go `instance.go`). It is mechanically required so `util.VerifySignature` can reconstruct the signed path. The CLAUDE.md "no SvelteKit changes for v1" guideline is superseded by the Phase 1 refactor reality; without this proxy the inbox cannot receive signed traffic at all.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote instance → SvelteKit inbox route | Untrusted HTTP-signed POST from an arbitrary remote actor crosses here |
| SvelteKit proxy → PocketBase Go route | Internal forward; X-Forwarded-Path is set here and trusted by the Go signature check |
| Go inbox handler → federation processors | Verified-actor activity dispatched to ProcessFollowActivity/Accept/Undo |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-03 | Spoofing | InstanceInboxHandler | mitigate | `util.VerifySignature` validates the HTTP signature against the sender actor's public key before any processing; unsigned/invalid requests get `e.UnauthorizedError`. |
| T-02-04 | Tampering | X-Forwarded-Path header | mitigate | Header is set by the trusted SvelteKit layer (event.url.pathname), not accepted from the remote client's own X-Forwarded-Path. The Go layer is only reachable internally via pb.send, matching the existing user-inbox trust model. |
| T-02-05 | Elevation of Privilege | actor-type branch | mitigate | Application-type Follows are stored as `pending` and require explicit admin approval (D-05/FLCL-02); they cannot auto-accept and gain follower status without human action. Branch filters on the local instance actor (object), which is the trusted, locally-set record. |
| T-02-06 | Information Disclosure | inbox handler | accept | The inbox returns 200 with the processor error embedded (mirrors existing ActivitypubActivityProcess behavior); no private actor fields are exposed. Acceptable to stay consistent with the established user-inbox contract. |
| T-02-07 | Repudiation | incoming Follow storage | mitigate | The incoming Follow is persisted to activitypub_activities (actor, object, type, iri), creating an audit trail and enabling correct Accept/Reject reconstruction. |
| T-02-SC | Tampering | go module / npm installs | mitigate | No new packages. Go imports (pub, core, util) and the npm import (activitypub-types, @sveltejs/kit) already present per RESEARCH.md audit and existing user-inbox route. |
</threat_model>
