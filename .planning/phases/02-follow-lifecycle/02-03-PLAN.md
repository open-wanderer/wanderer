<objective>
Deliver the admin-driven half of the instance Follow lifecycle as a vertical slice: an admin operating PocketBase's native admin UI can initiate an outgoing Follow, approve or reject an incoming pending Follow, and disconnect (unfollow) a peer — with the correct ActivityPub activity (Follow / Accept / Reject / Undo) delivered to the remote instance at each step.

Covers FLCL-01 (admin-initiated outgoing Follow via the OnRecordAfterCreateSuccess hook, per D-01), FLCL-03 (Accept on approval), FLCL-04 (Reject on rejection, mandatory per D-08), FLCL-05 (Undo on disconnect). No custom admin UI is built — the admin uses PocketBase's native collection record form to create/approve/reject/delete follows records (per D-02).

Purpose: Plan 02 made the instance able to RECEIVE follows. This plan makes the admin able to DRIVE the lifecycle. All three triggers are `follows`-collection record events. Because admin-panel operations bypass the HTTP API and call `app.Save()`/`app.Delete()` directly, the hooks MUST use the `AfterSuccess` family (`OnRecordAfterCreateSuccess`/`OnRecordAfterUpdateSuccess`/`OnRecordAfterDeleteSuccess`), NOT the `Request` family used by the existing user-follow handlers (Pitfall 1, D-06/D-07). Every hook must filter to instance-level follows first so user federation is untouched (Pitfall 4).
Output: Three new hook handlers + an `isInstanceFollow` filter in `db/hooks/follow.go`; two delivery helpers (`CreateAcceptFollowActivity`, `CreateRejectFollowActivity`) in `db/federation/follow.go`; three hook registrations in `db/main.go`; and a Go test for the filter + status-change logic.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin (PocketBase UI) → follows collection | Admin-authenticated writes drive outgoing AP activities; admin is trusted but actions must be scoped to instance follows |
| follows hook → remote instance inbox | Outgoing signed AP activity (Follow/Accept/Reject/Undo) crosses to an untrusted remote |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-08 | Elevation of Privilege | InstanceFollow*Handler | mitigate | Every handler calls `isInstanceFollow` first and returns early for user-level follows, so the instance actor's key is never used to sign activities for user follows (Pitfall 4). |
| T-02-09 | Spoofing | outgoing Accept/Reject/Undo | mitigate | PostActivity signs with the instance actor's private key; activities are constructed from the locally-stored original Follow, not from attacker-controlled input. |
| T-02-10 | Repudiation | lifecycle activities | mitigate | Each outgoing activity (Follow/Accept/Reject/Undo) is persisted to activitypub_activities with actor/object/type/published, giving an audit trail. |
| T-02-11 | Denial of Service | hook delivery | accept | PostActivity is fire-and-forget in a goroutine with panic recovery; a slow/unreachable remote does not block the admin save. Matches online-only constraint (dropped = dropped). |
| T-02-12 | Tampering | Reject path omission | mitigate | CreateRejectFollowActivity is wired into the update handler's "rejected" branch (D-08 mandatory); the rejected status value is enabled by the Plan 01 migration so the save succeeds. |
| T-02-SC | Tampering | go module installs | mitigate | No new packages. All imports already in go.mod per RESEARCH.md Package Legitimacy Audit. |
</threat_model>
