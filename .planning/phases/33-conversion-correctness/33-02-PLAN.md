## Runtime fact this plan depends on (verified, not in RESEARCH.md)

`GPX.parse()` passes `attrValueProcessors` to `xml2js`, which only coerces **attributes**.
`<ele>` is element *text*, so it is **never** coerced: `point.ele` is a **string** (`"1000"`) for
every XML-parsed GPX, and a real `number` only for programmatically constructed waypoints (route
planner, `correctElevation()`). Verified by running the real parser:

| Input | `point.ele` at runtime | `typeof` |
|-------|------------------------|----------|
| `<ele>1000</ele>` | `"1000"` | `string` |
| `<ele>0</ele>` | `"0"` | `string` |
| `<ele></ele>` | `""` | `string` |
| tag absent | `undefined` | `undefined` |
| `new Waypoint({ $: {...}, ele: 1000 })` | `1000` | `number` |

Consequence for the fix: a naive `Number.isFinite(point.ele)` guard would reject **every**
XML-parsed elevation and silently zero out gain/loss for all uploads. The coercion must happen
explicitly. That is what `parseElevation` exists for.
