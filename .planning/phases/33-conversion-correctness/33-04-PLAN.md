<objective>
Close VERIFICATION gap 1 (CR-02, BLOCKER): the CONV-04 fix removed the horizontal-movement
gate from smoothed elevation outright instead of replacing it with a noise-aware filter, so a
stationary recording with ordinary GPS/barometric jitter fabricates hundreds of metres of
gain and loss (independently reproduced: 210 m gain / 203 m loss over 0 m of travel), and
those values are persisted permanently because CONV-F01 migration is deferred.

Replace the bare `|diff| >= thresholdZ_m` commit rule with a **commit-then-retract**
filter: an elevation excursion is credited immediately (so a genuine climb is never
under-reported), and is *retracted* when the track returns to the pre-excursion elevation
**without having moved horizontally** — the signature of altimeter/GPS noise, and the only
thing that distinguishes a paused phone from rolling terrain.

Keeps the CONV-04 win intact: elevation is still evaluated on **every** sample, with no
early return gated on `smoothedDistance`. The horizontal check appears only on the
retraction path, which a monotonic climb never reaches.

Purpose: `trail.elevation_gain` / `elevation_loss` must be trustworthy for paused and
stationary recordings, which are a routine real-world input class.
Output: a noise-tolerant filter in `gpx-metrics-computation.ts` plus four regression
fixtures, three of which fail against the currently shipped code.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Uploaded/imported GPX -> `GPX.parse()` -> `GpxMetricsComputation` | User-supplied XML, already parsed upstream, crosses into arithmetic that this plan changes. The parse step itself is untouched. |
| `metrics.totalElevation*Smoothed` -> `trail.elevation_gain` / `elevation_loss` (PocketBase) | Computed numbers cross into persistence. CONV-F01 migration is deferred, so a wrong value written here is permanent. |

This plan adds **no new network boundary, no new endpoint, no new persistence write path,
no new authentication or authorization surface, and no new dependency.** It changes the
arithmetic performed on already-parsed numeric fields inside an existing pure class. The
honest security answer for the change itself is "no new attack surface"; the register below
covers the one real integrity concern (numeric corruption reaching persisted fields) and
the supply-chain line required by the phase's package gate.
