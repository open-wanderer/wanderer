<objective>
Build the deferred-upload drain: a `keepAlive` Riverpod notifier that walks the signed-in account's
not-yet-uploaded trails, replays the `PUT /tag` → `PUT /trail/form` → `PUT /waypoint` sequence
resume-from-step, writes each server id back the instant it arrives, backs off and parks on repeated
failure, and exposes a manual retry. Wire its two triggers (app foreground, connectivity regained)
into `MainApp`, plus the startup photo orphan sweep.

Purpose: SYNC-01/03/04/05 all live here. This is also the only place where a mistake produces a
duplicate trail on the server, because no backend idempotency mechanism exists.

Output: `sync_backoff.dart`, `trail_sync_provider.dart`, an app-wide lifecycle observer, and a
deliberate account-switch invalidation exclusion.
</objective>

**`app/lib/provider/trail/trail_sync_provider.dart`** — a new `@Riverpod(keepAlive: true) class TrailSync extends _$TrailSync` whose state is `Set<String> build() => {}`, holding the **local ids** currently draining (the server `id` is empty pre-sync, so it cannot be the key). Mirror `DownloadingTrailIds` exactly: re-entry guard at the top, `state = {...state, localId}` on entry, and a `finally` that always removes the key.

Methods:

- `Future<void> drainIfOnline()` — the single entry point every trigger calls. First `await ref.read(onlineStatusProvider.notifier).refresh()` and return immediately if it reports false. This is mandatory, not defensive: `OnlineStatus.build()` is optimistic (`true`), settles only from ordinary traffic, and Phase 35's OFFUI-04 already shipped a bug from trusting it at a cold moment (RESEARCH.md Pitfall 5). Then read the store, read `currentAccountId(store)` fresh (never a cached field), return if null, and call `selectDrainCandidates` with that id and `DateTime.now()`. Iterate the candidates **sequentially, one trail at a time** — Claude's-discretion item, chosen so a flaky connection cannot fan out into N concurrent partially-applied uploads, and so the in-flight set stays trivially reasonable for the delete gate. Add a re-entrancy guard on the whole drain (a private `bool _draining` flag reset in a `finally`), because both triggers can fire within milliseconds of each other on a foreground-with-reconnect.

- A private `Future<void> _drainOne(Store store, TrailEntity entity, String accountId)` implementing D-05's resume-from-step. Guard on the entity's `localId` being non-null, add it to the in-flight set, set the row's state to `uploading`, and then:
  1. Resolve tags via `ref.read(trailSaveProvider.notifier).resolveTags(...)` — a tag with a non-empty id is reused, one without is created. D-06's rule already lives in that method.
  2. If the row's `id` is still a local sentinel (`isLocalId`), build the multipart body with `toFormData(newPhotos: <File objects for the row's localPhotos>, isCreate: true)` and `PUT /trail/form`. The instant the response parses, call `writeServerTrailId` and let that transaction commit **before** anything else runs. This ordering is the whole of SYNC-04: there is no server idempotency key, so a crash after the server accepted the create but before the id was persisted is exactly what produces two trails (RESEARCH.md Pitfall 3). If the row's `id` is already a server id, skip this step entirely — the trail exists from a prior partial attempt.
  3. For each child waypoint whose `id` is still a local sentinel, call `WaypointSave.create` with the row's server trail id, then immediately `writeServerWaypointId` keyed on that waypoint's `localKey` — not on its (empty) id. A waypoint whose id is already a server id is skipped.
  4. On full success call `markTrailSynced` with the server photo filenames from the create response, then `deleteUnsyncedPhotoDir(localId)` (D-02), then invalidate `trailLibraryProvider` and the signed-in handle's `profileTrailsProvider` so the list drops the badge in place (SYNC-05).
  5. On any thrown failure call `recordDrainFailure` with `kMaxSyncAttempts` and `syncBackoffDelay`, and stop processing that trail. Do not delete the photo directory on failure — the retry needs it.

- `Future<void> retry(String localId)` — SYNC-03. Calls `resetDrainBackoff` then `drainIfOnline()`. Safe to call on a row that is already draining because of the in-flight guard.

- `Future<bool> deleteUnsynced(String localId)` — D-14. Returns false without doing anything when `state.contains(localId)` (deletion is blocked while a drain is in flight, never raced). Otherwise calls `deleteLocalTrailRow` and `deleteUnsyncedPhotoDir`, invalidates the same two list providers, and returns true.

Wrap every network call so a `DioException` is caught and routed into step 5 rather than escaping the notifier. Do not add a toast from inside the drain — SYNC-02 puts failure inline on the trail itself, and the design record explicitly rejects a separate pending-uploads surface.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| device → Wanderer API | The drain replays authenticated `PUT /tag`, `PUT /trail/form`, `PUT /waypoint` and photo uploads on the shared `Api` client |
| signed-in account → local drain queue | The drain uploads rows under the current session's credentials; a mis-scoped query would publish another account's content |
| crash point → server state | Any interruption between "server accepted the create" and "local row recorded the id" is an integrity hazard |
| app-docs filesystem → startup sweep | The sweep deletes directories at launch based on a live-row set |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-36-04-01 | Elevation of Privilege | `drainIfOnline` candidate selection | mitigate | `currentAccountId(store)` is re-read at the start of every drain run (never a notifier field) and passed to `selectDrainCandidates`, whose query filters `TrailEntity_.owner.equals`; account B can never upload account A's trail under B's session (D-13, ASVS V4) |
| T-36-04-02 | Tampering | duplicate server trail on retry | mitigate | `writeServerTrailId` commits before any waypoint step; the create step is skipped entirely when the row's id is no longer a local sentinel. Enforced by an acceptance criterion on textual call ordering inside `_drainOne`. |
| T-36-04-03 | Denial of Service | unbounded retry burning battery and data | mitigate | `kMaxSyncAttempts` ceiling plus a clamped `syncBackoffDelay` curve; a parked `failed` row is excluded by `isDrainDue` and only manual retry revives it (D-07) |
| T-36-04-04 | Denial of Service | overlapping drains desyncing bookkeeping | mitigate | Per-trail re-entry guard on the in-flight set plus a whole-drain `_draining` flag, both released in `finally` — the same class of failure documented for `_reconcileRegionComposition` in Phase 25 UAT |
| T-36-04-05 | Information Disclosure | in-flight bookkeeping surviving an account switch | mitigate | `trailSyncProvider` is deliberately excluded from `accountScopedProviders`; scoping is enforced by the owner-filtered query on every run, and the exclusion is doc-commented and test-pinned |
| T-36-04-06 | Tampering | startup sweep deleting live photos | mitigate | `keepLocalIds` is built from `unsyncedLocalIds(store)`, which includes rows in `uploading` state, so a crash-mid-drain resume keeps its files; the sweep is confined to `<app-docs>/unsynced` |
| T-36-04-07 | Spoofing / Session | credentials at deferred-upload time | accept | The drain reuses the existing authenticated `Api` client and `PersistCookieJar`; no new auth or session surface is introduced (RESEARCH.md Security Domain rates V2/V3 not applicable). A 401 during token refresh is deliberately not special-cased (D-07) and simply consumes an attempt. |
</threat_model>
