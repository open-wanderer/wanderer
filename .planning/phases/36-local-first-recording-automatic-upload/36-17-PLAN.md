<objective>
Close CR-03: `LocalUpdateOutcome.alreadyUploaded` correctly routes an edit to the network, and
the server ends up correct — but `_saveViaNetwork` writes to exactly two places, the remote
record and this screen's own fields. It never touches the ObjectBox row. That row still holds
the pre-edit name, is still owner-scoped to this account, is still `pending`/`uploading`/
`failed`, and — because `writeServerTrailId` already stamped a real server id onto it —
`mergeOwnTrails` (`own_trails_merge.dart:40-42`) dedupes the network hit **against that row's
id**. The own-trails list therefore renders the pre-edit values under a green
`trail_saved_successfully` toast, indefinitely: `alreadyUploaded` exists *because* the waypoint
loop is failing, and after `kMaxSyncAttempts` the row parks as `failed`, where `isDrainDue`
returns false forever. If the underlying waypoint failure is deterministic, the stale row is
permanent. From the hiker's seat this is indistinguishable from the silent loss CR-03 was raised
to fix — the loss moved from "the server never gets it" to "the device never shows it".

**Design decision — no dirty flag, no ObjectBox schema change.** The review's fix hint suggests
a dirty-flag on the row, and the earlier no-schema-change constraint is what forced the
workaround that produced this defect. A dirty flag is only needed when the local write happens
*before* the edit reaches the server — you then need to remember that the row diverges from the
server and must be pushed. That is not the shape here: `applyNetworkEditToLocalRow` runs
**after** a successful `POST /trail/form/{id}`, so the row is being reconciled to a known-good
server state. There is no new state to track and nothing to push, so no column is needed. The
tradeoff being accepted: a network save that succeeds and whose local reconciliation then throws
leaves the row stale (best-effort, logged) — which is exactly today's behaviour, not a
regression, and is bounded by retirement removing the row.

Also closes WR-13 (every save in the `alreadyUploaded` window re-uploads photos the drain
already sent, under the append-semantics `photos+` key, doubling the server-side set each time,
and the picker renders them twice before the save even runs), WR-14 (`_copyPhotosForLocalSave`
runs *before* the routing decision, so a refused write still mutates the photo directory —
`reconcileLocalPhotos` deletes a file the row still lists — and its `failedCount` is discarded on
every network route), and WR-16 (`resolveLocalSaveMode`'s doc comment asserts the exact opposite
of what `updateLocalTrail` does 250 lines below, so the next reader who trusts it re-opens CR-03).

Purpose: an edit the hiker made and the server accepted must be the edit the hiker sees.
Output: a reconciled local row, a photo payload that carries only genuinely new files, and a
routing decision that anticipates the refusal instead of discovering it after side effects.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Server response (`TrailSaveResult.trail`) → ObjectBox row | `applyNetworkEditToLocalRow` writes server-returned values into a persisted, owner-scoped row |
| Screen-held `localId` → row selection for a write | The id can originate in a `Trail` model constructed before an account switch |
| Picked photo paths → multipart upload | Paths come from `image_picker` and from app-owned storage and are sent under append semantics |
