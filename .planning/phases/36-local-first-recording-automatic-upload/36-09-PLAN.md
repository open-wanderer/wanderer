<objective>
Close UAT gap 1 (minor): "The own trails list shows a spinner every so often."

`trailFilterProvider` rethrows every offline `GET /trail/filter` failure as a plain
`Exception`, which opts it into Riverpod 3's `defaultRetry` (10 attempts, 200ms doubling
to a 6400ms cap). Each retry emits through `ProfileTrailsNotifier.build`'s `ref.watch`,
and `ref.watch` invalidates with `asReload: true`, so the list transitions to a genuine
`AsyncLoading`. `profile_trail_screen.dart:90` uses `.when()` with the default
`skipLoadingOnReload: false`, so every one of those ~20 emissions blanks the list.

This plan fixes all three layers, source-first: the filter no longer errors when the
device is merely offline (so there is nothing to retry), the list no longer rebuilds on
filter-provider churn even if it does error, and the screen no longer discards data it
already holds.

The fallback filter the offline path returns derives its slider bounds from the trails
actually on this device (user decision, 2026-08-03) rather than from a hard-coded
constant. Offline, the only trails that can possibly match a search are the ones on this
device, so bounds taken from those rows fit the real search space exactly — a hiker is
never handed a 500 km slider when nothing on the phone exceeds 40. The constant survives
as the empty-store floor.

Purpose: REC-06 requires the offline own-trails list to render. It renders, then
flickers to a spinner ~20 times over ~45 seconds, and drives ~20 dead network fetches
plus spurious `drainIfOnline()` kicks while the hiker just sits on the screen.

Output: a pure bounds calculator over on-device trail metrics, a filter provider with a
device-derived offline fallback and a bounded retry policy, a list provider decoupled
from filter churn, and a screen that keeps its rendered list across reloads.
</objective>

  documented, deterministic empty behaviour (an empty list) and costs one `List<double>` of

  materialisation" property the aggregate was chosen for is preserved.
