<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| menu action → durable local data | Delete on this menu reaches content that exists in exactly one place on earth |
| menu action → server | The same menu hosts a server `DELETE /trail/{id}` one branch away from a local-only action |
| rendered chip → drain provider | A tap on a card badge invokes an authenticated upload |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-36-08-01 | Tampering | `_deleteTrail` branch ordering | mitigate | The unsynced branch precedes the `isLocal` un-download branch and returns; gate-tested by index comparison. Without it an unsynced trail routes into `trailLibraryProvider.deleteTrail('')` and silently no-ops — the same class of fall-through defect the existing gate was written for (35-SECURITY.md) |
| T-36-08-02 | Tampering | delete during an in-flight upload | mitigate | The menu item is disabled while the trail's `localId` is in `trailSyncProvider`'s in-flight set, and `deleteUnsynced` independently refuses and returns false — a UI-only guard would still lose a race (D-14) |
| T-36-08-03 | Denial of Service | download action on an unsynced trail | mitigate | The item is hidden entirely under `if (!isUnsynced)`, so no request is ever issued with an empty trail id (D-17) |
| T-36-08-04 | Repudiation | misleading delete confirmation | mitigate | An unsynced delete uses its own l10n key stating it cannot be undone, never the shared string that also covers the genuinely reversible un-download flow |
| T-36-08-05 | Elevation of Privilege | retry tap uploading another account's trail | mitigate | `retry` funnels into `drainIfOnline`, which re-reads `currentAccountId` and selects candidates with an owner predicate (T-36-04-01); a chip can only ever be rendered for a trail already returned by an owner-scoped read |
</threat_model>
