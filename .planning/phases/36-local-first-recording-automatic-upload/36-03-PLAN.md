<objective>
Build `local_trail_store.dart` — the one place in the app that creates, reads, updates, promotes and
deletes a locally-captured `TrailEntity` row — and stop `TrailDownloadService` from wiping that
bookkeeping when the same trail is later downloaded.

Purpose: three later plans (the save path, the own-trails list, the drain) all need the same
account-scoped ObjectBox access. Writing it once, here, is what keeps D-13's "account B sees nothing"
and SYNC-04's "no duplicate on retry" from being re-derived three times with three different bugs.

Output: `local_trail_store.dart`, its pure-decision tests, and a `TrailDownloadService` carry-forward
guarded by a source-level gate test.
</objective>

**Pure decisions (no Store, unit-testable):**
- `enum LocalSaveMode { networkUpdate, createLocal, updateLocal }`
- `LocalSaveMode resolveLocalSaveMode(Trail trail)`: returns `networkUpdate` when `trail.syncState == TrailSyncState.synced && trail.id.isNotEmpty`; `createLocal` when `trail.localId == null`; `updateLocal` otherwise. Document why `trail.id.isEmpty` alone is no longer a sufficient discriminator (RESEARCH.md Pitfall 2: after this phase it means both "never saved" and "saved locally, still unsynced", and a two-way branch would create a second server trail out of one edit session).
- `bool isDrainDue(TrailEntity entity, DateTime now)`: true only when `entity.syncState` is `pending` or `uploading`, and `entity.syncNextAttemptAt` is null or not after `now`. A `failed` row is deliberately NOT due — D-07 parks it for manual retry only.

**Write path (all mutations inside `store.runInTransaction(TxMode.write, ...)`):**
- `String saveNewLocalTrail(Store store, {required Trail trail, required String ownerAccountId, String? authorActorId, required String localId, required List<String> trailLocalPhotos, required Map<String, List<String>> waypointLocalPhotosByKey})`. Builds the entity via `TrailEntity.fromModel(trail)`, then explicitly sets `id = localId`, `localId = localId`, `owner = ownerAccountId`, `syncState = TrailSyncState.pending`, `syncAttempts = 0`, `syncNextAttemptAt = null`, `localPhotos = trailLocalPhotos`, and for each child `WaypointEntity` sets `localPhotos` from `waypointLocalPhotosByKey` keyed on the waypoint's `localKey`. When `authorActorId` is non-null and an `ActorEntity` with that id already exists in the store, link it as `entity.author.target` — best-effort only, so the card shows the hiker's own name instead of "Unknown"; a missing actor row is not an error. Returns `localId`.
- `void updateLocalTrail(Store store, {required Trail trail, required String localId, required List<String> trailLocalPhotos, required Map<String, List<String>> waypointLocalPhotosByKey})`. Looks the existing row up by `TrailEntity_.localId.equals(localId)` INSIDE the transaction, and if absent does nothing. Otherwise builds a fresh entity from the model, then carries the existing row's `obxId`, `id`, `owner`, `localId`, `syncState`, `syncAttempts`, `syncNextAttemptAt` and `savedByUserIds` forward onto it before the put, so a metadata re-edit never changes identity or ownership (REC-05, SYNC-05). Remove `WaypointEntity` rows that belonged to the old row but are absent from the new waypoint set, so a deleted waypoint does not linger.
- `void deleteLocalTrailRow(Store store, String localId)`. Removes the row and its `WaypointEntity` children by `localId`; a no-op for an unknown id (mirrors `TrailLibraryNotifier.deleteTrail`'s silent no-op precedent). Does NOT touch the filesystem — the caller pairs it with `deleteUnsyncedPhotoDir` from 36-02.

Every read and write in this file that resolves an account MUST call `currentAccountId(store)` at the point of use, never accept a cached id from a long-lived caller.

- `isDrainDue` is false for a `failed` row even with a null `syncNextAttemptAt`
- `isDrainDue` is false for a `synced` row

Extend `local_trail_store.dart` with the read and bookkeeping half.

**Reads — every one of them owner-scoped:**
- `Trail? readLocalTrail(Store store, String localId)` — single-row lookup by `TrailEntity_.localId.equals(localId)`, returning `entity.toModel()` guarded by a `try/catch` that logs via `debugPrint` and returns null, matching `TrailLibraryNotifier.build()`'s "losing the one bad row is the correct blast radius" rationale.
- `List<Trail> readOwnLocalTrails(Store store, {required String accountId, String? authorActorId})` — queries `TrailEntity_.owner.equals(accountId) | TrailEntity_.savedByUserIds.containsElement(accountId)`, then keeps a row only when `entity.owner == accountId` OR (`authorActorId != null && entity.author.target?.id == authorActorId`). That second clause is REC-06's "downloaded trails the hiker authored themselves"; the `owner` clause is every not-yet-uploaded trail. Convert with the same per-entity `try/catch` guard, sort by `created` descending, and return a flat list — no sectioning and no special sort (D-11). Document that a row whose `owner` is null can never satisfy the first clause, which is what keeps a pre-existing downloaded row from leaking into another account's list (T-36-03-01).
- `int countUnsyncedTrails(Store store, String accountId)` — counts rows where `owner` equals the account AND `dbSyncState` is not `TrailSyncState.synced.index`. Used by the sign-out warning (D-12).
- `Set<String> unsyncedLocalIds(Store store)` — every non-null `localId` across ALL accounts whose row is not synced. Deliberately NOT account-scoped: its only consumer is the startup photo sweep, which must not delete another account's pending photos just because that account is signed out (D-13 hides, never deletes).
- `List<TrailEntity> selectDrainCandidates(Store store, {required String accountId, required DateTime now})` — rows with `owner == accountId` whose `syncState` is not synced, filtered through `isDrainDue`, oldest `created` first so a hike's trails upload in capture order. Returns entities, not models, because the drain needs the live rows.

**Drain bookkeeping — each one its own small write transaction:**
- `void writeServerTrailId(Store store, {required String localId, required String serverId})` — sets the row's `id` to the server id and leaves `localId`, `owner` and `syncState` untouched. This is SYNC-04's load-bearing write: it must be callable, and must commit, the instant `PUT /trail/form` returns, before any waypoint upload starts (RESEARCH.md Pitfall 3 — there is no server-side idempotency key, so a crash between "server accepted" and "id persisted" is what produces a duplicate trail).
- `void writeServerWaypointId(Store store, {required String localId, required String waypointLocalKey, required String serverWaypointId, List<String> serverPhotoFilenames = const []})` — finds the child `WaypointEntity` by `localKey`, sets its `id` to the server id and its `photos` to the returned filenames, clearing its `localPhotos`.
- `void markTrailSynced(Store store, {required String localId, List<String> serverPhotoFilenames = const []})` — sets `syncState` to `synced`, `syncAttempts` to 0, `syncNextAttemptAt` to null, replaces `photos` with the server filenames and clears `localPhotos`. The row is kept, not deleted: the `obxId` never changes across the transition, which is exactly what SYNC-05's "keeps its identity in place" means concretely.
- `void recordDrainFailure(Store store, {required String localId, required DateTime now, required int maxAttempts, required Duration Function(int attempts) backoff})` — increments `syncAttempts`; when the new count reaches `maxAttempts` sets `syncState` to `failed` and `syncNextAttemptAt` to null, otherwise sets `syncState` back to `pending` and `syncNextAttemptAt` to `now.add(backoff(newAttempts))`. Takes the backoff as a function parameter so the curve itself stays owned by 36-04 and this file stays free of policy.
- `void resetDrainBackoff(Store store, String localId)` — sets `syncState` to `pending`, `syncAttempts` to 0 and `syncNextAttemptAt` to null. This is SYNC-03's manual-retry primitive.

Extend `app/test/util/local_trail_store_test.dart` with pure tests for `recordDrainFailure`'s decision boundary expressed through a small pure helper if one is extracted, or — if the logic stays inline — add tests asserting the `backoff` callback contract by constructing a `TrailEntity` directly and calling nothing that needs a Store. Where a behaviour genuinely needs a live Store, do not fake one: record it in the plan's SUMMARY as device-verified-only and leave the source-level invariant to the greps below.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| account A rows → account B session | A shared ObjectBox store holds both accounts' captured trails; only the `owner` predicate separates them |
| server response → local row identity | The server-returned trail id is written back into a row that already exists locally |
| download path → local bookkeeping | `@Unique(onConflict: replace)` lets an unrelated download overwrite a locally-owned row wholesale |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-36-03-01 | Information Disclosure | `readOwnLocalTrails` / `countUnsyncedTrails` / `selectDrainCandidates` | mitigate | Every query filters on `TrailEntity_.owner.equals(currentAccountId(store))` re-read at the point of use; a null owner never matches, so a downloaded row cannot be mistaken for another account's capture (ASVS V4, D-13) |
| T-36-03-02 | Elevation of Privilege | drain candidate selection | mitigate | `selectDrainCandidates` takes the account id as a required argument derived from a fresh `currentAccountId` read, so account B can never upload account A's trail under B's credentials |
| T-36-03-03 | Tampering | duplicate server trail on retry | mitigate | `writeServerTrailId` is a standalone committed transaction that sets only `id`, callable the instant `PUT /trail/form` returns and before any subsequent step (RESEARCH.md Pitfall 3); no server-side idempotency key exists, so this client write is the entire mitigation |
| T-36-03-04 | Tampering | `TrailDownloadService` unique-replace put | mitigate | Six local-bookkeeping fields are re-read inside the same write transaction and carried onto the fresh entity, guarded by a source-level gate test |
| T-36-03-05 | Denial of Service | one corrupt cached row blanking the whole list | mitigate | Per-entity `try/catch` around `toModel()` in every read, mirroring `TrailLibraryNotifier.build()` — the blast radius is the one bad row |
| T-36-03-06 | Repudiation | `unsyncedLocalIds` returning cross-account ids | accept | Deliberate: its only consumer is the photo orphan sweep, which must not delete a signed-out account's pending photos. It returns opaque local ids only, never trail content, and is never used for display or upload. |
</threat_model>
