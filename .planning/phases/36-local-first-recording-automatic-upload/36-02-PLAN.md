Build the app-owned storage for photos attached to a trail that has not uploaded yet (D-01/02/03),
and land every new user-facing string from the UI design contract in one place so no later plan has

for days on a multi-day hike. Without a copy into app-owned storage the photo is gone by the time
the drain runs.

  <action>
Create `app/lib/util/local_photo_store_util.dart`. The root directory is `<app-docs>/unsynced`, deliberately named distinctly from `library/` so D-02's cleanup and orphan sweep can target it without ever touching a downloaded trail's files. Import `package:path` as `p` and build EVERY path with `p.join` — never string interpolation. Do not copy `trail_download_service.dart`'s `'${appDir.path}/library/$trailId'` interpolation style; RESEARCH.md's Security Domain names `p.join` as the required pattern here.

Pure, Store-free, `dart:io`-free path builders (so they are unit-testable without a device):
- `String unsyncedPhotoRoot(String appDocsPath)` → `p.join(appDocsPath, 'unsynced')`
- `String unsyncedTrailPhotoDir(String appDocsPath, String localId)` → root joined with `localIdDirSegment(localId)`
- `String unsyncedWaypointPhotoDir(String appDocsPath, String localId, String waypointLocalKey)` → trail dir joined with `'waypoints'` and `localIdDirSegment(waypointLocalKey)`

Every builder must route its id through `localIdDirSegment`, so a tampered or malformed key throws `ArgumentError` before any filesystem call happens (T-36-02-01).

Async filesystem operations:
- `Future<LocalPhotoCopyResult> reconcileLocalPhotos({required String dir, required List<String> desiredPaths})`. `LocalPhotoCopyResult` is a small class with `final List<String> paths` and `final int failedCount`. Behaviour: create `dir` recursively if absent; for each entry in `desiredPaths`, if the path is already inside `dir` (test with `p.isWithin`) keep it as-is, otherwise copy the source file into `dir` under a collision-free destination filename derived from `p.basename` (prefix with an index when a file of that name already exists) and record the destination path. On a per-photo failure — source missing, disk full, permission denied — catch it, increment `failedCount`, DROP that photo, and continue; never rethrow and never fall back to the picker path (D-03: the track is irreplaceable, the photo is not, and disk pressure is precisely when the OS cache purge that motivated D-01 is most likely). After processing, delete any file already inside `dir` that is not in the returned `paths` list, so a re-save that removed a photo also removes its copy. Return the kept paths in the same order as `desiredPaths`. Document explicitly that this inverts `trail_download_service.dart`'s abort-and-delete-everything polarity on purpose.
- `Future<void> deleteUnsyncedPhotoDir(String localId)` — resolves `getApplicationDocumentsDirectory()`, deletes the trail's directory recursively if it exists (which also removes its `waypoints/` subtree), swallowing failures. Used both on successful drain and on unsynced-trail delete (D-02/D-14).
- `Future<int> sweepOrphanedUnsyncedPhotos({required Set<String> keepLocalIds})` — lists the immediate children of the unsynced root, deletes every directory whose basename is not in `keepLocalIds`, returns the number deleted. Best-effort: swallow per-directory failures and keep going. Never touch anything outside the unsynced root. Document that the caller supplies `keepLocalIds` from live not-yet-synced rows, so a row still in `uploading` state after a crash keeps its photos for the resume (D-05), while a leaked directory from a crash between "server accepted" and "files deleted" is reclaimed (D-02).

Create `app/test/util/local_photo_store_util_test.dart` covering, using `Directory.systemTemp.createTempSync()` as the fake app-docs root and cleaning up in `tearDown`:
- the three path builders produce `p.join`-shaped paths under `<root>/unsynced`
- each builder throws `ArgumentError` for `'../escape'` and for an id not matching the local-id pattern
- `reconcileLocalPhotos` copies a real temp file in and returns its new path inside `dir`
- a path already inside `dir` is kept verbatim and not duplicated
- a non-existent source path increments `failedCount` by 1, is absent from `paths`, and does not throw
- a previously-copied file absent from `desiredPaths` is removed from `dir`
- `sweepOrphanedUnsyncedPhotos` deletes a directory whose name is not in `keepLocalIds` and leaves a kept one intact

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| picked photo path -> app-owned filesystem | An untrusted basename from `image_picker` (or an OS share) becomes a destination filename |
| local id / waypoint key -> directory segment | Row-derived values cross into `dart:io` path construction |
| unsynced photo root -> rest of app-docs | The sweep and the delete both walk a directory tree next to `library/`, `regions/` and `objectbox/` |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-36-02-01 | Tampering | `unsyncedTrailPhotoDir` / `unsyncedWaypointPhotoDir` | mitigate | Every id argument passes through `localIdDirSegment`'s `^local-\d+-\d+$` whitelist, which throws `ArgumentError` before any `dart:io` call; unit-tested with `../escape` |
| T-36-02-02 | Tampering | destination filename in `reconcileLocalPhotos` | mitigate | Destination is built from `p.basename` of the source joined with `p.join` into an already-validated directory; a source basename can therefore never climb out of the trail's directory |
| T-36-02-03 | Denial of Service | `sweepOrphanedUnsyncedPhotos` | mitigate | The sweep enumerates only the immediate children of `<app-docs>/unsynced` and deletes by basename membership, so it can never reach `library/`, `regions/`, `map_cache/` or `objectbox/`; per-directory failures are swallowed so one bad entry cannot abort the sweep |
| T-36-02-04 | Denial of Service | disk exhaustion from leaked copies | mitigate | D-02's startup sweep is implemented here as a real function (wired in 36-04), not deferred as a nice-to-have |
| T-36-02-05 | Information Disclosure | copies surviving an account switch | accept | Copies live under a `localId`-named directory whose row carries an `owner`; another account never sees the row, so the bytes are unreachable through the app. `account_data_purge_util.dart` already documents that scoping — not deleting — is this app's chosen invariant. |
</threat_model>
