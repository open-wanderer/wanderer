<objective>
Turn `_onSave` from a two-way network-only branch into the three-way local-first branch this phase
needs, copy picked photos into app-owned storage before the row is written, and remove the two
synthetic waypoint ids that would otherwise make a not-yet-uploaded waypoint look already-uploaded.

Purpose: this is the literal offline-save failure REC-01 must eliminate — today every branch calls
the network unconditionally and any exception, including a plain offline `DioException`, shows
`error_saving_trail`.

Output: a `trail_create_screen.dart` that never needs a connection to save a captured trail, and a
source gate protecting the empty-id convention.
</objective>

- **`LocalSaveMode.networkUpdate`** — an already-uploaded trail being edited. Keep today's `trailSaveProvider.updateTrail` call, its success handling, its toast and its `catch` showing `error_saving_trail`, byte-for-byte. Both local branches are **fully local-first: they never touch the network, online or offline.** This resolves RESEARCH.md's Open Question 1 in favour of the uniform Komoot/AllTrails model the design record cites — one code path instead of two, and REC-01's "no save failure caused by being offline" becomes structurally true rather than a caught-exception behaviour. The immediate follow-up that keeps today's online UX is a fire-and-forget `unawaited(ref.read(trailSyncProvider.notifier).drainIfOnline())` after a successful local write: online, the trail uploads within a moment of the toast; offline, `drainIfOnline` returns immediately after its connectivity refresh. Record this branch-order decision in the plan's SUMMARY.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `image_picker` cache path -> app-owned storage | Untrusted OS-supplied paths are copied into a directory this app owns |
| form input -> local ObjectBox row | Title, description, category and tags are written to durable local storage with no server validation |
| local save -> deferred upload under the hiker's credentials | Content written now is published later under whatever session is current at drain time |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-36-06-01 | Tampering | photo copy destination | mitigate | All destinations come from `unsyncedTrailPhotoDir`/`unsyncedWaypointPhotoDir`, which validate their id through `localIdDirSegment` and build with `p.join` (T-36-02-01); the screen never constructs a path itself |
| T-36-06-02 | Elevation of Privilege | owner assigned at save time | mitigate | `saveNewLocalTrail` receives `currentAccountId(store)` read fresh inside `_onSave`, never a value cached at screen construction, so a mid-session account switch cannot mis-attribute a capture (RESEARCH.md Open Question 2) |
| T-36-06-03 | Tampering | duplicate server trail from a re-saved draft | mitigate | `resolveLocalSaveMode` routes a draft with a non-null `localId` to `updateLocal`, never to a second create; gate-tested (RESEARCH.md Pitfall 2) |
| T-36-06-04 | Information Disclosure | device-local fields reaching the server | mitigate | `Trail.localId` and `Trail.syncState` are `includeToJson: false` (36-01), so `toFormData` cannot leak them when the drain later uploads |
| T-36-06-05 | Denial of Service | disk pressure during photo copy | mitigate | `reconcileLocalPhotos` drops the failing photo and returns a count instead of aborting; the trail — the irreplaceable artefact — still saves (D-03) |
| T-36-06-06 | Repudiation | silent photo loss | mitigate | A single toast reports how many photos could not be saved, so the loss is acknowledged rather than invisible |
</threat_model>
