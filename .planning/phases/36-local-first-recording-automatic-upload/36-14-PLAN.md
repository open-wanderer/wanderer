<objective>
Close UAT gap 4 (blocker) at its root: an offline-created trail that has since uploaded leaves
a permanent, undeletable orphan in the own-trails list once it is deleted.

**This plan replaces its own earlier approach.** The first version of 36-14 accepted the
retained row as correct (SYNC-05) and bolted an owner-scoped, server-id-keyed cleanup onto
`trail_dropdown.dart`'s server-delete branch. On 2026-08-03 the product owner decided instead
that **a local trail row is deleted once it uploads successfully** (ROADMAP.md, superseding the
2026-08-02 planner decision "local rows survive promotion"). Their model:

> a non-synced trail appears in my own trails list. A synced one does as well because it now
> lives on the server (as long as I'm online). A synced trail will not appear in my own trails
> list once I'm going back offline but that is ok. Once a trail has been uploaded it needs to be
> downloaded by the user to appear again in own trails.

With no row surviving a successful upload, the orphan class cannot exist -- there is nothing for
a later delete to leave behind, and nothing for a reconciliation sweep to reconcile. The
delete-path fix is dropped entirely, not kept alongside: `trail_dropdown.dart` is not touched by
this plan.

Purpose: SYNC-05 says an uploaded trail becomes an ordinary trail and does not appear twice.
REC-06 enumerates what the offline own-trails list contains -- "every not-yet-uploaded trail plus
those downloaded trails the hiker authored themselves". An uploaded-and-not-downloaded trail is in
neither set, so the retained row made the list a *superset* of what REC-06 promises. Retirement
makes the implementation match both requirements exactly rather than over-delivering into a state
nothing else in the app knew how to remove.

Output: a retirement primitive that deletes the capture row (or demotes it, when some account
holds the trail in its offline library) in one write transaction; the drain calling it at the one
point that proves the upload finished; and the create screen's save routing taught that a missing
row means "it uploaded", so a post-retirement edit can never land on a green success toast.
</objective>

SYNC-05 compliance, argued rather than asserted (the plan does not proceed if this fails):

  SYNC-05 reads "Once uploaded, an unsynced trail becomes an ordinary trail -- it keeps its
  identity in the library rather than appearing a second time." Two obligations. (1) *No second
  entry.* `writeServerTrailId` stamps the SERVER id onto the row before retirement, so the row and
  the server record share one identity throughout; retiring the row leaves exactly one entry, the
  server's, under that same id. There is no moment at which the trail is listed twice --
  `mergeOwnTrails` covers the only overlap window, as above. (2) *Becomes an ordinary trail.*
  Retirement is the strongest available form of this: afterwards nothing on the device claims the
  trail is anything other than ordinary. The previous reading -- that "keeps its identity in
  place" mandated keeping the ROW -- was a planner gloss (ROADMAP 2026-08-02), not requirement
  text, and it is what produced a row the app had no affordance to remove. Retention is not
  required by SYNC-05 and is excluded by REC-06's enumeration. Compliance holds; proceed.

           /// uploading can be deleted outright, rather than demoted.
           ///
           /// A locally-captured row normally has an EMPTY
           /// [TrailEntity.savedByUserIds]: [saveNewLocalTrail] never writes
           /// it and [updateLocalTrail] only carries it forward, so nothing on
           /// the capture path can populate it -- D-10 keeps ownership ("I
           /// recorded this") and library membership ("I downloaded this")
           /// strictly separate.
           ///
           /// A non-empty list therefore means some account downloaded this
           /// trail while its upload was in flight. That is possible from the
           /// moment `writeServerTrailId` stamps the server id, because from
           /// then on the trail is fetchable and `TrailDownloadService` writes
           /// into the SAME row (`TrailEntity.id` is
           /// `@Unique(onConflict: replace)`). Deleting it would destroy that
           /// account's offline library entry and strand `library/<id>/` on
           /// disk with nothing pointing at it.
           bool shouldDeleteUploadedRow(List<String> savedByUserIds) =>

           /// Which save path a screen should take when it holds
           /// [persistedLocalId] and the store's row for it is [persisted]
           /// (null when there is no such row).
           ///
           /// [resolveLocalSaveMode] alone cannot answer this. It sees one
           /// [Trail], so a caller with no persisted row has to fall back to
           /// its own screen snapshot -- and that snapshot is captured while
           /// `syncState` is still `pending` and the server id is still blank.
           /// Since a successful upload now RETIRES the row
           /// ([retireUploadedLocalTrail]), "I saved this locally and the row
           /// is gone" is the normal post-upload state, and routing it on the
           /// stale snapshot sends the edit into [LocalSaveMode.updateLocal],
           /// which writes to a row that no longer exists and reports success.
           ///
           /// A null [persistedLocalId] is the genuinely-never-saved case and
           /// is delegated unchanged, so a first save still routes to
           /// [LocalSaveMode.createLocal].

             required Trail screenTrail,
             required String? persistedLocalId,
             required Trail? persisted,

             if (persistedLocalId != null && persisted == null) {
               return LocalSaveMode.networkUpdate;
             }
             return resolveLocalSaveMode(persisted ?? screenTrail);
