<objective>
Close UAT gap 4 (blocker): an offline-created trail that has since uploaded leaves a
permanent, undeletable orphan in the own-trails list once it is deleted.

After a successful drain, `markTrailSynced` (`local_trail_store.dart:579-600`) deliberately
KEEPS the local row — that retention is SYNC-05's "keeps its identity in place" and is NOT
itself the bug. What is missing is the other end of the row's life. The row survives with
`owner == accountId`, `id == <server id>`, `syncState == synced` and `savedByUserIds == []`,
and deleting that trail takes `_deleteTrail`'s THIRD branch (`trail_dropdown.dart:310-332`):
the model came from `GET /trail/<id>`, so `syncState` is the `synced` default and `isLocal`
the `false` default (`models/trail.dart:125,137-139`), skipping both earlier branches. That
branch is a pure network DELETE plus four invalidations and touches no local storage.
`deleteLocalTrailRow` has exactly ONE call site app-wide (`trail_sync_provider.dart:365`,
inside `deleteUnsynced`) which that branch never reaches, and `readOwnLocalTrails` has no
`syncState` and no server-existence predicate — so the invalidation at
`trail_dropdown.dart:318` faithfully rebuilds the list and re-emits the orphan, forever.

The orphan is unreachable by every existing removal affordance: it is absent from
`library_screen` (its `savedByUserIds` is empty), its detail screen never reaches the `data:`
branch so `TrailDropdown` never mounts, and `TrailListItem` has no menu. Only clearing app
data removes it. That is what makes this a blocker rather than a cosmetic defect.

Purpose: REC-06 defines what the own-trails list contains and SYNC-05 defines what happens to
a row when it uploads. Neither says a row outlives the record it represents.

Output: a server-id-keyed, owner-scoped row deletion primitive; a best-effort notifier method
that pairs it with the unsynced-photo-directory sweep; and the server-delete branch wired to
call it only after the server has actually confirmed the deletion.
</objective>

Rejected alternative, recorded so it is not re-proposed:

- **Reusing `TrailLibraryNotifier.deleteTrail(id)`**, which UAT gap 4 suggests considering. It
  does remove a row whose membership drains to empty — the orphan's common shape — but it is
  wrong here on three counts. (1) It does NOT remove the row's `WaypointEntity` children
  (`trail_library_provider.dart:77` is a bare `box.remove(entity.obxId)`), so every orphan
  cleanup would leak its waypoints. (2) It is membership-scoped, not owner-scoped: if the
  hiker re-downloaded their own uploaded trail on a device where a SECOND account also holds
  it, `libraryMembersAfterDelete` returns a non-empty set, the row is KEPT, and the orphan
  survives the fix for the account that owns it. (3) It deletes `library/<id>/`, which for the
  orphan's normal shape does not exist. A purpose-built owner-scoped primitive is both smaller
  and correct.

Deferred design question, answered explicitly (UAT gap 4, third `missing:` bullet):

- **Should a synced local row be reconciled against server state by a background sweep?**
  Deferred, on purpose. No sweep exists today (`unsyncedLocalIds` feeds only
  `sweepOrphanedUnsyncedPhotos`, a photo-directory sweep). A row sweep would have to delete
  local rows whose server record 404s — and the app lets the hiker change `serverUrl`, after
  which EVERY local row's id 404s against the new instance. A sweep with that failure mode
  silently destroys trails; it needs a server-origin marker on the row before it can be safe,
  which is its own design. The delete-path fix in this plan is complete for every orphan
  created from now on. Orphans already on a device are not healed by it — accepted, because
  this phase has not shipped (feature/app, v1.8 in progress), so the affected population is
  pre-fix test devices where clearing app data is a legitimate remedy.
