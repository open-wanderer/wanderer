<objective>
Warn a hiker who signs out while trails are still waiting to upload, naming the count, then let the
sign-out proceed (D-12).

Purpose: nothing is lost either way — `TrailEntity` is deliberately never purged on logout — but the
hiker has no way to know that, and signing into a different account is the single most common
"my tour is missing" report the design record cites.

Output: one shared guard function used by both sign-out call sites, plus a source-level gate test so
a future third call site cannot quietly bypass it.
</objective>

Create `app/lib/util/unsynced_signout_guard.dart`.

- `bool shouldWarnBeforeSignOut(int unsyncedCount) => unsyncedCount > 0;` — trivially pure so the threshold is one named, testable decision rather than an inline comparison duplicated at two call sites.
- `Future<bool> confirmSignOutWithUnsyncedTrails(BuildContext context, WidgetRef ref)` — reads the store from `objectBoxProvider`, resolves `currentAccountId(store)` fresh, and returns `true` immediately when there is no signed-in account or when `shouldWarnBeforeSignOut(countUnsyncedTrails(store, accountId))` is false. Otherwise shows an `AlertDialog` built exactly like `trail_dropdown.dart`'s `_confirmDelete`: no title, `content` set to `AppLocalizations.of(context)!.signout_unsynced_warning(count)`, and two `TextButton`s — `cancel` returning false and the existing `logout` string returning true. The confirm button is NOT styled red: this is a warning, not a destructive action, and nothing is deleted either way (D-12).

Return `true` for confirm and `false` for cancel or a dismissed dialog, so a caller can simply `if (!await confirmSignOutWithUnsyncedTrails(...)) return;`. Guard the post-`await` use of `context` with a `context.mounted` check, matching the pattern already used in `settings_account_screen.dart`.

Document in the function's doc comment that the sign-out itself is never blocked — `TrailEntity` rows deliberately survive logout (`account_data_purge_util.dart`), so this dialog exists only to tell the hiker that, not to stop them.

Create `app/test/util/unsynced_signout_guard_test.dart` covering `shouldWarnBeforeSignOut` for 0, 1 and a large count. The dialog half needs a live ObjectBox store and is covered by the gate test in Task 2 rather than a widget test.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| signed-in account → local row count | The warning names a count derived from the current account's rows only |
| sign-out → local data lifetime | A destructive-looking action runs adjacent to durable, unuploaded user work |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-36-05-01 | Information Disclosure | unsynced count in the dialog | mitigate | `countUnsyncedTrails` filters on `TrailEntity_.owner.equals(currentAccountId(store))` re-read at the point of use, so the number never reflects another account's captures (ASVS V4, D-13) |
| T-36-05-02 | Repudiation | silent data-loss perception on sign-out | mitigate | The dialog names the count and states explicitly that the trails are not deleted, converting an invisible state into an acknowledged one (D-12) |
| T-36-05-03 | Tampering | a future sign-out call site bypassing the guard | mitigate | Source-level gate test asserts the guard precedes `logout()` in `settings_screen.dart` and documents the one deliberate exemption |
| T-36-05-04 | Denial of Service | blocking sign-out on a pending upload | accept | Deliberately not blocked — D-12 makes this a warning, not a hard stop; the trails survive logout by design (`account_data_purge_util.dart`) |
</threat_model>
