<objective>
Add the two entry points that complete the end-to-end navigation journey: a fixed full-width Navigate button on `TrailDetailScreen` (D-01) and a floating full-width Navigate button on `TrailDetailMapScreen` (D-02). Both run the same flow (D-05/D-06/D-07): derive costing from the trail category, extract (and downsample) waypoints from the parsed GPX, POST `/api/v1/valhalla/navigate` with an in-button spinner, and on success `context.push('/trail/:id/navigate', extra: response)` — on failure show an error toast and stay.

The shared flow lives in one helper (`navigation_launch_util.dart`) so both screens call identical, tested logic instead of duplicating the Dio call. After this plan, a user can tap Navigate on either screen and land in the working navigation screen from Plan 02 — the full user story is delivered.

Purpose: Delivers NAV-01 and NAV-02, wiring the entry points to the Plan-02 screen and the Phase-1 endpoint.
Output: `navigation_launch_util.dart`, modified `trail_detail_screen.dart`, modified `trail_detail_map_screen.dart`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → /api/v1/valhalla/navigate | Outbound POST body (waypoints, costing) crosses to the SvelteKit endpoint |
| trail GPX → request body | Untrusted/large GPX point arrays are extracted into the waypoint payload |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-07 | Denial of Service | oversized waypoint payload to Valhalla | mitigate | Client downsamples to ≤2000 points (preserving endpoints) before POST; the Phase-1 Zod schema also caps at 2000 (A4) — defense in depth |
| T-02-08 | Input validation | empty/degenerate trail (no GPX or <2 points) | mitigate | Helper guards `points.length < 2` and empty `maneuvers`/`shape` before navigating; shows error toast instead of entering a broken screen (V5 light) |
| T-02-09 | Tampering | costing string sent to endpoint | mitigate | Costing is derived to one of the two enum values (`pedestrian`/`bicycle`); the server re-validates via the Zod enum |
</threat_model>
