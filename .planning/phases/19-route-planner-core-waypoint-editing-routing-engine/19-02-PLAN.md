<objective>
Build the route-planner's single source of truth: a class-based `@riverpod` family notifier (`RouteAnchors`, keyed by the fixed-at-entry `travelProfile`) that owns the ordered anchor list, the per-segment Valhalla routing engine (with the per-segment `CancelToken` + generation-counter race-guard the research flagged as MEDIUM confidence and novel to this codebase), the geometric segment-split used by a plain insert tap, and an immutable-snapshot undo/redo stack.

Purpose: This is the phase's load-bearing state architecture — every later plan (map overlays in 19-03, screen wiring in 19-04) calls into this provider's public methods rather than reimplementing routing/undo logic near the UI. Building and testing it in isolation first means the risky, novel logic (race-guard combo, blocked-state persistence) gets full RED→GREEN attention without UI-layer noise.
Output: `route_anchor_provider.dart` (+ generated `.g.dart`), `route_segment_util.dart`, and their test coverage.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Flutter client → `/api/v1/valhalla/route` (existing SvelteKit proxy → Valhalla instance) | Client-constructed coordinate pairs cross this boundary; an untrusted/unreachable/malformed response crosses back |
| Async state mutation surface | Multiple overlapping gesture-triggered async calls (drag, retry, toggle) can race against the same in-memory state |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-19-02-01 | Tampering | Malformed/out-of-range anchor lat/lon reaching Valhalla | mitigate | Client-side ±90/±180 range validation before constructing any `/valhalla/route` request body in `_resolveSegment`; out-of-range pairs are marked `blocked` without a network call |
| T-19-02-02 | Denial of Service | Unbounded/rapid-fire drag or toggle triggering many concurrent Valhalla calls | mitigate | Each call is scoped to exactly 2 points per segment (no whole-route payload); the race-guard cancels the previous in-flight request for the same `segmentKey` before dispatching a new one, so at most one request per segment is ever truly in flight |
| T-19-02-03 | Tampering / Repudiation | Out-of-order Valhalla response applied to the wrong (already-superseded) segment state | mitigate | Per-segment `CancelToken` + monotonically increasing generation counter (RESEARCH.md's Race-Guard Pattern); a response whose generation doesn't match the latest dispatched request for that `segmentKey` is discarded, never applied |
| T-19-02-04 | Denial of Service | An unreachable/erroring Valhalla instance silently degrading the route to straight lines, masking a real failure from the user | mitigate | ROUTE-05: failure sets `SegmentState.blocked` and preserves the prior polyline rather than silently falling back to straight — the failure is visible and retryable, never silent (Pitfall 2 explicitly avoided) |
| T-19-02-SC | Tampering | npm/pip/cargo/pub package installs | accept | No new packages introduced (RESEARCH Package Legitimacy Audit: N/A); the fake-Dio-interceptor test harness uses only the already-audited `dio` 5.9.2 direct dependency, no new test-mocking package |
</threat_model>
