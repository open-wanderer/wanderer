<objective>
Wire the `TrailMap` call site off `Trail.pmTiles`/`demPmTiles` and onto `TileRepositoryManager.localTilePathsForBounds` for its offline style composition (RENDER-01), using the typed vector/DEM split delivered by 25-02. `TrailMap`'s viewport is fixed for the screen's lifetime (`widget.trail.bounds`, D-05/D-06), so this is a one-time-per-compose bounds query — `localTilePathsForBounds(trail.bounds)` naturally returns every overlapping region's paths in one call, preserving the existing multi-cell behavior for a trail spanning several downloaded regions. No new camera-idle logic here (D-06 scopes that to `navigation_screen` only).

Add a third provider listen (`regionListNotifierProvider`) so a region finishing download mid-session live-swaps the basemap in — reusing the exact dual-listen → `_swapStyle()` pattern already in place for theme toggle and glyph-cache warm (RESEARCH.md Pattern 1). Re-query `localTilePathsForBounds` fresh on every `_swapStyle()` (cheap linear scan) rather than caching the path list, so a region completing download after mount actually updates the map (Pitfall 6). An uncovered viewport resolves to empty vector paths → blank basemap, matching today's empty-`cellPaths` failure mode, with no new banner/indicator (D-01/D-02).

Purpose: Decouple trail-map rendering from any specific trail's download history — the app-wide region registry becomes the offline tile source.
Output: A rewired `TrailMap._composeStyle` + a third region-list listen; `offline_style_rewriter.dart` untouched (D-06).

NOTE: This plan is written for the full-style-reload composition strategy (RESEARCH.md's recommended default). If 25-01's `checkpoint:decision` selects incremental composition instead, this plan must be revised before execution.
</objective>
