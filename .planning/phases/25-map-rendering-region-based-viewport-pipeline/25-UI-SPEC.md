# Phase 25 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope Determination: No New UI Surface

This phase is an internal rendering-pipeline swap, not a new user-facing feature. `TrailMap` and `navigation_screen` change **where** their offline tile data comes from (`TileRepositoryManager.localTilePathsForBounds` instead of `Trail.pmTiles`/`demPmTiles`); they do not change **what the user sees**.

Confirmed against every upstream artifact read for this research:

- **`.planning/ROADMAP.md` Phase 25** — 4 success criteria, all internal/data-flow ("`TrailMap`/`navigation_screen` read... via `TileRepositoryManager`", "only regions intersecting the viewport contribute style sources", "reusing `offline_style_rewriter.dart` unchanged"). None describe a new screen, dialog, banner, or copy string.
- **`.planning/REQUIREMENTS.md` RENDER-01/02/03** — all three are plumbing/verification requirements (data-source swap, viewport-scoped source composition, a maplibre API spike). No requirement text mentions a UI element.
- **`.planning/phases/25-map-rendering-region-based-viewport-pipeline/25-CONTEXT.md` D-01/D-02** (locked user decisions) — explicitly reject a new "no offline data" banner or online-fallback indicator for an uncovered viewport. The uncovered-viewport behavior is a **blank basemap**, identical to today's existing failure mode when `cellPaths` is empty (pre-Phase-25 behavior, unchanged). This is a locked decision, not open for reinterpretation in planning or execution — do not add a banner/indicator/toast/snackbar for this case.
- **`.planning/phases/25-map-rendering-region-based-viewport-pipeline/25-RESEARCH.md`** — confirms all edit points are existing files (`trail_map.dart`, `navigation_screen.dart`, `tile_repository_manager.dart`), no new screens/widgets/routes. The one new piece of *logic* (a debounced camera-idle listener on `navigation_screen` recomputing which regions' sources are active) has **zero visible UI** of its own — it drives a native-GL style swap (`controller.setStyle(json)`), not a Dart widget.

**Consequence for this contract:** there is no new component inventory, no new copywriting, no new color/typography/spacing tokens to declare, and no registry usage to vet. The checker's six dimensions should evaluate this phase against "did the executor correctly avoid inventing UI" rather than against a populated visual spec.

## Non-Visual Note for Planner/Executor (context, not a design contract item)

The only new *logic* in this phase — `navigation_screen`'s debounced camera-idle recompute of active region sources (RENDER-02) and the RENDER-03 composition-strategy spike — is entirely internal to the native-GL style pipeline. Per `25-RESEARCH.md`'s recommendation, the default strategy is a full `controller.setStyle(json)` reload routed through the existing `_onStyleLoaded` re-add-track machinery, which is why no new loading/transition UI is needed even though a region-boundary crossing may cause a brief map flicker (D-03, explicitly accepted as a v1.6 tradeoff, not something to mask with a spinner or transition overlay).
