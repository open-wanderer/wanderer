# Phase 21 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Platform note:** This phase is Flutter mobile (`app/lib/`), not the SvelteKit web app. `shadcn` and the web `DESIGN.md`/"The Terrain Log" palette (Polar Night, flat-by-doctrine elevation) documented in `CLAUDE.md`'s Design Context are a **web-only** artifact set — no `DESIGN.md`/`PRODUCT.md` file exists in this repo for the Flutter app. This contract inherits verbatim from `19-UI-SPEC.md` and `20-UI-SPEC.md` (same feature, same screen family — `route_planner_screen.dart`, `trail_source_select_screen.dart`) and extends it only where this phase introduces new surfaces: the hike/bike entry-point bottom sheet, the app-bar Finish action, and the undo/redo relocation. Do not import web CSS tokens or shadcn primitives into this phase.

## Spacing Scale

Declared values (must be multiples of 4), inherited from `19-UI-SPEC.md`/`20-UI-SPEC.md` and extended with this phase's entry-sheet tokens:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Gap between card title and description (matches `_SourceActionCard`'s existing `SizedBox(height: 4)`) |
| sm | 8px | Gap between the two hike/bike cards inside the entry sheet — half of `_SourceActionCard`'s existing 12px inter-card gap, tightened because the sheet holds only two cards, not three (Claude's Discretion — see below) |
| md | 16px | Sheet content padding (`EdgeInsets.fromLTRB(16, 16, 16, 24)`, matching `trail_quick_filter_bar.dart`'s established modal-sheet padding pattern); card internal padding (`_SourceActionCard`'s existing `EdgeInsets.all(16)`, reused verbatim, do not shrink) |
| lg | 24px | Sheet top corner radius (`BorderRadius.vertical(top: Radius.circular(20))` is the *exact existing app-wide `showModalBottomSheet` constant — see exception below, not this token literally) |
| xl | 32px | Not used this phase |
| 2xl | 48px | Minimum touch target for the app-bar Finish `IconButton` (Material default, unchanged) |
| 3xl | 64px | Not used this phase |

Exceptions (reused, load-bearing existing constants — do not round):
- **20px sheet corner radius** (`BorderRadius.vertical(top: Radius.circular(20))`) — the *exact* constant every other `showModalBottomSheet` call site in the app uses (`trail_quick_filter_bar.dart`, `list_quick_filter_bar.dart`, `settings_account_screen.dart`). Use this literal value for the entry-point sheet, not the 16px `RouteAnchorSheet`/`WaypointSheet` constant (that one belongs to `DraggableScrollableSheet`, a different chrome family) and not a rounded 24px.
- **16px card corner radius / 12px icon-badge corner radius** — `_SourceActionCard`'s existing constants (`BorderRadius.circular(16)` on the `Card`, `BorderRadius.circular(12)` on the icon badge `Container`), reused verbatim for the two hike/bike cards so they read as the same visual family as the screen the user just came from.
- **18px control-icon size** — the app-bar Finish action's icon size, matching the existing 18px `FaIcon` convention used by every other `route_planner_screen.dart` app-bar/control icon (back button, undo/redo, auto-routing toggle).

## Entry-Point Bottom Sheet Contract (phase-specific — D-01/D-02, HANDOFF-03)

- **Trigger:** `TrailSourceSelectScreen`'s existing "Plan a route" `_SourceActionCard` (`trail_source_planner` l10n string, already reading "Open trail planner"). Its `onTap` no longer pushes `/route-planner` directly (that was the Phase 19 TEMPORARY wiring) — it now calls `showModalBottomSheet` to present this dialog first.
- **Chrome:** `showModalBottomSheet(context: context, isDismissible: true, enableDrag: true, shape: RoundedRectangleBorder(borderRadius: BorderRadius.vertical(top: Radius.circular(20))))` — the exact, unmodified shape/dismissal defaults every other bottom sheet in this app already uses. `isDismissible`/back-button-dismiss are Flutter's defaults; do not set `isDismissible: false` (D-02 — this dialog must be dismissible with no navigation on cancel).
- **No forced choice (D-02):** there is no "Continue" button and no non-dismissible barrier. Each card *is* the full action — tapping a card both selects the profile and proceeds; there is no intermediate "confirm" step.
- **Content layout** (`Padding(EdgeInsets.fromLTRB(16, 16, 16, 24))` inside the sheet's `builder`):
  1. A drag handle bar — reuse the exact widget `RouteAnchorSheet`/`WaypointSheet` already use (`Container(width: 30, height: 5, BorderRadius.circular(24), color: theme.colorScheme.secondaryContainer)`, centered, `Padding(vertical: 8)`) — for visual consistency with every other draggable/dismissible sheet in the app, even though this sheet is fixed-height (not a `DraggableScrollableSheet`).
  2. Two `_SourceActionCard`-identical cards, stacked vertically with an 8px gap (spacing exception above): **Hike** (`FontAwesomeIcons.personHiking` icon) and **Bike** (`FontAwesomeIcons.bicycle` icon) — see Copywriting Contract for exact title/description text. No third option, no "Continue"/"Cancel" buttons below the cards.
- **On tap:** the sheet closes (`Navigator.pop(context)`), then the caller resolves `initialCenter` (gated by the new `allowAutoGeolocate` setting per D-03 — GPS fix if true and available, else the simplest existing fallback the codebase already has a precedent for, e.g. the last-known `mapCameraProvider` position; exact fallback is implementer's discretion per 21-CONTEXT.md, not a visual-contract concern) and pushes `/route-planner` with the chosen `travelProfile` (`'pedestrian'` for Hike, `'bicycle'` for Bike — matching `gpx_util.dart`'s existing costing-profile string values) and the resolved `initialCenter`.
- **Loading affordance while resolving `initialCenter`:** reuse `_SourceActionCard`'s existing `isLoading` trailing-spinner treatment (the exact pattern the "Import file" card already uses for `_importing`) on the underlying "Plan a route" card on `TrailSourceSelectScreen` for the brief window between the sheet closing and the planner screen pushing, if that resolution is not instantaneous. Do not invent a new spinner/overlay pattern for this — reuse the card's own loading state.

## App Bar Finish Action & Undo/Redo Relocation Contract (phase-specific — D-04, HANDOFF-01, ROUTE-04 carryover)

- **Finish action:** an `AppBar.actions` `IconButton` on `RoutePlannerScreen`, taking the app-bar slot undo/redo previously occupied. Icon: `FontAwesomeIcons.check`, size 18 (matches the existing app-bar icon-size convention). Tooltip/label: reuse the existing `l10n.finish` string ("Finish") verbatim — do not introduce a new l10n key for the tooltip.
- **Styling:** identical `IconButton.styleFrom(backgroundColor: Theme.of(context).colorScheme.surface)` container treatment as the existing back button and (formerly) undo/redo — one consistent pill-in-a-circle look across every app-bar action on this screen.
- **Enabled state (≥2 anchors, D-05):** Accent-primary icon tint (same enabled-tint convention as undo/redo).
- **Disabled state (<2 anchors, D-05):** Flutter's standard disabled `IconButton` treatment (`onPressed: null`, ~38% opacity) — same precedent Phase 19 established for undo/redo when their stacks are empty. Do not show a toast/snackbar explaining why; the tooltip text carries the explanation (see Copywriting Contract) and is available on long-press even when disabled.
- **Undo/redo relocation (D-04):** move out of `AppBar.actions` into the existing top-right map `controls` `Column` (`route_planner_screen.dart`'s `Positioned(top: 128, right: 0)` slot, currently holding only the auto-routing toggle pill per Phase 20's wiring). Undo/redo keep their exact Phase 19 visual spec unchanged — pill-shaped `IconButton`s (`theme.canvasColor` background, `BorderRadius.circular(24)`, `Padding(all: 8.0)`, `VisualDensity.compact`, `FontAwesomeIcons.arrowRotateLeft`/`arrowRotateRight`, 18px, Accent-primary enabled tint / standard-disabled treatment) — only their **position** changes, stacking below the auto-routing toggle in the same `Column` (Search → Auto-routing → Undo → Redo, top to bottom, extending Phase 20's established stacking order). Do not restyle them as part of this move.
- **Tapping Finish:** triggers the handoff sequence (Draft Trail Handoff Contract below). No confirmation dialog before handoff — Finish is a direct action, not a destructive one.

## Draft Trail Handoff Contract (phase-specific — HANDOFF-01, D-06/D-07/D-08)

This section documents the user-visible behavior and copy around the handoff sequence; the underlying data-shape rules (no `Waypoint` records, `waypoints: []`) are requirement-level (HANDOFF-01/`21-CONTEXT.md` D-07) and out of this visual contract's scope beyond what's needed to spec the transition correctly.

- **Sequence on Finish tap:** (1) one-time `/api/v1/valhalla/height` fetch against the final `plannedGpxProvider` route, merging `ele` into the GPX — **no loading spinner/dialog is required to be shown for this fetch** unless it measurably blocks the UI thread; if a loading affordance is needed, reuse the existing full-card `isLoading` spinner convention, not a new overlay. (2) On success or failure alike (D-06 — silent, best-effort, no error UI), build the draft `Trail` (`waypoints: []`, GPX track only, category pre-filled per D-08) and set `pendingImportedTrail` before navigating, following `trail_import_util.dart`'s exact existing mechanism. (3) `navContext.push('/trail/create/edit', extra: draftTrail)` — identical push shape to the GPX-file-import flow; no new transition/animation is introduced.
- **No error state for elevation failure (D-06):** never show a toast, dialog, or banner if the height fetch fails. This is a deliberate silent-degrade — the create/edit screen simply opens with ele-less GPX points. Do not add any "Couldn't fetch elevation" copy anywhere in this flow.
- **Resulting create/edit screen state:** `TrailCreateScreen` opens pre-filled with the synthesized track (rendered exactly as any GPX-file import renders today) and **no waypoint list entries** — the existing waypoints section of the create/edit form shows its normal empty state (unchanged widget, zero items), not a special "route-planner" variant. The category picker is pre-selected to the hike- or bike-mapped category (D-08) rather than left unset — this is the one field that differs from a plain GPX import's default state.
- **Category pre-fill icon/label reference (D-08, Claude's Discretion for exact lookup):** when the create/edit category picker renders the pre-filled selection, it uses that category's own icon/name exactly as `category_icon_util.dart`'s existing `_categoryIconData`/`trailCategoryIcon` already render any category — no new icon or badge is introduced for a "planner-originated" category. There is no visual difference between a route-planner-prefilled category chip and a manually-picked one.
