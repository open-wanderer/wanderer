  <behavior>
    - Single outer ring (Freiburg shape): input with one `1`-headed ring of `lon<TAB>lat` scientific-notation pairs terminated by `END`, then a file-closing `END`, returns a GeoJSON geometry `{"type":"Polygon","coordinates":[[...]]}` and a bbox `[minLon,minLat,maxLon,maxLat]` computed over the ring vertices.
    - Two outer rings, neither `!`-prefixed (Fiji antimeridian shape): returns `{"type":"MultiPolygon","coordinates":[[[...ring1...]],[[...ring2...]]]}`, NOT a single Polygon with two rings.
    - Outer ring plus a `!`-prefixed inner ring (synthetic fixture — no real one exists per RESEARCH A3): returns a Polygon whose coordinates are `[outerRing, holeRing]`, hole present as the 2nd ring.
    - Winding: after parsing, every outer ring has positive signed area (counter-clockwise) and every hole has negative signed area (clockwise); a fixture whose source points are wound the wrong way is reversed on output.
    - Ring closure: output rings have first coordinate == last coordinate even if the source omitted the closing repeat.
    - Coordinate order: each source line is `lon<TAB>lat`; output GeoJSON positions are `[lon, lat]` (do NOT transpose).
    - Malformed inputs each return a non-nil error and never panic: a coordinate line with a non-2 field count, an unparseable float, and a ring block that hits EOF before its `END`.
  </behavior>
  <action>
    Create `ParsePoly(data []byte) (geometry map[string]any, bbox [4]float64, err error)` in `db/commands/poly_parser.go`, package `commands`, stdlib only (`bufio`/`bytes`/`strings`/`strconv`/`math`/`fmt`) per D-03 (no new dependency). Implement the Osmosis `.poly` grammar exactly as verified in 28-RESEARCH.md Code Examples: line 1 is a free-text name (ignored); each ring begins with a header line (`1`, `2`, ... for outer; a `!`-prefixed header for a hole); coordinate lines are whitespace/tab-separated `lon lat` in scientific notation until a lone `END`; the whole file ends with a final `END`. Parse each ring into a `[][2]float64` of `[lon, lat]` positions. Classify a ring as a hole iff its header line begins with `!`, otherwise outer.

    Assemble geometry: if exactly one outer ring, emit a GeoJSON `Polygon` with coordinates `[outer, ...holes]` (all holes attached to the single outer). If more than one outer ring, emit a `MultiPolygon` (D-04's multi-part case), assigning each hole to the first outer ring that contains the hole's first vertex via a point-in-ring ray-cast test, falling back to the first outer ring when none contains it; each element is `[outer, ...itsHoles]`. Represent geometry as `map[string]any{"type": ..., "coordinates": ...}` so it round-trips cleanly through `encoding/json` and matches the JSON-field write idiom in 28-RESEARCH.md.

    Correct winding before emitting: compute each ring's signed area with the shoelace formula (`~10 lines`, per Don't Hand-Roll); reverse the point slice so outer rings are counter-clockwise (signed area > 0) and holes clockwise (signed area < 0), matching RFC 7946 (Pitfall 4). Ensure every emitted ring is closed (append the first position if the last differs). Compute `bbox` as `[minLon, minLat, maxLon, maxLat]` over all OUTER-ring vertices, reusing the exact element order documented in db/services/regions/config.go.

    Return descriptive errors (never `panic`) for: a coordinate line whose field count != 2, an unparseable float (`strconv.ParseFloat`), and a ring that reaches EOF before `END` — tag each error with the offending line content so plan 28-02's caller can log which region/file failed (Security Domain, Threat T-28-01). Write `db/commands/poly_parser_test.go` covering every case in `<behavior>` using inline string fixtures (build the synthetic hole and mis-wound fixtures by hand per RESEARCH A3).

  <behavior>
    - The `World` and `WorldCoasts` header lines (zero `;` characters) are skipped and never appear as nodes (Pitfall 2).
    - Depth = exact count of leading space characters, one space per level (Pitfall). `Germany` -> depth 0; ` Germany_Baden-Wurttemberg` -> depth 1; `  ...Freiburg` -> depth 2.
    - `comaps_id` = the first `;`-delimited field with leading spaces trimmed, internal spaces preserved verbatim (Pitfall 3): e.g. `Germany_Free State of Bavaria`.
    - Parent linkage: a node at depth d gets `ParentComapsID` = the most recent node seen at depth d-1; depth-0 nodes get an empty `ParentComapsID`.
    - Kind: a node is `group` iff the immediately following (non-skipped) line is at depth d+1; otherwise `leaf`. The last node is always `leaf`.
    - Name derivation (Open Question 1): strip the exact `ParentComapsID + "_"` prefix from `comaps_id`; a depth-0 node's name is its full `comaps_id`. `Germany_Free State of Bavaria` with parent `Germany` -> `Free State of Bavaria`.
    - Path (materialized): depth-0 node path = slug(comaps_id); deeper node path = parentPath + "." + slug(comaps_id), where slug lowercases and replaces spaces with `_`. `Germany_Free State of Bavaria` -> path `germany.germany_free_state_of_bavaria`.
    - sort_order = zero-based index among siblings sharing the same parent, in file order.
  </behavior>
  <action>

Read line by line with `bufio.Scanner`. Skip any line containing zero `;` (the `World`/`WorldCoasts` headers — Pitfall 2). For each remaining line: compute `Depth` by counting leading U+0020 space bytes; take `ComapsID` as the substring before the first `;` with only the leading indentation trimmed (keep internal spaces — Pitfall 3).

Track a per-parent sibling counter to assign `SortOrder` (zero-based, file order — Claude's Discretion: preserve CoMaps sibling ordering). Derive `Name` by stripping the `ParentComapsID + "_"` prefix from `ComapsID` (full name at depth 0). Build `Path` as parentPath + "." + slug(ComapsID) (slug = lowercase + spaces->underscores), or slug(ComapsID) at depth 0.
