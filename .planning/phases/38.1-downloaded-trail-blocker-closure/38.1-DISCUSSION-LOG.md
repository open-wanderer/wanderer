## CR-01 delete scoping

### Q1 — How should `_allowDelete`'s unsynced escape hatch be fixed?

| Option | Description | Selected |
|--------|-------------|----------|
| Owner-scope the hatch | Keep the `isUnsyncedState` branch but require `readOwnLocalTrail(...) != null`. Account B falls through to the authorship check and gets `false`. Smallest UI-layer change, reuses an existing owner-scoped read. | ✓ |
| Drop the hatch entirely | `_allowDelete` becomes authorship-only. Simplest rule; costs a placeholder-author capture its Delete route, which then needs a separate one. | |
| Owner-scope + store-layer guard | Both the owner-scoped hatch and hardening `deleteUnsynced`. | |

**User's choice:** Owner-scope the hatch
**Notes:** The store-layer half was split out into Q2/Q3 rather than bundled, and both were then chosen — so the effective outcome is defense-in-depth, arrived at deliberately.

### Q2 — Fix `deleteUnsynced`'s account-agnostic photo dir too, and how far?

| Option | Description | Selected |
|--------|-------------|----------|
| Gate the photo delete on the row | `deleteLocalTrailRow` returns `bool`; skip `_deletePhotoDirBestEffort` when it matched nothing. No on-disk change, no migration. | |
| Account-scope the path too | Move to `unsynced/<accountId>/<localId>/`. Structurally unreachable across accounts; changes on-disk layout and touches every path helper caller. | ✓ |
| UI gate only | Leave `deleteUnsynced` alone; the owner-scoped `_allowDelete` already blocks the reachable path. | |

**User's choice:** Account-scope the path too
**Notes:** *"No migration needed. App is not yet in production."* — this removed the option's main cost and is recorded as a hard constraint in CONTEXT.md D-06.

### Q3 — Also fix `deleteUnsynced` returning `deleted` when the owner-scoped lookup matched nothing?

| Option | Description | Selected |
|--------|-------------|----------|
| Yes — gate the result too | `deleteLocalTrailRow` returns `bool`; skip the photo dir and return a not-mine result. Kills the false success toast; two independent guarantees. | ✓ |
| No — path scoping is enough | The wrong-account call now deletes only its own nonexistent dir; the toast is cosmetically wrong in an unreachable state. | |

**User's choice:** Yes — gate the result too

### Q4 — What about existing `unsynced/<localId>/` dirs from the old layout?

| Option | Description | Selected |
|--------|-------------|----------|
| Ignore them | New writes go to the scoped path; the old root is never read again. Zero migration code. | ✓ |
| Delete the legacy root on first launch | One-shot cleanup; small amount of throwaway code that must itself be correct. | |
| Migrate them into the scoped path | Preserves dev-device capture photos; most code for least value. | |

**User's choice:** Ignore them

## CR-02 waypoint pruning

### Q1 — How should pruning in `applyServerTrailToLibraryRow` be controlled?

| Option | Description | Selected |
|--------|-------------|----------|
| Authoritative flag, default true | `bool waypointsAreAuthoritative = true`; fetch trigger keeps the default, save trigger passes `!result.hadWaypointFailures`. Caller declares what it knows. | ✓ |
| Never prune from the save path | Follow `applyNetworkEditToLocalRow`'s precedent exactly. Simplest; a genuine waypoint deletion survives offline until the next full fetch. | |

**User's choice:** Authoritative flag, default true
**Notes:** `TrailSaveResult.hadWaypointFailures` already exists, so this is wiring rather than plumbing.

## CR-03 remove-download

### Q1 — Where should the fix live?

| Option | Description | Selected |
|--------|-------------|----------|
| Store guard + UI guard | `deleteTrail` refuses to remove a live-capture row and drops only membership; `library_screen.dart` gains the guard the dropdown already has. | ✓ |
| Store guard only | Structurally safe, but the action silently no-ops with no explanation. | |
| UI guard only | Matches precedent, but leaves the unscoped `box.remove` armed for the next caller. | |

**User's choice:** Store guard + UI guard

### Q2 — What should the guard actually test?

| Option | Description | Selected |
|--------|-------------|----------|
| Owner-scoped live capture | The same predicate CR-01 introduces. Account B keeps *Remove download*; account A doesn't see it on their own pending capture. Fixes the dropdown's mirror-image defect too. | ✓ |
| Keep `isUnsynced`, just mirror it | Minimal and matches shipped precedent, but preserves the exact reasoning error the phase exists to remove. | |

**User's choice:** Owner-scoped live capture
**Notes:** This surfaced that `trail_dropdown.dart:206`'s existing `!isUnsynced` guard is itself an instance of the phase's core defect — it hides the *safe* action from an account that legitimately holds the download.

### Q3 — When the guard says no, what does the hiker see?

| Option | Description | Selected |
|--------|-------------|----------|
| Hide the action | Matches the dropdown's shipped behaviour and Phase 38's D-16/D-17 test: hide when meaningless, not merely unavailable. | ✓ |
| Enabled + refusal toast | Mirrors D-15's Edit choice, but costs an untranslated key for a state waiting cannot resolve. | |
| You decide | Defer to the planner. | |

**User's choice:** Hide the action
