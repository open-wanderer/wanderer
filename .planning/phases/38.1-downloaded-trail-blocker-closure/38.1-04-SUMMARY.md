# Phase 38.1 Plan 04: Store-Level Delete Guard (CR-03) Summary

**`TrailLibraryNotifier.deleteTrail` now refuses to `box.remove` a row that is still some account's live capture (`isLiveCaptureRow`), always drops this account's `savedByUserIds` membership regardless, and only deletes `library/<id>/` files when the row itself was actually removed -- with a source gate pinning the guard ahead of the removal.**

## Accomplishments
- Closed the store half of CR-03: an unscoped `box.remove(entity.obxId)` that ran whenever the calling account was the last library member no longer runs when the row is still a live capture for some account (`isLiveCaptureRow(entity)`, consumed in its pure form directly on the row already in hand inside the transaction -- no new query, per D-12's "exactly one predicate" rule).
- `deleteTrail` now always drops this account's `savedByUserIds` membership, even on the keep-the-row branch, so "Remove download" can never silently no-op.
- The `library/<id>/` on-disk cleanup is gated on a renamed, meaning-inverted `rowRemoved` flag, so downloaded files are never deleted out from under a row that is being kept because it is a live capture.
- Extended `deleteTrail`'s doc comment to name the CR-03 failure being closed and the deliberate leaked-directory tradeoff, so a future reader does not "fix" the intentional asymmetry back.
- Added `trail_library_delete_guard_test.dart`, a source gate (no ObjectBox harness exists under `flutter test`) pinning: the guard is evaluated before the removal, the guard is a refusal (not a log), membership is still dropped on the keep-the-row branch, the method never references `deleteUnsyncedPhotoDir`, and the directory delete is gated on `rowRemoved`. Manually confirmed the gate fails when the guard is reordered after `box.remove`, then reverted the reorder.
