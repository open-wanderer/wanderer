# Phase 38.1: Downloaded-Trail Blocker Closure - Context

**Gathered:** 2026-08-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the three BLOCKERs and four in-scope WARNINGs from `38-REVIEW.md` so that **no destructive
action in the app is scoped by a field read off a shared cache row**. Deleting local capture state
is scoped by account/owner; removing a download is scoped by library membership; neither can
destroy the other's data.

This is a gap-closure phase for Phase 38, executed **before Phase 37**. It fixes defects that
follow from a false premise (Phase 36's D-10) — it adds no new capability and no visual work.

**In scope:** CR-01, CR-02, CR-03, WR-07, WR-08, WR-12, and correcting Phase 36's D-10 in place.
**Out of scope:** every other WARNING in `38-REVIEW.md` (WR-01 through WR-06, WR-09 through WR-11)
— see Deferred Ideas.

</domain>

<decisions>
## Implementation Decisions

### The premise being corrected

- **D-01:** Phase 38's **D-03 is retracted**, and with it Phase 36's **D-10**. Unsynced-ness and
  library membership are **independent axes** — a row may be neither, either, or both. The overlap
  is not a brief race: Phase 36's D-07 parks a repeatedly-failing upload in `failed` state with no
  scheduled retry, so a row can hold another account's `localId` and non-synced `syncState`
  indefinitely. Full derivation with file:line evidence:
  `.planning/notes/unsynced-and-downloaded-are-not-mutually-exclusive.md`.
- **D-02:** The rule that replaces it, and which every fix below is an instance of: **any
  destructive action must be scoped by the identity it actually destroys.** Local capture state
  (rows, photo dirs) → scoped by `owner`/account. Download removal → scoped by `savedByUserIds`
  membership. Never by a flag read off the shared row.
- **D-03:** Phase 38's **D-01 still holds and is extended.** D-01 governed destructive-action
  *availability* (membership + authorship, never `Trail.isLocal`); 38.1 extends the same reasoning
  to *scoping* — the same class of error, one layer down.

### CR-01 — cross-account data loss via `_allowDelete`

- **D-04:** **Owner-scope the escape hatch, don't drop it.** `_allowDelete` keeps its
  `isUnsyncedState` branch but requires that **this account owns the local row**:

  ```dart
  final localId = widget.trail.localId;
  if (isUnsyncedState(widget.trail.syncState) && localId != null) {
    final store = ref.read(objectBoxProvider);
    final accountId = currentAccountId(store);
    return accountId != null &&
        readOwnLocalTrail(store, localId: localId, accountId: accountId) != null;
  }
  return widget.trail.author == user.actorId;
  ```

  Rejected: dropping the hatch entirely (authorship-only). It is the simpler rule, but a capture
  whose author is still a placeholder loses its Delete route and would need a separate one — new
  scope for a gap-closure phase. `readOwnLocalTrail` already exists and is already owner-scoped
  (`app/lib/provider/trail/local_trail_provider.dart:34`), so this reuses a shipped predicate
  rather than inventing one.

- **D-05:** **Account-scope the unsynced photo directory.** `unsyncedTrailPhotoDir` resolves
  `<appDocs>/unsynced/<localId>/` today — **no account component at all**, which is what turns the
  reasoning error into real cross-account file deletion. Move to
  `<appDocs>/unsynced/<accountId>/<localId>/` so the directory is *structurally* unreachable
  across accounts. Every reader and writer of `unsyncedTrailPhotoDir` / `unsyncedPhotoRoot` /
  `localIdDirSegment` must be updated together.

- **D-06:** **No migration for the old layout.** *Explicit user constraint: the app is not yet in
  production.* Existing `unsynced/<localId>/` directories on dev devices are simply never read
  again. Write no migration code and no first-launch cleanup — both were offered and both were
  rejected as cost without value.

- **D-07:** **Gate the delete result on the row match too** — belt and braces, independent of the
  path change. `deleteLocalTrailRow` returns `bool`; when it matched no row, `TrailSync.deleteUnsynced`
  must **skip** `_deletePhotoDirBestEffort` and must **not** return `UnsyncedDeleteResult.deleted`.
  Today it reports success — success toast, route popped, map providers notified — for an operation
  that deleted nothing it was allowed to delete. The store becomes honest regardless of who calls it.

### CR-02 — waypoint pruning from a known-incomplete list

- **D-08:** **Add `bool waypointsAreAuthoritative = true` to `applyServerTrailToLibraryRow`.** The
  caller declares what it knows:
  - the D-14 **fetch** trigger keeps the default `true` — a full server fetch *is* authoritative,
    and must stay so or WR-05 (server-side waypoint deletes never propagating) regresses;
  - the D-13 **save** trigger at `app/lib/routes/trail_create_screen.dart:800-812` passes
    `waypointsAreAuthoritative: !result.hadWaypointFailures`.

  `TrailSaveResult.hadWaypointFailures` already exists
  (`app/lib/provider/trail/trail_save_provider.dart:19`), so the signal needs no plumbing — only
  wiring. Rejected: *never prune from the save path* (simpler, but a genuine waypoint deletion then
  survives offline until the next full fetch) and *default `false`, opt in* (safest against a
  forgetful future caller, but silently regresses WR-05 if the fetch call site is missed).

- **D-09:** **When not authoritative, keep the existing row unchanged.** Re-add any
  `WaypointEntity` absent from the incoming list back into `entity.waypoints` as-is. Its photo
  files under `library/<id>/waypoints/<key>/` stay valid, and the row still reflects the last state
  the server confirmed — which is truthful, since the failed PATCH did not happen server-side
  either. Rejected: keeping it with a staleness marker (needs a new entity field, a migration and
  UI work — far beyond blocker closure).

- **D-10:** **Leave `some_waypoints_failed_to_save` alone.** Once pruning is gated the toast is
  accurate again; the defect was the silent local deletion, not the wording. No new string, and no
  14th untranslated key against D-17's English-only-in-13-locales tax.

### CR-03 — "Remove download" destroying a capture

- **D-11:** **Fix it in the store *and* the UI**, matching the defense-in-depth shape chosen for
  CR-01. `TrailLibraryNotifier.deleteTrail` must refuse to `box.remove` a row that is still a live
  capture and drop only the membership; the UI must not offer the action where it doesn't apply.
  Store-only would leave the hiker with a silent no-op; UI-only would leave the unscoped
  `box.remove` armed for the next caller.

- **D-12:** **The guard predicate is owner-scoped live capture — the same one CR-01 introduces**,
  not `isUnsynced`. This matters: `trail_dropdown.dart:206` currently hides the whole download
  family on `isUnsynced`, read off the shared row — so in the overlap state it hides *Remove
  download* from account B, who genuinely holds the trail in their library, while leaving the
  destructive action available. That guard is the mirror image of CR-01 and is fixed by the same
  predicate. One predicate serves both blockers; extract it once rather than writing it twice.

- **D-13:** **Hide the action when the guard says no**, matching the dropdown's shipped behaviour.
  This is consistent with Phase 38's D-16/D-17: hiding is right when the action would be
  *meaningless* rather than temporarily unavailable — and for your own not-yet-uploaded capture
  there is genuinely no download to remove. Unlike D-15's Edit, waiting for connectivity never
  makes it available. Rejected: enabled + refusal toast (another untranslated key for a state the
  hiker cannot resolve by waiting).

- **D-14:** `library_screen.dart`'s long-press `Remove` `ListTile`
  (`app/lib/routes/library_screen.dart:162-174`) gets the guard it is missing, so the two surfaces
  behave identically. Its confirm copy (`remove_download_confirm_body`, "the trail itself is not
  deleted") then becomes true, which it currently is not.

### WR-07/08/12 and the premise correction

- **D-15:** **Delete `LibraryDetailScreen` and its route.** `app/lib/routes/library_detail_screen.dart`
  plus the nested `GoRoute` at `app/lib/provider/router_provider.dart:181-188`. Nothing pushes
  `/library/:id` — library cards push `trailDetailLocation(trail)` — and the screen is a bare
  `DraggableScrollableSheet` that duplicates the real trail detail screen worse, with a
  `firstWhere` and no `orElse` that throws on any id not in the library. Deleting it also removes a
  second surface that would otherwise need every 38.1 guard re-applied. Rejected: wiring it up —
  that is new scope, and a diverging duplicate detail surface is exactly where CR-03 came from.
- **D-16:** **WR-08 — correct `Trail.isLocal`'s doc comment.** It still names the three consumers
  Phase 38 deleted as "load-bearing", inviting reintroduction. Rewrite it to state the flag is
  data-provenance only and must never gate a destructive action.
- **D-17:** **WR-12 — add the missing fixture.** Neither new test suite constructs
  `availableOffline: true` alongside a non-synced `syncState`, so they *structurally cannot fail*
  when the D-10 premise breaks. Add that fixture and drive all three blocker fixes through it —
  this is the test that would have caught the whole phase.
- **D-18:** **Correct Phase 36's D-10 in place** in
  `.planning/phases/36-local-first-recording-automatic-upload/36-CONTEXT.md`, pointing at the
  correction note, so the false premise stops propagating into future phases. The *badges* D-10
  justified remain fine (cosmetic); only the destructive-action gating it was later used to justify
  is retracted.

### Claude's Discretion

- Where the shared owner-scoped live-capture predicate lives (store helper vs provider vs util) and
  what it is named — D-12 requires only that there be exactly one.
- The exact signature change on `deleteLocalTrailRow` (`bool` return vs a small result type), as
  long as D-07's two behaviours are gated on it.

<code_context>
## Existing Code Insights

### Reusable Assets
- **`readOwnLocalTrail(store, localId:, accountId:)`** — already owner-scoped, already used at
  `app/lib/provider/trail/local_trail_provider.dart:34`. D-04's `_allowDelete` gate and D-12's
  download-family guard are both expressible in terms of it; no new query is needed.
- **`TrailSaveResult.hadWaypointFailures`** — already computed and already surfaced in the UI
  (`trail_create_screen.dart:849-855`). D-08 needs only to pass the value it already has one call
  further down.
- **`isUnsyncedState(...)`** — keep it, but never as the *sole* term in a destructive-action gate.
  D-04 and D-12 both pair it with an owner check.

### Established Patterns
- **`applyNetworkEditToLocalRow` deliberately never touches waypoints** (`local_trail_store.dart:548-556`,
  "clobbering any of them here would ... silently discard data this function was never given"). The
  precedent already existed; CR-02 is its sibling failing to follow it.
- **`shouldDeleteUploadedRow`'s doc already describes the overlap** in plain language — the codebase
  knew, D-10 just didn't carry it. Treat existing store docs as evidence, not commentary.
- **`@Unique(onConflict: replace)` on `TrailEntity.id`** means the download writer and the capture
  writer target **one row**. Any fix that assumes two rows is wrong.
- **Hide vs disable vs refuse** — 38-CONTEXT D-16/D-17 settled this: hide when meaningless, refuse
  with a string when temporarily unavailable, never silently grey out. D-13 applies the first.

### Integration Points
- The owner-scoped live-capture predicate (D-12) is the single new shared concept; it lands between
  the store layer and both UI surfaces (`trail_dropdown.dart`, `library_screen.dart`).
- The `unsynced/<accountId>/<localId>/` path change (D-05) fans out to every caller of the photo
  path helpers — this is the widest-reaching edit in the phase and should be planned as its own
  unit of work.

</code_context>

<specifics>
## Specific Ideas

- **"No migration needed. App is not yet in production."** — the user's explicit constraint on
  D-05/D-06. Do not add migration or cleanup code for the old `unsynced/<localId>/` layout, and do
  not treat legacy dirs as data worth preserving.
- The user chose defense-in-depth consistently — store-level *and* UI-level — for both CR-01 (D-07)
  and CR-03 (D-11), while declining it where the gate is genuinely structural. Follow that instinct
  when a judgement call arises: make the store honest, and make the UI not offer what the store
  will refuse.
- WR-12 (D-17) is not bookkeeping. The fixture that constructs `availableOffline: true` with a
  non-synced `syncState` is the one that would have caught this entire phase; treat it as a
  first-class deliverable, not a test-coverage chore.

</specifics>

<deferred>
## Deferred Ideas

The remaining WARNINGs from `38-REVIEW.md` were surfaced and deliberately left out of 38.1's scope.
They are real and should be scheduled, but they are not the premise error this phase closes:

- **WR-01** — a failed *refresh* renders a bare, un-`Scaffold`ed error page with no back button
  (`trail_detail_screen.dart:107-126`); `AsyncLoader.build` checks `hasError` before `hasValue`.
- **WR-02** — `ref.invalidate` after `await context.push(...)` with no `mounted` guard.
- **WR-03** — `navCacheJson` carried forward while `gpxData` is replaced; the cached Valhalla route
  can outlive the track it was computed for.
- **WR-04** — every downloaded-trail detail open re-mints the author/category rows, orphaning other
  trails' `ToOne` targets.
- **WR-05** — a trail whose waypoints were all deleted server-side keeps them offline forever.
  **Note the coupling: D-08 must not regress this** — the fetch path stays authoritative.
- **WR-06** — both new remove-download handlers drop an unawaited `Future`.
- **WR-09** — the new *Update* action re-enters a download path that deletes the existing offline
  copy on any failure.
- **WR-10** — `_showContextMenu`'s `router` parameter is implicitly `dynamic`.
- **WR-11** — new query handles are not closed on the exception path.

Also raised and not pursued: wiring `/library/:id` up as a distinct Library detail presentation
(D-15 deletes it instead) and adding a staleness marker to preserved waypoints (D-09).

</deferred>
