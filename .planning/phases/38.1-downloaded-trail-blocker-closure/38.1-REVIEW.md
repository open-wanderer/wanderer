# Phase 38.1: Code Review Report

**Reviewed:** 2026-08-04T00:00:00Z
**Depth:** standard
**Files Reviewed:** 22
**Status:** issues_found

## Summary

The three named blockers are, on their own terms, closed. `unsynced/<accountId>/<localId>/`
is genuinely airtight against traversal: both segments route through
`recordIdDirSegment`/`localIdDirSegment` before any `p.join`, `recordIdDirSegment`'s
`^[A-Za-z0-9_-]{1,64}$` admits no `.`, `/` or `\`, and the sweep really is two-level
(`isLocalId(basename)` at level 2 is what keeps it off `waypoints/` and off the legacy
one-level tree, and level-1 directories are never deletion candidates). The
`rowRemoved` inversion in `TrailLibraryNotifier.deleteTrail` is correct at every one of
its two consumers. `waypointsAreAuthoritative` defaults to `true`, `trail_provider.dart`
keeps the default, `trail_create_screen.dart` passes `!result.hadWaypointFailures`, and
the `false` branch re-adds rather than partially merges. `isLiveCaptureRow` /
`isOwnLiveCapture` / `ownLiveCaptureProvider` really are one rule with two wrappers, and
no consumer reconstructs the predicate inline.

What the phase did **not** close is the *other half* of each rule it wrote down.

The phase's own thesis is "an account-scoped value must be read fresh at the point of
use, never from a long-lived cache" (D-13, repeated in six doc comments). The two new
Riverpod providers violate it: `ownLiveCaptureProvider` and `localTrailProvider` are
keyed only on `localId`, are absent from `accountScopedProviders`, and nothing else
invalidates them on an auth user-id change — so a screen retained on the back stack
across an account switch keeps serving account A's answer to account B (CR-01).

Symmetrically, CR-03 taught `TrailLibraryNotifier.deleteTrail` to respect capture state,
but its mirror — `TrailSync.deleteUnsynced` → `deleteLocalTrailRow` — still removes a row
that other accounts hold in `savedByUserIds`, and never cleans the `library/<id>/`
directory that row was the only handle on (CR-02).

Beyond those two, the deliberate `library/<id>/` "leak" tradeoff in the SUMMARY is not
bounded (there is no `library/` sweep anywhere in the app, and the row that is supposed to
keep the directory reachable is itself removed by `retireUploadedLocalTrail` shortly
after), the CR-02 authoritativeness signal has a silent hole upstream in
`TrailSave.updateTrail`, and the sole source gate protecting the `rowRemoved` polarity
does not actually pin that polarity.

## Critical Issues

### CR-01: `ownLiveCaptureProvider` / `localTrailProvider` cache an account-scoped answer across an account switch

**File:** `app/lib/provider/trail/local_trail_provider.dart:26-35`, `app/lib/provider/trail/local_trail_provider.dart:48-55`, `app/lib/provider/account_scope_invalidation.dart:71-84`
**Classification:** **BLOCKER**

**Issue:**
Both new/changed providers are families keyed **only** on `localId`. Neither key includes
the account, and neither is listed in `accountScopedProviders`, which is the only thing
`main.dart:154` invalidates on an auth user-id change. Riverpod therefore memoizes the
result of `currentAccountId(store)` + the owner-scoped query for as long as *any* widget
keeps listening — auto-dispose only fires when the last listener goes away, and Flutter
keeps pushed-under routes mounted (`maintainState: true`).

Two concrete consequences:

1. **Content leak.** `trail_detail_screen.dart:74` and `trail_detail_map_screen.dart:71`
   do `ref.watch(localTrailProvider(localId))`. Account A opens
   `/trail/local/<localId>`, pushes to settings, signs out and signs in as B, then pops
   back. The retained screen re-renders from the cached `Trail` and shows account A's
   private, not-yet-uploaded trail to account B. This is verbatim the leak
   `readOwnLocalTrail`'s own doc comment claims to prevent
   (`local_trail_store.dart:914-927`): the owner clause is evaluated once and then cached.

2. **Stale destructive-action gate.** `trail_dropdown.dart:81` watches
   `ownLiveCaptureProvider(trail.localId)`. A cached `true` from account A re-arms
   `_allowDelete`'s escape hatch (`trail_dropdown.dart:437-439`) for account B with no
   authorship check — the exact CR-01 shape 38.1 exists to eliminate. The store layer
   currently refuses the resulting write (`deleteLocalTrailRow` returns `false`), so this
   degrades to a misleading error toast rather than data loss; but the UI gate itself is
   unscoped, and defense-in-depth is not the same as the gate being correct.
   A cached value also never recomputes when the drain retires the row, so the download
   family stays hidden and Delete stays offered on a trail that is now fully synced.

The doc comment on `ownLiveCapture` asserts it is "the single UI-facing handle on
`isOwnLiveCapture`"; what it actually is, is a memoized snapshot of it.

**Fix:**
Add both families to the invalidation list, and prefer including the account in the key
so a switch cannot alias two accounts onto one cache entry.

```dart
// app/lib/provider/account_scope_invalidation.dart
import 'package:wanderer/provider/trail/local_trail_provider.dart';

final accountScopedProviders = <ProviderOrFamily>[
  ownProfileProvider,
  settingsProvider,
  trailLibraryProvider,
  // ...
  // 38.1 D-13: both are keyed only on localId and resolve currentAccountId
  // INSIDE build(); without this an auto-dispose family kept alive by a
  // retained back-stack route serves the previous account's answer.
  localTrailProvider,
  ownLiveCaptureProvider,
];
```

Also add a unit test on `accountScopedProviders` asserting that every provider whose
`build()` calls `currentAccountId(store)` is present in the list — that is the invariant,
and it is currently unenforced.

### CR-02: `deleteLocalTrailRow` destroys other accounts' library membership and permanently orphans `library/<id>/`

**File:** `app/lib/store/local_trail_store.dart:782-806`, `app/lib/provider/trail/trail_sync_provider.dart:592-615`
**Classification:** **BLOCKER**

**Issue:**
CR-03 was fixed in one direction only. `TrailLibraryNotifier.deleteTrail` now refuses to
`box.remove` a live-capture row (`trail_library_provider.dart:100`), and
`retireUploadedLocalTrail` refuses to remove a row with library members
(`local_trail_store.dart:862`, via `shouldDeleteUploadedRow`). `deleteLocalTrailRow` has
**neither** guard: it matches on `(localId, owner)` and unconditionally removes the row
and its `WaypointEntity` children.

Reachable sequence, entirely within the overlap state this phase documents as unbounded:

1. Account A captures trail T. `writeServerTrailId` stamps server id `S` (so T is now
   fetchable), a later waypoint upload fails, D-07 parks the row as `failed` with no
   scheduled retry.
2. Account B, on the same device, downloads T. `TrailDownloadService` writes into the
   *same* row (`TrailEntity.id` is `@Unique(onConflict: replace)`), sets
   `savedByUserIds = [B]`, carries `owner`/`localId`/`syncState` forward, and writes
   `library/S/` plus `entity.photos` = absolute paths into that directory
   (`trail_download_service.dart:145-146`).
3. Account A taps Delete. `_allowDelete` → `isOwnLiveCapture` true → the unsynced branch
   calls `deleteUnsynced(localId)`, which issues `DELETE /trail/S`, then
   `deleteLocalTrailRow` removes the row outright.

Result: account B's `savedByUserIds` entry is destroyed with no consideration, and
`library/S/` — whose only reference was `entity.photos` on the row just removed — is
orphaned on disk forever. `deleteUnsynced` only cleans `unsynced/<accountId>/<localId>/`
(`trail_sync_provider.dart:615`), and grep confirms there is **no sweep for `library/`
anywhere in the app** (the only writer is `trail_download_service.dart:63`; the only
deleter is `trail_library_provider.dart:113-119`, gated on `rowRemoved`).

This is the same defect class the phase exists to eliminate: a destructive action scoped
by one identity (`owner`) while destroying state that belongs to a different identity
(`savedByUserIds`, and files keyed on the server id).

**Fix:**
Make `deleteLocalTrailRow` refuse to remove a row that other accounts still hold, and
report that back so the caller can clean the right things:

```dart
/// Returns what happened, so the caller can tell "removed", "demoted because
/// another account still holds it" and "no row I was allowed to touch" apart.
enum LocalRowDeleteOutcome { removed, demotedStillHeld, noMatch }

LocalRowDeleteOutcome deleteLocalTrailRow(
  Store store,
  String localId, {
  required String accountId,
}) {
  return store.runInTransaction(TxMode.write, () {
    // ... existing owner-scoped query ...
    if (entity == null) return LocalRowDeleteOutcome.noMatch;

    // Mirror retireUploadedLocalTrail: never remove a row some account holds
    // in its offline library -- that would destroy their library entry and
    // orphan library/<id>/ with nothing left pointing at it.
    if (!shouldDeleteUploadedRow(entity.savedByUserIds)) {
      entity.owner = null;
      entity.localId = null;
      entity.syncState = TrailSyncState.synced;
      entity.syncAttempts = 0;
      entity.syncNextAttemptAt = null;
      entity.localPhotos = [];
      trailBox.put(entity);
      return LocalRowDeleteOutcome.demotedStillHeld;
    }
    // ... existing waypoint + row removal ...
    return LocalRowDeleteOutcome.removed;
  });
}
```

`deleteUnsynced` then treats `removed` and `demotedStillHeld` as success (both still
delete `unsynced/<accountId>/<localId>/`) and `noMatch` as `UnsyncedDeleteResult.failed`.
Separately, `library/<id>/` needs an owner: either delete it on the `removed` branch after
checking the row is gone, or add a `library/` orphan sweep alongside
`sweepOrphanedUnsyncedPhotos` in `main.dart` (see WR-03).

### WR-01: `TrailLibraryNotifier.deleteTrail` still leaks `WaypointEntity` children

**File:** `app/lib/provider/trail/trail_library_provider.dart:100-103`
**Classification:** **WARNING**

**Issue:** The remove branch is a bare `box.remove(entity.obxId)` with no
`WaypointEntity` cleanup. `local_trail_store.dart:826-831` names this exact call site as
the leak `retireUploadedLocalTrail` deliberately does not copy ("copying that shortcut
here would leak a set of waypoints on every successful upload"). The phase rewrote this
statement's guard and its return value but left the leak in place. Orphaned waypoint rows
have a dangling `trail` `ToOne`, are invisible to every read path, and accumulate for the
life of the install (they only self-heal if the same trail is re-downloaded, because
`WaypointEntity.id` is `@Unique(onConflict: replace)`).

**Fix:**
```dart
if (remaining.isEmpty && !isLiveCaptureRow(entity)) {
  final waypointBox = store.box<WaypointEntity>();
  for (final waypoint in entity.waypoints) {
    waypointBox.remove(waypoint.obxId);
  }
  box.remove(entity.obxId);
  return true;
}
```

### WR-02: `deleteTrail`'s future is discarded at both call sites and its filesystem delete is unguarded

**File:** `app/lib/provider/trail/trail_library_provider.dart:113-121`, `app/lib/components/trail/trail_dropdown.dart:401`, `app/lib/routes/library_screen.dart:234`
**Classification:** **WARNING**

**Issue:** Both confirm handlers call `ref.read(trailLibraryProvider.notifier).deleteTrail(trail.id);`
without `await` and without a `catch`. `deleteTrail` awaits
`getApplicationDocumentsDirectory()` and `trailDir.delete(recursive: true)`, neither of
which is wrapped — an I/O error (a file held open by the photo viewer, a permission
failure) throws into a discarded future. Two consequences: the exception surfaces as an
unhandled async error in the zone rather than as UI feedback, and
`state = state.where((t) => t.id != id).toList();` at line 121 **never runs**, so the
library list keeps rendering a trail whose ObjectBox row has already been removed.

Note the existing `_deletePhotoDirBestEffort` / `sweepOrphanedUnsyncedPhotos` /
`deleteUnsyncedPhotoDir` trio all use best-effort try/catch for exactly this reason; this
path is the odd one out.

**Fix:**
```dart
if (rowRemoved) {
  try {
    final appDir = await getApplicationDocumentsDirectory();
    final trailDir = Directory(p.join(appDir.path, 'library', recordIdDirSegment(id)));
    if (await trailDir.exists()) await trailDir.delete(recursive: true);
  } catch (e, st) {
    // Best-effort: an unreclaimed directory must never leave the list stale.
    debugPrint('TrailLibrary: library dir cleanup failed for "$id": $e\n$st');
  }
}
state = state.where((t) => t.id != id).toList();
```
and `await`/`unawaited(...)` the call explicitly at both call sites. While here, note the
raw interpolation `'${appDir.path}/library/$id'` at line 115 — every other path builder in
this phase (`local_photo_store.dart:28-31`, `trail_download_service.dart:63`) uses
`p.join` + `recordIdDirSegment`; this one takes `id` straight from a `Trail` model.

### WR-03: the "deliberate leaked directory" tradeoff is not bounded

**File:** `app/lib/provider/trail/trail_library_provider.dart:72-78` (doc), `app/lib/store/local_trail_store.dart:862-882`
**Classification:** **WARNING**

**Issue:** The doc comment justifies not deleting `library/<id>/` on the keep-the-row path
with "A leaked directory is recoverable (and the row stays reachable from the hiker's
own-trails list)". That reasoning does not survive one more step:

- The keep-the-row path is reached only when `remaining.isEmpty` — i.e. it writes
  `savedByUserIds = []` onto the row it keeps.
- When that capture's upload later succeeds, `retireUploadedLocalTrail` evaluates
  `shouldDeleteUploadedRow([])` → `true` → `trailBox.remove(entity.obxId)`.
- `library/<id>/` now has **no** referent: the row is gone, `entity.photos` (which held the
  absolute paths into it) is gone, and there is no `library/` sweep anywhere in the app.

The directory is leaked permanently, not temporarily, and it is the full downloaded photo
set — tens of MB per trail on a device where the phase's other sweep exists precisely
because unbounded photo directories matter.

**Fix:** Add a `library/` counterpart to `sweepOrphanedUnsyncedPhotos`, driven by the set
of `TrailEntity.id`s that have a non-empty `savedByUserIds`, and call it from
`main.dart:122` beside the existing sweep. Alternatively, have
`retireUploadedLocalTrail`'s remove branch return enough information for the caller to
reclaim `library/<serverId>/`.

### WR-04: `waypointsAreAuthoritative: !result.hadWaypointFailures` is not a sound completeness signal

**File:** `app/lib/routes/trail_create_screen.dart:841-846`, `app/lib/provider/trail/trail_save_provider.dart:169-180`
**Classification:** **WARNING**

**Issue:** CR-02's fix rests on `hadWaypointFailures` meaning "`finalWaypoints` may be
incomplete". `TrailSave.updateTrail` sets that flag **only** in its three `catch (_)`
blocks. It also has a fourth path that drops a waypoint from `finalWaypoints`:

```dart
for (final wp in diff.updated) {
  final old = (oldTrail.expand?.waypointsViaTrail ?? const [])
      .where((o) => o.id == wp.id).firstOrNull;
  if (old == null) continue;   // <- wp is never added to finalWaypoints,
                               //    and hadFailures stays false
  ...
}
```

`diff` is computed on `listKey` (`id.isNotEmpty ? id : localKey`), but the re-lookup here
is on `id`. Any case where the listKeys match while the ids do not — an old waypoint with
id `X` and no `localKey` versus a new one with `localKey == 'X'` and an empty id — falls
through this `continue`. `applyServerTrailToLibraryRow` is then called with
`waypointsAreAuthoritative: true` and `waypointBox.remove(oldWaypoint.obxId)` deletes a
still-live waypoint from the offline copy: the exact CR-02 failure, still reachable.

Reachability is narrow, but it is the *only* thing standing between CR-02's fix and the
bug it fixed, and nothing tests it.

**Fix:** Make the drop explicit in `trail_save_provider.dart`:
```dart
if (old == null) {
  // The list is now incomplete -- callers use hadWaypointFailures as the
  // "this waypoint set is not authoritative" signal (38.1 CR-02).
  hadFailures = true;
  continue;
}
```
Better still, rename the field to something that names the property callers rely on
(`waypointSetIsComplete`) so future drop paths are obviously in scope.

### WR-05: `_deleteTrail`'s unsynced branch has no retired-server-id fallback

**File:** `app/lib/components/trail/trail_dropdown.dart:513-613`
**Classification:** **WARNING**

**Issue:** `trail_create_screen.dart:508-516` explicitly handles the case where a screen's
`trail.id` snapshot is still the blank local sentinel because the drain retired the row
after the last read — it consults `TrailSync.serverIdForRetired(localId)` via
`resolveNetworkSaveTarget` (CR-01, phase 36). The delete path does not. `_deleteTrail`
routes on `isUnsyncedState(trail.syncState)` off the same stale model, reaches
`deleteUnsynced(localId)`, which finds no row (`readLocalTrailServerId` → null,
`deleteLocalTrailRow` → false) and returns `UnsyncedDeleteResult.failed` → generic
`error_deleting_trail`. The hiker cannot delete their trail from that screen at all, and
the toast blames a failure that did not happen.

**Fix:** In `_deleteTrail`'s unsynced branch, on `UnsyncedDeleteResult.failed`, consult
`ref.read(trailSyncProvider.notifier).serverIdForRetired(localId)` and, when it yields a
real id, route to `_deleteOnServer(context, trail.copyWith(id: retiredId))` instead of
toasting — mirroring `resolveNetworkSaveTarget`'s shape on the save path.

### WR-06: the source gate for `rowRemoved` does not pin its polarity

**File:** `app/test/provider/trail/trail_library_delete_guard_test.dart:122-130`
**Classification:** **WARNING**

**Issue:** This gate is the *only* proof for `deleteTrail`'s destructive path (no ObjectBox

### WR-08: `deleteUnsynced` reports `failed` after a successful server DELETE when the local row vanished mid-flight

**File:** `app/lib/provider/trail/trail_sync_provider.dart:556-607`
**Classification:** **WARNING**

**Issue:** The server `DELETE /trail/{id}` is issued at line 569, `deleteLocalTrailRow` at
line 592. If the row is removed in between (a drain pass completing, a concurrent tap),
`rowMatched` is false and the method returns `UnsyncedDeleteResult.failed`. The caller
(`trail_dropdown.dart:601-611`) toasts `error_deleting_trail` for a trail the server has
already deleted, never calls `trailDeletionsProvider.announce(trail.id)`, and never pops
the route — so the map keeps rendering a trail that no longer exists anywhere.

**Fix:** Track whether the server DELETE was attempted and succeeded, and return `deleted`

```dart
var serverCopyDeleted = false;
if (serverId != null) { /* ... */ serverCopyDeleted = true; }
final rowMatched = deleteLocalTrailRow(store, localId, accountId: accountId);
if (!rowMatched) {
  debugPrint(...);
  // The server copy IS gone; only the local row raced us. Report success so
  // the map announcement and route pop still happen.
  return serverCopyDeleted
      ? UnsyncedDeleteResult.deleted
      : UnsyncedDeleteResult.failed;
}
```
