## The two blockers

**CR-02 — `deleteLocalTrailRow` destroying other accounts' library membership.**
This was also the phase's one blocking verification gap (`38.1-VERIFICATION.md`,
19/20). `deleteLocalTrailRow` matched a row by `(localId, owner)` and removed it
unconditionally, never checking `savedByUserIds` — unlike its sibling
`retireUploadedLocalTrail`, which already had that guard. Because
`TrailEntity.id` is `@Unique(onConflict: replace)`, account B's download lands
in account A's row, so A's ordinary delete wiped B's membership. The fix
introduces `LocalRowDeleteOutcome` (`noMatch` / `removed` / `demotedStillHeld`)
and reclaims `library/<serverId>/` only on the `removed` branch.

**CR-01 — providers caching an account-scoped answer across an account switch.**
`localTrailProvider` and `ownLiveCaptureProvider` were keyed only on `localId`,
resolved the account inside `build()`, and were absent from
`accountScopedProviders`. Fixed by registering them for invalidation on an auth
change, the minimal correct move — re-keying the families would have cascaded
widely for no additional safety.

## Notes on the subtler fixes

- **WR-03** turned out to be only partly covered by CR-02's fix. The
  `deleteUnsynced` path was handled, but the drain path was not:
  `retireUploadedLocalTrail` returned the same `String?` from both exits, so its
  caller could not distinguish demote from remove. It now returns
  `({String? serverId, bool rowRemoved})` and the drain pairs `rowRemoved` with
  a best-effort directory reclaim.

- **WR-08** deliberately narrows an existing invariant rather than relaxing it.
  `deleteUnsynced` now reports `deleted` from the no-match branch, but *only*
  when `serverCopyDeleted` proves the owner-scoped `readLocalTrailServerId`
  returned an id for this account and the server DELETE then succeeded or 404'd.
  In the CR-01 overlap that read returns null, no DELETE is issued, and the
  branch still returns `failed` having touched nothing.

- **WR-05**'s scope was narrowed by WR-08 — the "raced the drain" case now
  returns `deleted`, so the remaining case is specifically a row the drain
  retired before the screen's snapshot. Recovery goes through the
  account-guarded `serverIdForRetired`, mirroring `resolveNetworkSaveTarget` on
  the save path.

## Source gates

Several fixes touch paths with no ObjectBox harness under plain `flutter test`,
so they are pinned by source gates. Each new or modified gate was **confirmed to
fail against the specific regression it targets and pass when restored**:

- the `rowRemoved` polarity gate (WR-06)
- the D-07 no-match gate, refined to allow `deleted` only when gated on
  `serverCopyDeleted` (WR-08)
- a new gate pinning that `serverCopyDeleted` is never set outside the
  owner-scoped `serverId != null` branch (WR-08 / CR-01)
- the `retireUploadedLocalTrail` "both exits carry the captured serverId" gate,
  re-pointed to the record return plus two new assertions that the exits
  disagree on `rowRemoved` (WR-03)
- a new gate pinning that `serverIdForRetired` is consulted before the error
  toast (WR-05)

Existing gates were re-pointed rather than deleted, per their own inline
instructions.
