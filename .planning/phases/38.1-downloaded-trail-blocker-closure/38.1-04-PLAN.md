<objective>
Close CR-03's store half (D-11 / D-12): `TrailLibraryNotifier.deleteTrail` must refuse to
`box.remove` a row that is still a live capture, and drop only this account's `savedByUserIds`
membership instead.

Purpose: both "Remove download" confirm dialogs promise *"the trail itself is not deleted"* and then
call this method, which does an unscoped `box.remove(entity.obxId)` whenever this account is the
last library member. On the overlap row — `owner` set, `localId` set, `syncState == failed`,
`savedByUserIds == [A]` — that row IS the hiker's pending recording. Removing it destroys the queued
upload (`selectDrainCandidates` can never find it again), leaks its `WaypointEntity` children, and
orphans its unsynced photo directory. The UI half (hiding the action where it is meaningless) lands
in plan 05; store-only would leave a silent no-op, UI-only would leave the unscoped `box.remove`
armed for the next caller.

Output: a guarded `deleteTrail` and a source gate that pins the guard ahead of `box.remove`.
</objective>

Import `package:wanderer/store/local_trail_store.dart` for `isLiveCaptureRow`.

members, `library/<id>/` is NOT deleted. The row's `photos` column holds local file paths written by

pending recording pointing at missing images. A leaked directory is recoverable (and the row is
still reachable from the hiker's own-trails list); a broken reference is not. This phase is about
not destroying things.

Extend the method doc to name the failure being closed (CR-03): both confirm dialogs promise the
trail itself is not deleted, and on an overlap row this method used to destroy the queued upload,
leak its `WaypointEntity` children, and orphan the unsynced photo directory that `deleteTrail` does

view loses the row either way, which is correct: they removed their download.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| library membership → row lifetime | `deleteTrail` treated "no library members left" as "nobody needs this row", but `owner`/`localId`/`syncState` are a second, independent claim on the same row that membership knows nothing about. |
| UI promise → store behaviour | `remove_download_confirm_body` states "the trail itself is not deleted". Any store path that can delete the trail from behind that string is a repudiation defect, not only a data-loss one. |

| T-38.1-03 | Denial of Service | `TrailLibraryNotifier.deleteTrail`'s unscoped `box.remove(entity.obxId)` destroying a not-yet-uploaded recording — permanent, unrecoverable, and offered behind copy that promises the opposite | mitigate | Task 1 guards the removal with `isLiveCaptureRow(entity)` and drops only membership otherwise; Task 2 pins the guard's position with a source gate. |
