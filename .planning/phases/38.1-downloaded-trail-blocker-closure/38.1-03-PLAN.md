<objective>
Close CR-01's store half: move unsynced photo storage from `<appDocs>/unsynced/<localId>/` to
`<appDocs>/unsynced/<accountId>/<localId>/` (D-05) so one account's capture photos are
*structurally* unreachable from another account's delete path, and gate `TrailSync.deleteUnsynced`'s
file delete and success result on `deleteLocalTrailRow` having actually matched a row (D-07).

Purpose: CR-01 is the phase's high-severity threat. `_allowDelete`'s escape hatch is only half the
bug — the other half is that `unsyncedTrailPhotoDir` has no account component at all, so even a
correctly-refused, owner-scoped row delete was followed by an unscoped recursive directory delete
and a success toast. D-05 removes the path by which the mistake can express itself; D-07 makes the
store honest regardless of who calls it. Defense in depth, exactly as the user chose.

Output: an account segment in every unsynced photo path, every reader and writer updated in
lockstep, a two-level orphan sweep, an honest `deleteUnsynced`, and a behavioural cross-account
isolation test.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| account A's on-disk capture state → account B's delete path | Before D-05, `<appDocs>/unsynced/<localId>/` had no account component, so the two accounts' storage was literally the same directory. This is the boundary that did not exist and now does. |
| `accountId` string → filesystem path segment | D-05 promotes a server-issued record id to a path segment. New attack surface introduced by this plan's own fix; must be validated. |
| local row identity → destructive outcome reporting | `deleteUnsynced` reported `deleted` on a path where the owner-scoped write matched nothing. |
