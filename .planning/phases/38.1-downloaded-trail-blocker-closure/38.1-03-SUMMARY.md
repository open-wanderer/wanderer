# Phase 38.1 Plan 03: Account-Scoped Unsynced Photo Storage (CR-01 Store Half) Summary

**Moved unsynced photo storage from `<appDocs>/unsynced/<localId>/` to `<appDocs>/unsynced/<accountId>/<localId>/` so one account's capture photos are structurally unreachable from another account's delete path, and gated `TrailSync.deleteUnsynced`'s file delete and success result on `deleteLocalTrailRow` having actually matched a row.**

## Accomplishments

- Closed the file-storage half of CR-01: `unsyncedTrailPhotoDir`, `unsyncedWaypointPhotoDir`, and `deleteUnsyncedPhotoDir` all now require an `accountId` validated through `recordIdDirSegment` before any filesystem call, so `<appDocs>/unsynced/<accountId>/<localId>/` is a genuinely different directory per account rather than the same directory both accounts happened to share
- Rewrote `sweepOrphanedUnsyncedPhotos` to enumerate two levels (account directories, then `isLocalId`-gated localId directories within each), proven by tests to never touch a second-level `waypoints/` directory or a pre-D-05 legacy first-level `unsynced/<localId>/` tree (D-06: no migration, no cleanup, ever)
- Closed the provider half of CR-01 (D-07): `TrailSync.deleteUnsynced` now captures `deleteLocalTrailRow`'s `bool` result and refuses the photo delete, the provider invalidations, and the `deleted` outcome when no row was actually matched, returning `UnsyncedDeleteResult.failed` instead
- Threaded `accountId` through every caller in `trail_create_screen.dart` (`_copyPhotosForLocalSave`'s two call sites, the `photosNotYetOnServer` guard), keeping the same fall-back-to-unfiltered discipline on a missing/malformed account id that the file already used for a malformed localId
- Added the CR-01 behavioural proof: an on-disk test creates identically-named `localId` directories under two different accounts and shows `deleteUnsyncedPhotoDir` for one account leaves the other's directory and file completely intact
- Added two source gates pinning D-07's ordering (row-match guard before the photo delete) and outcome (`failed`, never `deleted`, on a no-op)

## Decisions Made

- `photosNotYetOnServer`'s new `accountId == null` branch skips the filter entirely (falls back to unfiltered `localPhotoPaths`) rather than throwing, matching the existing catch branch's documented behavior for a malformed id -- both "cannot determine account" and "cannot determine localId" degrade the same way.
- `updateLocal`'s new `accountId` read copies `createLocal`'s exact shape and `StateError` message verbatim, per the plan's explicit instruction, so the existing catch surfaces the same `error_saving_trail` toast from either local-save branch.
- Fixed the pre-existing `local_trail_retirement_gate_test.dart` "files are swept after the row is retired" test in place (it string-matched `_deletePhotoDirBestEffort(localId)`, broken by Task 2's signature change to two arguments) rather than leaving it failing -- it pins a real, still-true invariant (row deleted before files swept) that this plan did not intend to touch.
