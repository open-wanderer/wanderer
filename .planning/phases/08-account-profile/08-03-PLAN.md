<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Flutter client → SvelteKit/Go API | Avatar upload, bio save, account deletion cross here; server is authoritative for access control and storage. |
| Flutter client → iOS OS (photo library) | Gallery pick crosses into OS-managed media (gated by Plan 01's NSPhotoLibraryUsageDescription). |
| User action → destructive deletion | Irreversible account+trails deletion is triggered from the client. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-09 | Repudiation / Tampering | Accidental or unauthorized account deletion | mitigate | An explicit `AlertDialog` confirm gate (ACCT-05/D-12) stands between the tile tap and `DELETE /user/{id}`; the destructive action is styled red and is the last item. Deletion only proceeds on an affirmative dialog result. |
| T-08-10 | Tampering (IDOR) | Deleting/uploading to another user's account | mitigate | All paths use `user.id` from `authProvider.value` (the authenticated user's own id); the server enforces `id === authStore.record.id` → 403 (V4). |
| T-08-11 | Session | Stale session after deletion | mitigate | After `DELETE`, `authProvider.notifier.logout()` clears the cookie jar + ObjectBox and go_router redirects to `/login` (D-13), so no stale authenticated session remains. |
| T-08-12 | Information Disclosure | Avatar/bio save errors leaking internals | mitigate | Failures surface via the existing toast pattern with safe `l10n.*` messages; no `print()` of tokens/PII (V7). |
| T-08-13 | Tampering (stale cache) | Displayed avatar/email stale after change | mitigate | `authProvider.refresh()` re-fetches the expanded UserEntity and re-writes ObjectBox after avatar/email change (Pitfall 3 / Runtime State Inventory); bio re-writes via `settingsProvider.saveToServer`. |
</threat_model>
