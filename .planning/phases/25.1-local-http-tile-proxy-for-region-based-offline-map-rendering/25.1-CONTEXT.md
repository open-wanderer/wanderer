# Phase 25.1: Local HTTP tile proxy for region-based offline map rendering - Context

**Gathered:** 2026-07-23
**Status:** Ready for planning

<domain>
## Phase Boundary

This phase replaces the incremental `addSource`/`removeSource` region-swap reconcile (`_reconcileRegionComposition` in `navigation_screen.dart`, and the equivalent add-only `_addRegionComposition` in `trail_map.dart`) with a local loopback HTTP tile proxy: a static XYZ `tiles:` source (vector and DEM) served by an in-app `HttpServer`, resolving each `(z,x,y)` tile request against the downloaded region archives via `pmtiles`' per-tile random access. MapLibre Native's own viewport tracking takes over which regions contribute tiles, eliminating the hand-rolled Dart diffing entirely. This directly closes Phase 25's UAT Test 4 gap (a reentrancy race in the reconcile, diagnosed in `.planning/debug/navigation-screen-region-swap-broken.md`). Before finalizing the approach, an on-device spike must confirm MapLibre Native reliably loads loopback-HTTP tiles while the device is offline (airplane mode) — this phase's own risk gate, mirroring RENDER-03's spike in Phase 25.

</domain>

<decisions>
## Implementation Decisions

### Scope
- **D-01:** The proxy replaces region tile serving on **both** `TrailMap` and `navigation_screen`, not just the broken `navigation_screen` path. `TrailMap`'s current add-only incremental reconcile passed all its Phase 25 UAT tests, but unifying both screens on one mechanism deletes the `_sourceFromJson`/`_layerFromJson` duplication between the two files and leaves exactly one rendering mechanism app-wide, rather than one working-but-legacy path and one newly-replaced path living side by side long-term.

### Region Overlap Resolution
- **D-02:** When two downloaded regions' bboxes overlap and a requested tile falls inside the overlap, the proxy serves the tile from the region with the **smallest bbox** (most specific/local region wins over a broader one that happens to also cover the same spot).
- **D-03:** If two overlapping regions have bboxes of exactly equal size (a tie), the proxy serves the tile from whichever region was **most recently downloaded**. This tie-break is expected to be rare in practice.

### Risk-Gate Fallback Plan
- **D-04:** If the on-device spike finds MapLibre Native does NOT reliably load loopback-HTTP tiles while offline (airplane mode), do **not** pre-commit to falling back to a patched version of the old incremental reconcile. Stop and reassess with the user instead — the patch-based fallback (reentrancy guard + symmetric tracking-set updates + gating camera-idle during GPS-follow) remains a known, previously-scoped option, but the decision of whether to use it, revisit the proxy design, or consider something else is deferred to that point, not decided now.

### Claude's Discretion
- Server lifecycle details (app-wide singleton `HttpServer` vs. per-screen, port selection/binding strategy, start/stop tied to app foreground/background) — not discussed; implementation detail for planning/research to resolve using standard `dart:io` `HttpServer` patterns.
- Exact per-tile "which archive covers this tile" lookup mechanism (e.g., how `splitRegionTilePaths`/`localTilePathsForBounds`-style logic gets adapted to a per-tile `(z,x,y)` query instead of a bbox query) — technical implementation detail.
- Whether the vector and DEM proxy endpoints are one server with two routes, or two separate servers — implementation detail.
- Uncovered-tile behavior at the proxy layer (e.g., HTTP 404 vs. empty tile response) — should produce the same user-visible outcome already locked in Phase 25 (D-01/D-02 there: blank basemap, no banner/indicator), but the exact proxy-level mechanism to achieve that is Claude's call.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `TileRepositoryManager`'s existing region/package query surface (Phase 22/23) — the proxy's per-tile lookup builds on the same `RegionEntity`/`DownloadedTilePackageEntity` data, just needs a `(z,x,y)` → winning-archive-path resolution instead of (or alongside) the existing bbox-based `localTilePathsForBounds`.
- `pmtiles` 1.2.0's `PmTilesArchive.tile()` — already a dependency, per-tile random access is a documented capability just not yet exercised anywhere in the app.

### Established Patterns
- No `HttpServer`/`shelf` usage exists anywhere in `app/lib` today (per the debug doc's feasibility check) — this phase introduces genuinely new infrastructure (server lifecycle, port binding, background/foreground handling), not an extension of an existing pattern.

### Integration Points
- Both `TrailMap` and `navigation_screen` need their offline style composition rewired to a single static XYZ source instead of the current per-widget incremental composition (D-01).
- The proxy's overlap-resolution logic (D-02/D-03) is a new decision point in the tile-serving path that doesn't exist in `localTilePathsForBounds` today (that method returns paths for every overlapping region, doesn't pick a winner).

</code_context>

<specifics>
## Specific Ideas

- Smallest-bbox-wins overlap resolution, most-recently-downloaded as the tie-break (D-02/D-03) — a deliberate product choice about which region "feels" authoritative when downloads overlap.
- No pre-committed fallback if the offline-loopback-HTTP spike fails (D-04) — explicitly deferred, not a gap in the discussion.

</specifics>
