**Task 2 decision: PROCEED.** Per-test-case evidence, gathered on a physical Pixel 6 running the harness (`cd app && flutter run -t test/services/tile_proxy_spike_harness.dart`):

| Case | Description | Result | Notes |
|------|-------------|--------|-------|
| (a) | Online — style composed via `rewriteStyleForProxy`, basemap rendered through the proxy | PASS | Camera flew to the selected region as expected |
| (b) | Wi-Fi/cellular off, airplane mode NOT engaged | PASS | Within the SAME already-loaded map session as (a), no app restart; user confirmed tiles kept rendering while panning |
| (c) | Full airplane mode | **PASS** | Same session, no restart; user explicitly confirmed "tiles kept rendering while panning in airplane mode" — **this is the load-bearing PROXY-03 result** |
| (d) | Mid-session region download | PASS | Reload regions + fly to the newly-covered area, no screen remount needed — matches the harness's own test instructions |
| (e) | Platform manifest exceptions (Android cleartext / iOS ATS) | PASS | User's pasted `adb logcat` output shows zero `CLEARTEXT communication ... not permitted` errors; only unrelated log lines present (Mbgl sprite-load warning, HTTP "Canceled" during the Wi-Fi-off transition, GC noise) — confirms Plan 01's `network_security_config.xml` scoped-to-127.0.0.1 exception works correctly on-device |

All five test cases passed. Cases (b) and (c) — the load-bearing airplane-mode result — were exercised within a single already-loaded map session (no app restart between cases), which is the scenario Plan 04's production rewiring targets (a user who is online at app launch, then goes offline mid-session).

**Case (d) refresh mechanism for Plan 04:** tapping "Reload regions" (re-querying `store.box<RegionEntity>().getAll()`) followed by flying the camera to the newly-covered region's bounds is sufficient to surface newly-downloaded tiles — no screen remount, no proxy restart. Plan 04 should wire a lightweight `regionListNotifierProvider` listen that triggers the same reload-and-let-MapLibre-refetch behavior (no incremental source/layer diffing needed, since the proxy resolves per-tile coverage server-side).

**Initial ambiguous result, disambiguated via follow-up questions:** the user first reported "Load map (rewriteStyleForProxy) does not work when offline" for cases (b)/(c), which risked reading as a PROXY-03 failure. Two follow-up questions isolated the actual trigger: the user had pressed the harness's "Load map" button again after the app had been fully restarted while already offline — a different scenario than panning within an already-loaded session. Once isolated to "cold restart while offline" vs. "already-loaded session going offline," the load-bearing in-session airplane-mode result was a clean, unambiguous PASS.

### Separate, out-of-scope finding (logged as a follow-up, NOT fixed in this phase)

**Pre-existing bug: `MapStyleSourcesNotifier` has no offline fallback for `/map/style-sources`.**

Root cause of the initial ambiguous result above, traced independently via source read (not by the user restating anything): `_loadStyle()` in the harness — mirroring production `_composeStyle` in both `trail_map.dart` and `navigation_screen.dart` — awaits `ref.read(glyphSpriteCacheProvider.future)`, which transitively depends on `MapStyleSourcesNotifier` (`app/lib/provider/map_style_sources_provider.dart`). That provider makes an **unconditional** `api.get('/map/style-sources')` network call on every fresh `build()`, with **zero offline fallback or local cache**, even when the glyph/sprite files it needs are already present on disk. It is `@Riverpod(keepAlive: true)`, so once resolved successfully in a running app session it stays cached for that session's lifetime — explaining why the harness's case (a) online load succeeded and why panning within that SAME session while later going offline (cases b/c) worked fine. But a genuinely cold app process that launches (or restarts) directly into an offline state has no way to ever resolve this provider, so `_composeStyle`/`_loadStyle` fails at the glyph-cache step before `rewriteStyleForProxy` is ever reached.

This bug:
- **Dates to Phase 15** (`map_style_sources_provider.dart`'s original introduction) — unrelated to Phase 25.1's tile-proxy work.
- **Equally affects current production code today** — both `trail_map.dart` and `navigation_screen.dart` call the exact same `glyphSpriteCacheProvider` chain, so this is not introduced or worsened by this phase.
- **Is out of scope for PROXY-01/02/03** and is NOT turned into a new task in this phase's remaining plans.
- **Logged as a follow-up** in `.planning/STATE.md`'s Blockers/Concerns section (see below) for a future phase to pick up.
