## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** The proxy replaces region tile serving on **both** `TrailMap` and `navigation_screen`, not just the broken `navigation_screen` path. `TrailMap`'s current add-only incremental reconcile passed all its Phase 25 UAT tests, but unifying both screens on one mechanism deletes the `_sourceFromJson`/`_layerFromJson` duplication between the two files and leaves exactly one rendering mechanism app-wide, rather than one working-but-legacy path and one newly-replaced path living side by side long-term.
- **D-02:** When two downloaded regions' bboxes overlap and a requested tile falls inside the overlap, the proxy serves the tile from the region with the **smallest bbox** (most specific/local region wins over a broader one that happens to also cover the same spot).
- **D-03:** If two overlapping regions have bboxes of exactly equal size (a tie), the proxy serves the tile from whichever region was **most recently downloaded**. This tie-break is expected to be rare in practice.
- **D-04:** If the on-device spike finds MapLibre Native does NOT reliably load loopback-HTTP tiles while offline (airplane mode), do **not** pre-commit to falling back to a patched version of the old incremental reconcile. Stop and reassess with the user instead — the patch-based fallback (reentrancy guard + symmetric tracking-set updates + gating camera-idle during GPS-follow) remains a known, previously-scoped option, but the decision of whether to use it, revisit the proxy design, or consider something else is deferred to that point, not decided now.

### Claude's Discretion

- Server lifecycle details (app-wide singleton `HttpServer` vs. per-screen, port selection/binding strategy, start/stop tied to app foreground/background) — not discussed; implementation detail for planning/research to resolve using standard `dart:io` `HttpServer` patterns.
- Exact per-tile "which archive covers this tile" lookup mechanism (e.g., how `splitRegionTilePaths`/`localTilePathsForBounds`-style logic gets adapted to a per-tile `(z,x,y)` query instead of a bbox query) — technical implementation detail.
- Whether the vector and DEM proxy endpoints are one server with two routes, or two separate servers — implementation detail.
- Uncovered-tile behavior at the proxy layer (e.g., HTTP 404 vs. empty tile response) — should produce the same user-visible outcome already locked in Phase 25 (D-01/D-02 there: blank basemap, no banner/indicator), but the exact proxy-level mechanism to achieve that is Claude's call.

None — discussion stayed entirely within phase scope. No new capabilities were proposed.

## Summary

The three mandatory feasibility claims from the debug doc's "Considered Alternative" section are **independently re-verified against the installed package source** (not just trusted): `maplibre` 0.3.5's `VectorSource` and `RasterDemSource` both expose a `tiles: List<String>?` field usable as an XYZ URL template, and `pmtiles` 1.2.0's `PmTilesArchive.tile(ZXY(z,x,y).toTileId())` is a real, working per-tile random-access API returning a `Tile` with `.bytes()` (decompressed) and a `TileType`→MIME-type mapping already built into the package. No new third-party package is required: `dart:io HttpServer` (Dart SDK, not a pub.dev package) is sufficient for the loopback server, and `shelf` is correctly identified in the debug doc as unnecessary weight for a single-purpose tile responder.

The bigger, previously-undocumented finding is that **PROXY-03's risk gate is not purely a device-only unknown**. Two concrete, source-and-docs-verifiable platform requirements were found that will silently break the proxy regardless of airplane-mode behavior if not addressed: (1) Android's Network Security Config blocks all cleartext (HTTP, non-TLS) traffic by default for apps targeting API 28+ (Wanderer's `targetSdk` is `flutter.targetSdkVersion`, which is well above 28) — this applies to `127.0.0.1` exactly like any other host unless explicitly exempted, and MapLibre Android's tile-fetch path resolves to `org.maplibre.gl:android-sdk-opengl`, which uses OkHttp (confirmed via the package's own `HttpRequestUtil.setOkHttpClient()` surface), and OkHttp enforces this same Android platform policy; (2) iOS App Transport Security's exact treatment of loopback IP literals is genuinely mixed across sources, so proactively adding an ATS exception is the only zero-risk option. Neither the current `AndroidManifest.xml` nor `Info.plist` has any cleartext/ATS exception today — both must be added as explicit phase tasks, independent of whatever the on-device spike finds about airplane-mode reliability. `NSLocalNetworkUsageDescription` (the iOS 14+ Local Network permission prompt) is confirmed NOT required for loopback traffic — it only gates connections that could reach *other* devices on the LAN.

A second architectural finding worth flagging prominently to the planner: because the proxy source becomes a single **static** entry in the style JSON (declared once at `initStyle`/every `setStyle`, never incrementally added/removed), the entire `_addedSourceIds`/`_addedLayerIds`/`_seedRegionTracking` tracking-set machinery in both `trail_map.dart` and `navigation_screen.dart` is deleted outright, not patched — this is the actual mechanism by which the reentrancy bug class disappears (D-04's premise). `offline_style_rewriter.dart`'s N-cell-duplication logic (`_rewriteSourceGroup`) also becomes unnecessary for **tile serving** (MapLibre's native XYZ tile loader now handles arbitrary viewport coverage against the proxy directly) but the file is NOT deleted outright — its `glyphs`/`sprite` `file://` rewriting and DEM-vs-vector source-type splitting are unrelated concerns that still apply. One real, not-yet-resolved gap surfaced by this research (not previously identified in the debug doc): there is no `StyleController.reloadSource()`/`invalidateTiles()` API in `maplibre_platform_interface` 0.3.5, so it is unverified whether MapLibre Native automatically re-fetches a tile it previously received as "not found" once a region finishes downloading mid-session — this must be added to the on-device spike's test list (see Open Questions).

**Primary recommendation:** Build a single `dart:io HttpServer` bound to `InternetAddress.loopbackIPv4` on an OS-assigned ephemeral port (`port: 0`), started in `main()` immediately after `openStore()` (mirroring the existing `objectBoxProvider.overrideWithValue(store)` pattern) and exposed to the widget tree via a `keepAlive` Riverpod provider override holding the resolved base URL. Serve `/vector/{z}/{x}/{y}.pbf` and `/dem/{z}/{x}/{y}.png` routes (one server, two path prefixes — simplest option under Claude's Discretion), each resolving the winning region via a new pure, unit-testable `resolveRegionForTile` helper (bbox-overlap filter + smallest-area-then-most-recent sort, sibling to `bboxOverlaps`/`splitRegionTilePaths` in `tile_repository_manager.dart`), then reading the winning archive via a small LRU-style cache of open `PmTilesArchive` handles (never reopen-per-request). Add the Android/iOS cleartext exceptions as explicit, non-optional tasks in Wave 1, ahead of/alongside the spike, since they are required for the spike itself to produce a meaningful result.

### Pattern 1: Static XYZ proxy source (replaces incremental add/remove entirely)

**What:** Both `VectorSource` and `RasterDemSource` accept a `tiles: List<String>` XYZ URL template instead of a single-archive `url:`. Declaring this ONCE per composed style (baked into every `initStyle`/`setStyle` JSON output, exactly like the existing `glyphs`/`sprite` fields) means MapLibre Native's own tile loader decides which tiles to request based on the live viewport — no Dart-side `addSource`/`removeSource`/`addLayer`/`removeLayer` calls are needed for region coverage at all.

**When to use:** Anywhere the style currently repoints a tiled source at a local `.pmtiles` archive (today: `_pointSourceAtCell`/`_pointDemSourceAtCell` in `offline_style_rewriter.dart`). Replace those two functions' `pmtiles://file://<cellPath>` output with a fixed `http://127.0.0.1:<port>/vector/{z}/{x}/{y}.pbf` / `.../dem/{z}/{x}/{y}.png` template — no per-cell/per-region enumeration needed in the style JSON at all, since the proxy resolves coverage per-request.

**Example (source-verified fields):**
```dart
// Source: maplibre_platform_interface-0.3.5/lib/src/style/sources/vector_source.dart
ml.VectorSource(
  id: 'protomaps',
  tiles: ['http://127.0.0.1:$proxyPort/vector/{z}/{x}/{y}.pbf'],
  maxZoom: 14, // must match generator.go's extraction depth — same constant
              // _offlinePmtilesMaxZoom already encodes today
);

// Source: maplibre_platform_interface-0.3.5/lib/src/style/sources/raster_dem_source.dart
ml.RasterDemSource(
  id: 'hillshadeSource',
  tiles: ['http://127.0.0.1:$proxyPort/dem/{z}/{x}/{y}.png'],
  maxZoom: 12, // must match demMaxZoom in db/services/tiles/generator.go
  tileSize: 512,
  encoding: const ml.RasterDemTerrariumEncoding(),
);
```

**Consequence for `_swapStyle`:** Because this is now just another static field in the composed style JSON (like `glyphs`/`sprite`), the existing `_swapStyle()` pattern in both `TrailMap` and `NavigationScreen` (recompute composed JSON via `_composeStyle`, call `controller.setStyle(json)` if it differs from `_lastStyleJson`) automatically re-declares the proxy source correctly on every theme toggle or glyph-cache-warm `setStyle` call — **no special-casing needed**. This directly answers mandatory research question 8: a full `setStyle` re-declares the source from scratch every time (it always has — `setStyle` replaces the whole document), and since the proxy source is now *always* part of `_composeStyle`'s output rather than something added after the fact, it survives every `setStyle` call by construction.

### Pattern 2: Per-tile overlap resolution (PROXY-02/D-02/D-03)

**What:** A new pure function, sibling to `bboxOverlaps`/`splitRegionTilePaths` in `tile_repository_manager.dart`, that takes a tile's derived lon/lat bbox and an `Iterable<RegionEntity>`, filters to bbox-overlapping AND downloaded (vector or DEM, per the requested kind) regions, then picks a winner: smallest bbox area first, `DownloadedTilePackageEntity.downloadedAtUtc` descending as the tie-break.

**When to use:** Called once per incoming proxy HTTP request (not per viewport) — MapLibre issues individual tile requests as panning/zooming occurs, so this must be cheap. With a realistic region count (tens, not thousands, per `SETUI` requirements' "flat list is the right complexity" framing), a full linear scan of `_store.box<RegionEntity>().getAll()` per request is expected to be fast enough without a spatial index; flag as a scaling concern only if profiling later shows otherwise.

**Example (new, unit-testable like its siblings):**
```dart
// New sibling to bboxOverlaps/splitRegionTilePaths in tile_repository_manager.dart
@visibleForTesting
RegionEntity? resolveRegionForTile(
  Iterable<RegionEntity> regions,
  LngLatBounds tileBounds, {
  required bool dem, // true = DEM package, false = vector package
}) {
  final candidates = regions.where((region) {
    final target = dem ? region.demPackage.target : region.vectorPackage.target;
    if (target?.localFilePath == null) return false;
    return bboxOverlaps(
      minLon: region.minLon, minLat: region.minLat,
      maxLon: region.maxLon, maxLat: region.maxLat,
      query: tileBounds,
    );
  }).toList();

  if (candidates.isEmpty) return null;

  candidates.sort((a, b) {
    final areaA = (a.maxLon - a.minLon) * (a.maxLat - a.minLat);
    final areaB = (b.maxLon - b.minLon) * (b.maxLat - b.minLat);
    final areaCompare = areaA.compareTo(areaB);
    if (areaCompare != 0) return areaCompare;
    // Tie-break: most-recently-downloaded wins (D-03).
    final aTarget = dem ? a.demPackage.target : a.vectorPackage.target;
    final bTarget = dem ? b.demPackage.target : b.vectorPackage.target;
    final aTime = aTarget?.downloadedAtUtc ?? DateTime.fromMillisecondsSinceEpoch(0);
    final bTime = bTarget?.downloadedAtUtc ?? DateTime.fromMillisecondsSinceEpoch(0);
    return bTime.compareTo(aTime); // descending — most recent first
  });

  return candidates.first;
}
```
Plain planar `(maxLon-minLon) * (maxLat-minLat)` degree² area is deliberately used rather than a great-circle/projected area calculation — regions are hand-curated, admin-defined bboxes (BACK-01), not user-drawn shapes, so latitude-dependent distortion is irrelevant to the "which region feels more local" UX intent behind D-02. `[ASSUMED — reasoning-based, not sourced; flag for planner/discuss-phase confirmation if precision matters more than this research assumes]`

### Pattern 3: Server lifecycle — `main()`-time bind, `keepAlive` provider exposure

**What:** Mirrors the existing `objectBoxProvider.overrideWithValue(store)` pattern in `main.dart`: bind the `HttpServer` in `main()` (after `openStore()`, since the request handler needs the `Store` to query `RegionEntity`), then override a `keepAlive` provider with the resolved base URL before `runApp()`.

**When to use:** The server's port must be known BEFORE the first `_composeStyle()` call on either `TrailMap` or `navigation_screen` — both screens bake the URL template into the very first style JSON they build. Starting the server lazily (e.g., on first map-screen mount) would require `_composeStyle` to handle "port not yet known" as a loading state, adding complexity the `main()`-time approach avoids entirely. This directly answers mandatory research question 4.

**Example (mirrors `objectbox_store_provider.dart` and `main.dart`'s existing wiring):**
```dart
// provider/region/tile_proxy_provider.dart
@Riverpod(keepAlive: true)
class TileProxyBaseUrl extends _$TileProxyBaseUrl {
  @override
  String build() => throw UnimplementedError(); // overridden in main.dart
}

// main.dart
final store = await openStore(directory: dbPath);
final proxyServer = await TileProxyServer.start(store); // binds loopbackIPv4, port: 0
runApp(
  ProviderScope(
    overrides: [
      objectBoxProvider.overrideWithValue(store),
      tileProxyBaseUrlProvider.overrideWithValue(proxyServer.baseUrl), // 'http://127.0.0.1:<port>'
      cookieJarProvider.overrideWithValue(jar),
    ],
    child: MainApp(),
  ),
);
```
The server itself never needs to stop for the lifetime of the app process (matches the `keepAlive` ObjectBox `Store` precedent) — no app-lifecycle-driven start/stop is needed since loopback binding has no battery/network cost while idle and the OS reclaims the socket on process death.

### Anti-Patterns to Avoid

- **Binding to `InternetAddress.anyIPv4` (`0.0.0.0`) instead of `InternetAddress.loopbackIPv4`:** exposes the tile server to the entire local network/hotspot the device is connected to — an unintended local information-disclosure and attack-surface increase. Must bind loopback-only.
- **Reopening `PmTilesArchive.fromFile()` on every single tile request:** each open re-reads and parses the archive header/root directory (`fromReadAt` in `archive.dart`). Cache open `PmTilesArchive` handles per resolved file path (small LRU, matching the package's own internal `_leafCache` precedent), invalidating an entry when `TileRepositoryManager.deleteRegion`/a fresh download replaces that region's file.
- **Trusting `ZXY`'s constructor `assert`s as request validation:** `pmtiles-1.2.0/lib/src/zxy.dart`'s `ZXY(z, x, y)` constructor validates ranges via Dart `assert()`, which is **stripped in release/profile builds** — a malformed or out-of-range `z`/`x`/`y` parsed from the HTTP request path would silently skip validation in a release build. The proxy's own request handler must explicitly bounds-check `z`/`x`/`y` (e.g., `z >= 0 && z <= 26`, `x/y in [0, 2^z)`) before constructing a `ZXY`, independent of the package's own assert. `[VERIFIED: installed package source — pmtiles-1.2.0/lib/src/zxy.dart:11-14]`
- **A fixed, well-known port number:** prefer OS-assigned ephemeral (`port: 0`) — a predictable fixed port is a (low-severity, since tile data isn't sensitive, but non-zero) local-attack-surface consideration on mobile OSes, where the loopback interface is shared across all apps on the device (unlike containerized environments).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |

| Tile-ID ↔ (z,x,y) conversion for pmtiles lookups | A custom Hilbert-curve tile-id encoder | `pmtiles` package's own `ZXY(z, x, y).toTileId()` / `ZXY.fromTileId()` | Already a correct, tested implementation shipping in the pinned dependency (`pmtiles-1.2.0/lib/src/zxy.dart`) — re-deriving Hilbert-curve math is unnecessary and error-prone |

**Key insight:** This phase's "don't hand-roll" list is short because most of the hard parts (tile-id math, MIME mapping, archive random access) are already solved by the pinned `pmtiles` package — the genuinely new code this phase writes is glue (HTTP routing, region-resolution, server lifecycle), which is appropriately small and hand-rolled per Claude's Discretion in CONTEXT.md.

## Common Pitfalls

### Pitfall 1: Android blocks the proxy's cleartext HTTP by default — independent of airplane mode

**What goes wrong:** MapLibre Native's tile request to `http://127.0.0.1:<port>/...` fails immediately with a cleartext-not-permitted error on a real Android device, and this happens **online or offline** — it has nothing to do with airplane mode.
**Why it happens:** Since Android 9 (API 28), cleartext (non-TLS HTTP) traffic is blocked by default for apps whose `targetSdkVersion` is 28+. Wanderer's `android/app/build.gradle.kts` sets `targetSdk = flutter.targetSdkVersion` (Flutter's current default is well above 28), and neither `AndroidManifest.xml` nor a `network_security_config.xml` currently grants any cleartext exception (confirmed absent by direct read). MapLibre's Android SDK dependency (`org.maplibre.gl:android-sdk-opengl:13.0.+`, read from `maplibre_android-0.3.5`'s own `build.gradle`) uses OkHttp for tile HTTP requests (`HttpRequestUtil.setOkHttpClient()` is part of its public surface), and OkHttp on Android enforces the platform's Network Security Config cleartext policy for every host, including `127.0.0.1` — there is no automatic loopback exception.
**How to avoid:** Add a `network_security_config.xml` with a `<domain-config cleartextTrafficPermitted="true"><domain includeSubdomains="false">127.0.0.1</domain></domain-config>` entry (narrower and more defensible than a blanket `android:usesCleartextTraffic="true"` on the whole `<application>`), referenced via `android:networkSecurityConfig="@xml/network_security_config"` in `AndroidManifest.xml`. This must land as an explicit task, independent of and prior to the on-device spike — otherwise the spike will fail for a reason unrelated to the actual PROXY-03 question.
**Warning signs:** `CLEARTEXT communication to 127.0.0.1 not permitted by network security policy` in `adb logcat`; a tile source that fails to load with no visible Dart-side exception (since the failure occurs inside MapLibre Native's own HTTP layer, not in Dart code the app controls).
**Confidence:** `[CITED: developer.android.com/privacy-and-security/security-config]` for the general policy; `[VERIFIED: maplibre_android-0.3.5/android/build.gradle, app/android/app/build.gradle.kts, app/android/app/src/main/AndroidManifest.xml]` for the project-specific absence of any existing exception and the OkHttp dependency chain.

### Pitfall 2: iOS App Transport Security's loopback treatment is ambiguous — add an explicit exception proactively

**What goes wrong:** Same class of failure as Pitfall 1 but on iOS — a tile request to `http://127.0.0.1:<port>/...` may be blocked by ATS.
**Why it happens:** ATS requires HTTPS by default since iOS 9. Community sources disagree on whether IP-literal loopback addresses (`127.0.0.1`) are automatically exempted or require an explicit `NSAppTransportSecurity` exception — some report IP-literal loopback works with no `Info.plist` change, others report `localhost`/loopback needs an explicit `NSExceptionDomains` entry. `Info.plist` today has no `NSAppTransportSecurity` key at all.
**How to avoid:** Add an explicit, narrowly-scoped ATS exception rather than relying on the ambiguous default — either an `NSExceptionDomains` entry for `127.0.0.1` (and `localhost`, to cover both address forms) with `NSExceptionAllowsInsecureHTTPLoads = true`, or the coarser `NSAllowsLocalNetworking = true` key (introduced iOS 10, intended for local/`.local` peer networking but also commonly used to unblock loopback dev servers). This is zero-cost (no user-facing prompt, no App Review risk for a loopback-only exception) and removes a genuinely unresolved variable ahead of the spike.
**Warning signs:** A tile source that silently fails to load on iOS with no Dart-side exception, isolated to iOS while Android (once Pitfall 1 is fixed) works.
**Confidence:** `[CITED: multiple community/Apple-forum sources — MEDIUM, genuinely mixed evidence]`. Recommend treating "add the exception" as required regardless of which reading of ATS behavior is correct, since the cost of adding it is near zero.

### Pitfall 3: `NSLocalNetworkUsageDescription` is NOT needed for loopback — don't add it speculatively

**What goes wrong:** Adding the iOS 14+ Local Network permission usage-description key "just in case" triggers an unnecessary user-facing permission prompt on first launch, for a permission this phase does not need.
**Why it happens:** Easy to confuse with Pitfall 2 since both are iOS networking-permission concerns.
**How to avoid:** Confirmed loopback (`127.0.0.1`/`::1`) traffic never leaves the device and is explicitly exempted from the Local Network privacy restriction — that restriction targets connections capable of reaching *other* devices on the LAN (Bonjour/mDNS discovery, subnet-broadcast, etc.), which this phase's server never does. Do not add `NSLocalNetworkUsageDescription`.
**Confidence:** `[CITED: Apple Developer Forums — multiple corroborating threads, MEDIUM-HIGH]`.

### Pitfall 4: No native "reload/invalidate tile source" API exists — mid-session region-download-complete behavior is unverified

**What goes wrong:** A region finishes downloading while `navigation_screen` is open and displaying a previously-blank (uncovered) area; the newly-downloaded tiles may or may not appear without further action, depending on whether MapLibre Native retries a tile it previously received as 404/empty for the currently-rendered viewport.
**Why it happens:** `maplibre_platform_interface-0.3.5`'s `StyleController` (confirmed by reading `style_controller.dart`'s full method list) exposes `addSource`/`addLayer`/`removeLayer`/`removeSource`/`updateGeoJsonSource`/image helpers — **no `reloadSource`, `invalidateTiles`, or equivalent cache-bust method exists**. The old `_reconcileRegionComposition`'s post-removal camera-nudge trick (`animateCamera` with an unchanged camera, "25-01 finding 1") forces a **repaint** of already-fetched tile data — it is not established whether it also forces a **re-fetch** of tiles MapLibre's own ambient tile cache previously marked as empty/404.
**How to avoid:** This is not resolvable from Dart-level source reading — MapLibre Native's tile-cache retry/backoff behavior lives in its C++ core, outside this package's Dart surface. Add "does a region completing download mid-session make its tiles appear without a screen remount" as an explicit test case in the PROXY-03 on-device spike (see Open Questions). If the spike finds tiles do NOT auto-appear, the fallback is a single `removeSource` + `addSource` pair on the ONE static proxy source id (triggered by the existing `regionListNotifierProvider` listener) — structurally much smaller than the deleted N-region diff loop (fixed, well-known id; no per-region loop; still worth a lightweight boolean reentrancy guard as defense in depth, but not the same bug class as before).
**Warning signs:** On-device spike shows a downloaded region's tiles staying blank in an already-rendered viewport until the user manually pans/zooms or the screen remounts.

### Pitfall 5: Serving gzip-compressed MVT bytes without matching HTTP semantics

**What goes wrong:** Serving `tile.compressedBytes()` (raw gzip-compressed bytes, per `header.tileCompression`) without a correct `Content-Encoding: gzip` response header can produce a client that either fails to parse the vector tile (treats compressed bytes as raw MVT) or double-decompresses.
**How to avoid:** Serve `tile.bytes()` (already decompressed by the package's `Compression.decoder()`) with no `Content-Encoding` header set — this sidesteps the question of whether MapLibre Native's OkHttp/NSURLSession-based fetch transparently handles `Content-Encoding: gzip` identically to a `127.0.0.1` local response as it would a real CDN response. `[ASSUMED — reasoning-based recommendation, not sourced from a specific MapLibre doc; flagged as the safer default]`.

### Pitfall 6: TrailMap's coverage scope changes from "trail's own bounds" to "any downloaded region"

**What goes wrong:** Today, `TrailMap._composeStyle` explicitly queries `TileRepositoryManager.localTilePathsForBounds(widget.trail.bounds)` — offline tiles are scoped to the specific trail's bbox. Under the proxy architecture (a single static, globally-scoped source), `TrailMap` would serve tiles for **any** downloaded region the map happens to render, not just the one(s) covering the trail. Since `TrailMap` typically has a fixed/limited camera (per-trail `fitBounds`, often gesture-disabled), this is likely a non-issue in practice, but it is a genuine behavior change from today's trail-scoped design that D-01 (unify both screens on the proxy) does not explicitly call out.
**How to avoid:** Not a code defect — flag explicitly for the planner/discuss-phase as an intentional-but-not-previously-discussed consequence of D-01, so it can be confirmed rather than silently shipped as a side effect.

## Code Examples

### Minimal `dart:io` loopback tile server skeleton

```dart
// Source: dart:io core SDK API (HttpServer, HttpRequest, HttpResponse) — standard,
// stable API; no external package. High confidence — core SDK docs.
import 'dart:io';

class TileProxyServer {
  final HttpServer _server;
  TileProxyServer._(this._server);

  String get baseUrl => 'http://127.0.0.1:${_server.port}';

  static Future<TileProxyServer> start(Store store) async {
    final server = await HttpServer.bind(InternetAddress.loopbackIPv4, 0);
    final proxy = TileProxyServer._(server);
    unawaited(proxy._serve(store));
    return proxy;
  }

  Future<void> _serve(Store store) async {
    await for (final request in _server) {
      _handle(request, store).catchError((Object e) {
        request.response.statusCode = HttpStatus.internalServerError;
        return request.response.close();
      });
    }
  }

  Future<void> _handle(HttpRequest request, Store store) async {
    final segments = request.uri.pathSegments; // e.g. ['vector', '8', '12', '34.pbf']
    if (segments.length != 4) {
      request.response.statusCode = HttpStatus.notFound;
      return request.response.close();
    }
    final kind = segments[0]; // 'vector' or 'dem'
    final z = int.tryParse(segments[1]);
    final x = int.tryParse(segments[2]);
    final yStr = segments[3].split('.').first; // strip .pbf/.png extension
    final y = int.tryParse(yStr);

    // Explicit bounds check — NEVER rely on ZXY's constructor assert (stripped
    // in release builds, see Pitfall "Trusting ZXY's assert").
    if (z == null || x == null || y == null ||
        z < 0 || z > 26 || x < 0 || x >= (1 << z) || y < 0 || y >= (1 << z)) {
      request.response.statusCode = HttpStatus.badRequest;
      return request.response.close();
    }

    // ... resolveRegionForTile + PmTilesArchive.tile(ZXY(z, x, y).toTileId())
    // ... on TileNotFoundException / no covered region: statusCode = 404
  }
}
```

// Reasoning-based pattern — not sourced from a specific doc; mirrors pmtiles

class _ArchiveCache {
  final Map<String, PmTilesArchive> _open = {};

  Future<PmTilesArchive> forPath(String path) async {
    final cached = _open[path];
    if (cached != null) return cached;
    final archive = await PmTilesArchive.fromFile(File(path));
    _open[path] = archive;
    return archive;
  }

  Future<void> invalidate(String path) async {
    final archive = _open.remove(path);
    await archive?.close();
  }
}

### Standard XYZ tile → lon/lat bbox conversion (no existing app dependency)

```dart
// Standard Web Mercator / "slippy map" tile math — widely documented
// (OSM wiki "Slippy map tilenames"). [CITED: standard formula, HIGH confidence
// — well-established, not project- or package-specific]
import 'dart:math' show pi, atan, exp, sinh;

({double west, double south, double east, double north}) tileToBounds(
  int z, int x, int y,
) {
  double lon(int tx) => tx / (1 << z) * 360.0 - 180.0;
  double lat(int ty) {
    final n = pi - 2.0 * pi * ty / (1 << z);
    return 180.0 / pi * atan(0.5 * (exp(n) - exp(-n)));
  }
  return (west: lon(x), east: lon(x + 1), north: lat(y), south: lat(y + 1));
}
```

## Open Questions

1. **Does MapLibre Native reliably load loopback-HTTP tile sources while the device reports no network connectivity (airplane mode)?**
   - What we know: Loopback traffic (127.0.0.1) never traverses a physical network interface — it stays entirely within the OS's local TCP/IP stack, independent of cellular/Wi-Fi radio state. No Android/iOS platform-level "check connectivity before allowing loopback socket" behavior was found in any searched source. No "reachability"/"connectivity"/"airplane" logic exists anywhere in the `maplibre_android`/`maplibre_ios`/`maplibre_platform_interface` Dart-level package source (confirmed via full-tree grep) — but the actual HTTP fetch logic lives in MapLibre Native's C++/JNI/Swift core (OkHttp on Android, confirmed via the `android-sdk-opengl` dependency's own `HttpRequestUtil` surface; NSURLSession-based on iOS, not independently confirmed this session), which is outside what Dart-level source reading can fully verify.
   - What's unclear: Whether OkHttp (Android) or NSURLSession (iOS) perform any proactive "is the device online" pre-flight check before attempting a socket connection that could reject a loopback request purely because the OS's global connectivity state reports "offline" — this would be an unusual and undocumented behavior if present, but cannot be ruled out from source reading alone.
   - Recommendation: This is precisely why PROXY-03 mandates an on-device spike — it cannot be resolved further by research. The spike harness should mirror `region_render_spike_harness.dart`'s established pattern (`app/test/services/tile_proxy_spike_harness.dart`, launched via `flutter run -t ...` against a physical device) and test, at minimum: (a) tiles load online via the proxy; (b) tiles continue loading with Wi-Fi/cellular data OFF but airplane mode NOT engaged; (c) tiles continue loading with airplane mode fully engaged; (d) a region completing download mid-session becomes visible in an already-rendered viewport without a screen remount (Pitfall 4); (e) the Android cleartext exception (Pitfall 1) and iOS ATS exception (Pitfall 2) are both confirmed necessary/sufficient on real hardware, not just per the research above.

2. **Does a `removeSource`+`addSource` pair (or some other mechanism) reliably force MapLibre Native to re-fetch previously-404'd tiles for the current viewport?**
   - What we know: No native `reloadSource`/`invalidateTiles` API exists on `StyleController` (confirmed by reading its full method list). The existing camera-nudge trick forces a repaint of already-loaded tile data (a different problem than forcing a re-fetch of previously-missing data).
   - What's unclear: MapLibre Native's internal tile-cache retry/backoff policy for a tile previously returned as "not found" — this logic lives in the C++ core, not the Dart bindings.
   - Recommendation: Add explicitly to the PROXY-03 spike's test list (item d above). If neither light-touch mechanism works, escalate to the user/planner rather than defaulting to a full `setStyle` reload, which reintroduces some of the flash/cost this phase is trying to avoid.

3. **Exact iOS ATS exception mechanism (`NSExceptionDomains` vs. `NSAllowsLocalNetworking`) — which one (or both) is actually required on real hardware?**
   - What we know: Both are documented, valid `NSAppTransportSecurity` keys; community evidence for which one (or whether either) is strictly required for `127.0.0.1` specifically is mixed.
   - What's unclear: The current iOS version's exact behavior (search results referenced discussions of varying vintage; Apple's ATS behavior toward loopback has evolved across iOS versions without a single authoritative changelog entry found).
   - Recommendation: Add both exceptions proactively (zero cost, no App Review risk for a loopback-only exception) rather than trying to determine the minimal-necessary one — let the spike confirm the combined config works, and don't spend further research/planning time narrowing to the theoretically-minimal single key.
