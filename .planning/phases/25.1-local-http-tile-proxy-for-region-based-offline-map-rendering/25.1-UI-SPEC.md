# Phase 25.1 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope Determination: No New UI Surface

This phase is a pure rendering-**mechanism** swap, not a user-facing feature. It replaces `trail_map.dart`'s and `navigation_screen.dart`'s incremental `addSource`/`removeSource`/`_reconcileRegionComposition`/`_addRegionComposition` region-swap reconcile with a local loopback HTTP tile proxy (an in-app `HttpServer` serving a single static XYZ `tiles:` source) so MapLibre Native's own viewport tracking takes over which regions contribute tiles. It does not change **what the user sees** — only **how** the already-shipped offline map rendering (Phase 25) resolves tiles internally. It is architecturally identical in kind to Phase 25 itself, whose UI-SPEC (`.planning/phases/25-map-rendering-region-based-viewport-pipeline/25-UI-SPEC.md`) correctly recorded "no new UI surface" — this phase produces the same kind of contract.

Confirmed against every upstream artifact read for this research:

- **`.planning/ROADMAP.md` Phase 25.1** — Goal/Why describe a mechanism replacement only ("replace... region-swap reconcile... with a loopback HTTP tile proxy... so MapLibre Native's own viewport tracking handles which regions contribute tiles"). No success criterion, screen, dialog, banner, or copy string is named.
- **`.planning/REQUIREMENTS.md` PROXY-01/02/03** — all three are plumbing/verification requirements: PROXY-01 is an internal source-serving mechanism swap, PROXY-02 is a deterministic backend tile-resolution rule (smallest-bbox-wins, most-recent tie-break) with no user-visible surface, PROXY-03 is an on-device spike verifying HTTP loopback tile loading works offline. None mention a UI element, string, or visual state.
- **`.planning/phases/25.1-local-http-tile-proxy-for-region-based-offline-map-rendering/25.1-CONTEXT.md`** — D-01 through D-04 are all internal architecture/product decisions (scope of the swap, overlap-resolution rule, fallback-decision deferral). The "Claude's Discretion" list (server lifecycle, per-tile lookup mechanism, one-vs-two-server topology, uncovered-tile HTTP status) is explicitly implementation detail, not design-contract material. The doc explicitly reaffirms: "the user-visible outcome... is unchanged from Phase 25's locked decisions; only the underlying mechanism changes" — i.e., uncovered viewport still renders a blank basemap with no banner/toast (Phase 25's D-01/D-02, carried forward unchanged).
- **`.planning/phases/25.1-local-http-tile-proxy-for-region-based-offline-map-rendering/25.1-RESEARCH.md`** — confirms every edit point is an existing file (`trail_map.dart`, `navigation_screen.dart`, `tile_repository_manager.dart`) plus new internal-only files (`tile_proxy_server.dart`, `xyz_tile_bounds.dart`, `tile_proxy_provider.dart`) — no new screen, widget, or route. Explicitly notes Android/iOS manifest changes (cleartext/ATS exceptions) are platform networking policy, not UI. The one flagged UX-adjacent nuance (Pitfall 6: `TrailMap`'s tile-serving scope technically widens from "trail's own bounds" to "any downloaded region" under a global static source) is flagged as a behavior note for the planner, not a new visible UI state — `TrailMap`'s camera is fixed/gesture-limited per-trail, so no new user-observable surface results.

**Consequence for this contract:** there is no new component inventory, no new copywriting, no new color/typography/spacing tokens to declare, and no registry usage to vet. The checker's six dimensions should evaluate this phase against "did the executor correctly avoid inventing UI" rather than against a populated visual spec.

## Copywriting Contract

Not applicable. ## Non-Visual Note for Planner/Executor (context, not a design contract item)

The new logic this phase introduces — a loopback `HttpServer` (`tile_proxy_server.dart`), a per-tile region-overlap resolver (`resolveRegionForTile`, PROXY-02), and Android/iOS platform-manifest changes (cleartext/ATS exceptions required per `25.1-RESEARCH.md` Pitfalls 1–2) — is entirely internal to the native-GL tile-fetch pipeline and mobile OS networking policy. None of it renders a Dart widget or user-facing string. The one behavior nuance flagged in research (Pitfall 6: `TrailMap` technically becomes able to render tiles from any downloaded region, not just the ones covering its specific trail, once the source is a single global static proxy endpoint) is a data-scope note for the planner to confirm, not a new visible UI state — `TrailMap`'s camera remains fixed/gesture-limited to the trail's own bounds as established in prior phases, so no new user-observable surface results in practice.
