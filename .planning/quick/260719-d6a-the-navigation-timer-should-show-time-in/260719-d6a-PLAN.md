<objective>
Change the Flutter navigation session so the timer reflects **time in motion** instead of total elapsed wall-clock time, and so that when the user stops moving the timer, GPS tracking, and stats accumulation all pause automatically — resuming when the user moves again.

Purpose: Time-in-motion is the meaningful hiking metric (standing at a viewpoint should not inflate "moving time"), and pausing GPS while stationary saves battery on long hikes.

Output: Movement detection in `navigation_stats_provider.dart` that auto-freezes the existing pause machinery when stationary (making `elapsed` become time-in-motion for free), a low-power GPS config in `tracelet_position_source.dart`, and screen wiring that couples the two.

## Key discovery findings (so the executor does not re-hunt)

- **The timer is already pause-aware.** `NavigationStatsNotifier` computes `elapsed = DateTime.now().difference(_start!) - _pausedAccum` and skips advancing while `state.isPaused`. It already has `_pausedAccum`, `_pauseStart`, and `togglePause()` (manual pause button). Because `elapsed` subtracts all paused time, **auto-pausing on stationary automatically turns `elapsed` into time-in-motion** — no separate "motion clock" is needed. The manual pause button already contributes to `_pausedAccum`; stationary intervals just need to feed the same accumulator.
- **DO NOT hand-roll movement detection.** An earlier attempt at this plan built a custom Haversine+speed-threshold detector and a bespoke low-power GPS config from scratch. This was wrong: `tracelet` (the GPS engine this app already uses, `^3.5.0`, resolved `3.5.7`) has a **native GPS-speed motion state machine** built exactly for this, and it also drives GPS power state automatically. Use it instead of reinventing it:
  - `tl.MotionConfig(motionDetectionMode: tl.MotionDetectionMode.speed, speedMovingThreshold: <m/s>, speedStationaryDelay: <seconds>, stationaryTrackingMode: tl.StationaryTrackingMode.periodic, stationaryPeriodicInterval: <seconds>, stationaryPeriodicAccuracy: <DesiredAccuracy>, speedWakeConfirmCount: <int>)` — a `moving → slowing → stationary` state machine driven by GPS speed (not the accelerometer `stopTimeout`, which is coarse-grained in *minutes* — do not use `MotionDetectionMode.accelerometer`/`stopTimeout` for this). When it declares `stationary`, tracelet **automatically swaps the native tracking engine to periodic one-shot fixes** (`stationaryTrackingMode: periodic`) — this is the low-power GPS behavior; no manual `setStationary()`/second config object is needed.
  - `tl.Tracelet.onSpeedMotionChange(void Function(tl.SpeedMotionEvent) callback)` fires `SpeedMotionEvent(state, previousState, trackingMode)` whenever the state machine transitions. `state` is `SpeedMotionState.moving | slowing | stationary`. Only fires when `motionDetectionMode: speed` is configured. This is the sole signal the app needs to drive `NavigationStats.isStationary` — treat `state == SpeedMotionState.stationary` as not-moving, and `moving`/`slowing` both as moving (do not freeze during the brief "slowing" grace window — the engine hasn't committed to stationary yet).
  - Reject any temptation to also compute movement from `pos.speed`/Haversine in `NavigationStatsNotifier` — tracelet's `onSpeedMotionChange` is the single source of truth for "is the user moving," and `TraceletPositionSource` is the only place that touches tracelet's engine.
- **The GPS battery lever already exists and does not need a new method.** `TraceletPositionSource.setForeground(bool)` already swaps tracelet configs live (no session restart) for the app-lifecycle (foreground/background) dimension. The stationary/moving dimension is now handled *inside* `_foregroundConfig()`'s `MotionConfig` (see above) — tracelet's own engine does the config-equivalent swap internally when it declares stationary/moving, so `TraceletPositionSource` only needs to (a) configure the speed engine and (b) expose a `Stream<bool>` of motion transitions, not implement a second manual GPS-config-swap method.
- **`NavigationStats` is a freezed class** (`freezed` 3.2.5). Adding a field requires regenerating `navigation_stats_provider.freezed.dart` via build_runner.
- **`formatElapsed(stats.elapsed)`** in `navigation_screen.dart` needs no change — the displayed value becomes moving time automatically once the provider logic changes.
- **Tunable defaults** (pick values fit for hiking pace, not vehicle pace — tracelet's own defaults of `speedMovingThreshold: 1.5` m/s / `speedStationaryDelay: 180`s are vehicle-oriented): use `speedMovingThreshold: ~0.4` m/s (~1.5 km/h, slow walking pace), `speedStationaryDelay: ~10` seconds, `stationaryPeriodicInterval: ~20` seconds, `stationaryPeriodicAccuracy: tl.DesiredAccuracy.medium` (or similar mid-tier value — check the enum's available values), `speedWakeConfirmCount: 1` (default; do not add extra debounce, the engine already has `slowing` as a grace state).
</objective>
