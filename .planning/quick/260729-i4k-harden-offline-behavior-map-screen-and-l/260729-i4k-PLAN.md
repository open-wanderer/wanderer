<objective>
Harden the Flutter app's behaviour when it is opened, or loses connectivity, while offline. Today the map screen paints a raw exception string, the list screen paints a generic "Something went wrong", the bottom-nav avatar collapses to a blank grey circle, and the profile screen shows a spinner then an error that also takes the settings gear off screen.

Purpose: an offline user should see a clear, static "You're offline" message with a working Try again action on the map and list screens, keep seeing their cached identity in the nav bar and on the profile screen, and always be able to reach Settings.

Output:
- `onlineStatusProvider` — one keepAlive source of truth fed by a dio interceptor on the shared api client
- `WandererOfflineState` — one reusable offline empty state with a retry CTA
- `avatar_cache_util.dart` — deterministic on-disk avatar cache (no new package)
- `offline_guard_util.dart` + `SettingsOfflineBanner` — Settings stays browsable offline while its network-dependent actions are gated
- Offline takeovers wired into map, list, nav bar, and profile screens

Context compliance (CONTEXT.md locked decisions, all covered below):
| Locked decision | Covered by |
|---|---|
| Global keepAlive `onlineStatusProvider`, seeded by `isBackendReachable`, kept live by a dio interceptor | Task 1 |
| Ordinary HTTP error responses must NOT flip to offline | Task 1 (`isConnectionFailure`) |
| Migrate the three existing `isBackendReachable` call sites; keep the probe itself | Task 1 |
| Map: full takeover of the map area only, `DraggableScrollableSheet` survives | Task 2 |
| List: same takeover replacing "Something went wrong" | Task 2 |
| Try again CTA forces a fresh probe | Task 2 |
| Nav avatar + profile basics reconstructed from the local `UserEntity` | Task 3 |
| Network-only profile extras get a "You are offline" empty state, not an error | Task 3 |
| Settings always reachable from the profile screen while offline | Task 3 |
| Settings visible and browsable while offline, but read-only: anything requiring network (save/sync) is disabled or deferred until connectivity returns | Task 4 (primitives + account screen and its sheets), Task 5 (remaining network-dependent sub-screens) |
| Discretion — per-row disabling vs. a single banner, whichever is least structural change | Task 4 chooses **both, minimally**: one shared banner per screen (a one-line insert) plus a `guardOnline` early-return in each screen's already-existing single save chokepoint. No control tree is restructured. |
</objective>
