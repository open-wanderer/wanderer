<objective>
Fix three defects observed after switching accounts in the Flutter app (log out of A, log in as B, same device):

1. **Privacy leak (top priority):** the local library still lists account A's downloaded trails, including private ones. `TrailEntity`/`WaypointEntity` rows and `<app-docs>/library/<trailId>/` files are global — `Auth.logout()` only clears the `UserEntity` box and the cookie jar (`app/lib/provider/auth_provider.dart:219-225`), so everything account A downloaded stays readable by account B.
2. **Downloaded regions read as not-downloaded while their bytes are still counted.** The two answers come from two different sources that can drift apart: the summary stats the filesystem per region row (`region_disk_usage_util.dart` -> `regionVectorPath(root, region.id)`), while the row status derives from `RegionEntity.vectorPackage.target` (`region_entity.dart:112`). ObjectBox does not cascade or repair a `ToOne`, so once a link is lost the archive stays on disk, keeps being counted, and the row reports `notDownloaded` — and `splitRegionTilePaths` also stops handing that archive to the offline map, so this is a rendering bug too, not only a label bug.
3. **Stale own-profile.** `ownProfileProvider` is `@Riverpod(keepAlive: true)` and calls `ref.read(authProvider.future)` (`profile_provider.dart:42-46`), so nothing rebuilds it when auth changes; the previous account's `Actor` survives the switch until a manual pull-to-refresh.

Shared root cause: per-account local state (ObjectBox rows, on-disk files, keepAlive Riverpod caches) is neither scoped by user id nor dropped on auth change.

**Chosen fix, and why (the (a) scope-by-user-id vs (b) clear-on-switch vs (c) both question):**
**(b) clear on account change**, for the library and every other account-scoped local artifact. Reasoning:
- (a) alone cannot satisfy the privacy requirement. Scoping `TrailEntity` by `userId` leaves account A's GPX tracks, trail photos and waypoint photos sitting in `<app-docs>/library/<trailId>/` and its cached avatar in `<app-docs>/avatars/` — readable by anything with filesystem access, and only *hidden* from account B by a query filter. "No path may leave account A's trails readable by account B" demands deletion, not filtering.
- (a) is also the higher-risk change: a missed query path silently leaks. Deletion is structural — after the purge there is no row and no file to leak, regardless of which read path is used.
- (c) adds the field, the ObjectBox schema change and the query audit on top of the deletion that already closes the hole; no additional privacy is bought. Rejected as scope.
- Deliberately **not** purged: `RegionEntity` / `DownloadedTilePackageEntity` (server basemap data, not user content, expensive to re-download), `CategoryEntity` / `SubcategoryEntity` (server reference data), `LocalSettingsEntity` (device preferences: theme, locale, selected server), `<app-docs>/map_cache/` (shared glyph/sprite cache), `<app-docs>/regions/` (region archives).

Issue 2 gets a self-heal rather than a diagnosis-dependent patch: making the persisted region state reconcile itself against the filesystem at startup fixes the divergence whichever write path lost the link, and simultaneously restores offline rendering for that region. Issue 3 gets the structural fix (watch auth) plus the same cache-invalidation sweep that protects every other keepAlive cache holding account-scoped server data.

Output:
- `account_data_purge_util.dart` — the single account-scoped purge (boxes + directories) with a pure switch predicate
- `account_scope_invalidation.dart` — one list of keepAlive providers holding account-scoped state, invalidated on any auth user-id change
- `region_disk_reconcile_util.dart` — DB-to-disk self-heal for region packages, plus an orphan-directory sweep
- `auth_provider.dart` / `main.dart` / `profile_provider.dart` wiring

**Known limitation, carried over deliberately (not a scope reduction):** a region row flipped `inCatalog = false` by a catalog refresh keeps its archive and keeps being counted, while the Settings tree (built from the fetched hierarchy) does not render it. That is D-08's explicit decision — the archive stays usable offline via the tile proxy, so those bytes are genuinely in use. Surfacing such rows in the UI is a separate change and is not part of this fix.
</objective>
